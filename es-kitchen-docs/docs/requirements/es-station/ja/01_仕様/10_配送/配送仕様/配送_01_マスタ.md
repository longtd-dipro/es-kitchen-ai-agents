## 3. マスタ

### 3-1. 倉庫マスタ（画面06B）

既存の**中継先マスタ**の画面をそのまま骨格として使い、**倉庫区分**（ピッキング／中継／**返送先**）で項目を出し分ける〔サイクル §2.3A〕〔要件 REQ-DL-410・665〕〔決定v2.3 #41〕。凡例：**◎** 必須／**○** 任意／**—** 持たない

- **返送先（`warehouse_type = return`）**：残った商品を本社などへ送り返すときの届け先として登録する拠点〔決定v2.3 #41〕。**複製の理由「返送」のときだけ**納品先として選べる（8-4）。返送先で使う項目（IDのプレフィックス・必須項目の出し分け）は DEV にも書かれていないため未定義
- **倉庫マスタはリードタイムを持たない。** リードタイムは**契約の配送区分（冷蔵／冷凍／資材）ごと**に持ち、**既定値の自動補完もしない**。旧版の「エリア別リードタイム」「エリア」「閉鎖予定日」は削除済みで、閉鎖は #7 のステータスで表す〔サイクル §2.3A・§12-1〕〔決定 #10／#16／#52〕
- **`locked` の起点は「出荷指示リードタイム」ではなく「出荷指示の初回送信成功」**である。#24 が決めるのは**出力のタイミング**だけ〔決定v2.1 #3〕〔要件 REQ-DL-867・812〕
- **倉庫マスタは対応温度帯も持たない**（商品の取扱倉庫から導出する・§3-4）。そのため**ピッキング倉庫だけの必須項目は「倉庫コード」1つ**、中継先だけの必須項目は「運送区分」「営業所コード」〔サイクル §2.3A・§2.3B〕〔要件 REQ-DL-668〕

**ステータスの扱い**〔サイクル §2.3A〕〔要件 REQ-DL-683・684〕

| ステータス | 契約の割当先 | 既存の予定・配送データ | 一覧 | 戻せるか |
|---|---|---|---|---|
| **有効** | 出る | 通常どおり | 既定で表示 | — |
| **無効**（使用を止めた） | 出ない | **動かさない**。そのまま出荷・納品まで完了させる | 既定は非表示。フィルタで表示 | 戻せる |
| **削除済み**（誤登録・重複） | 出ない | **動かさない** | 「削除済みを含む」でのみ表示 | 運営管理者のみ・理由必須 |

- **物理削除はしない。** 削除できるのは**参照している予定・配送データが0件のときだけ**で、1件でもあれば件数を表示して「無効にしますか」と促す。無効化・削除はいずれも理由必須で変更履歴に残す。**仮登録は設けず**、まだ使わない営業所は「無効」で登録しておく
- 新規登録は**「＋ 倉庫を追加」の1つ**。押したあと**倉庫区分を選ぶステップ**を挟み（**既定は「中継先」**）、選んでからフォームを出す〔要件 REQ-DL-685〕。区分の選択画面にはそれぞれの必須項目とIDのプレフィックスを添える。区分を間違えた場合は、参照が0件なら削除して登録し直し、1件でもあれば無効にして新しく登録する。**無効にした倉庫にまだ予定が残っている契約は一覧で出し、運営が手動で付け替える**。タブは基本情報／変更履歴〔原典：納品サイクル設定 §2.3A〕
- 一覧は**検索（倉庫名・カナ・営業所コード・都道府県・市区町村・郵便番号）**（2026/09/30 変更。旧：倉庫名・カナ・営業所コード・都道府県）**／倉庫区分・運送区分での絞り込み／ページング／CSV一括取込・一括更新**を備える。倉庫を新規に追加すると**出荷不可**枠が未設定になるため、一覧に**「出荷不可枠：未設定」**と表示して画面01へ誘導する〔サイクル §2.3A〕〔要件 REQ-DL-672・673・674・686〕 一覧には**住所列**（郵便番号・都道府県・市区町村・町域・番地）を出す。**最寄りの中継先（営業所）をシステムで自動判別はしない**。運営が住所で検索して選び、ヒットしなければ新規登録する〔要件シート 行29・決定_要件シート一部反映_回答_20260930〕 **移行**：既存の中継先データは**倉庫区分＝中継**としてそのまま取り込む（約300件はCSV）。追加作業は**ピッキング倉庫2件の登録**、**画面01での出荷不可枠の設定**、**商品の取扱倉庫の設定**だけ〔サイクル §2.3B〕

### 3-2. 中継先

> **2026/10/01 追加（お客様確認 B1）**：営業所の閉鎖は自動では検知しない（手段がない）。代わりに、中継先の詳細に**その中継先を使っている拠点（契約の配送ルート）の一覧**を出し、閉鎖が分かったときに影響する拠点をすぐ確かめられるようにする〔要件 REQ-DL-209〕。

|---|---|---|

| 件数 | **約300件**。検索・絞り込み・ページング・CSV一括取込／更新が前提 | 〔サイクル §2.3A〕〔要件 8H-6〕 |
| 中継の段数 | **2段以上の中継は想定しない** | 〔要件 8H-6〕 |
| 営業所コード | 配送会社から**支給され、変わることがある**。送り状に出る。CSVで一括更新できるようにする | 〔サイクル §2.3A〕〔要件 REQ-DL-673〕 |
| 持たないもの | **リードタイムを持たない**。**送り状も再発行しない**。件数しきい値・出荷指示リードタイム・**出荷不可**枠・日別の不可日を持たない。**途中ステータスも取得しない** | 〔サイクル §2.3B・§4C-2〕〔要件 REQ-DL-814〕 |

| 最寄りの判別（2026/09/30 追加） | **自動判別しない（検索のみ）**。中継先一覧を都道府県・市区町村・郵便番号で検索し、住所列を見て選ぶ。ヒットしなければ新規登録する | 〔要件シート 行29・決定_要件シート一部反映_回答_20260930〕 |

| 地点の資料 | 搬入経路図・マニュアルは**拠点・中継先マスタ側（地点の資料）**に持ち、配送データにはコピーせず参照で出す | 〔サイクル §4A-4C〕〔要件 REQ-DL-826〕 |

- 配送ルートは**固定2段階（ピッキング倉庫→中継先）を廃し、配送元・配送先を都度指定できる可変構造**とする。配送先表示は中継先と最終配送先を**2行に分けて**表示する〔サイクル §0〕〔要件 REQ-DL-411〕 **中継があってもリードタイムは合計1つが正。** 中継分は参考値として表示するだけで、計算には使わない〔決定 #21〕

### 3-4. 商品と倉庫

**商品と倉庫は多対多**で持つ（`商品マスタ ──< 商品取扱倉庫 >── 倉庫マスタ`）〔サイクル §2.3C〕〔要件 REQ-DL-675・676〕

| テーブル | 持つもの |
|---|---|
| **商品マスタ** | 商品コード・商品名・温度帯・入数・消費期限・**単価**・説明 |
| **商品取扱倉庫**（新規） | 商品 × 倉庫の組と**取扱ステータス（有効／無効）**のみ |

- **持ち方**：両方の倉庫で扱う商品は商品1件＋取扱行2件、関東専用・関西専用の商品は商品1件＋取扱行1件、**同じ商品名だが単価・説明が違うなら商品を2件に分ける**（それぞれ取扱行1件）
- **倉庫ごとに変わる属性は持たない。** 同じ商品を同じ倉庫に設定した場合は**すべて同じ前提**とし、**単価や説明が異なるなら別の商品として登録する**。入数・単価は商品マスタが持つ
- **温度帯の判定**：**倉庫マスタ**は対応温度帯を持たないため、配送区分で「冷凍 × 国分センター」のような指定をしたときは**その倉庫でその温度帯の商品を1件以上扱っているか**で判定し、0件なら「先に商品の取扱倉庫を設定してください」と警告する〔要件 REQ-DL-668〕 **順番**：契約（拠点）→ 配送区分で**倉庫** → その倉庫で**取扱がある商品** → 法人に見せる商品。倉庫を先に決めないと商品が出せないため、**契約で倉庫を選ぶ設定は残す**
- **契約の倉庫を変えたとき**：移動先に取扱行がない商品だけが置き換えの対象になる。「そのまま使える商品」と「置き換えが必要な商品」を分けて表示し、運営が確認してから**適用月（サイクル月の A1）から**適用する〔要件 REQ-DL-677〕
- **複製で別倉庫から出すとき**：移動先に取扱行があればそのまま複製できる。なければ**代替品扱い**とし、商品を選び直す。在庫は**倉庫別**に持ち、**倉庫間の移動（横持ち）はフェーズ2で作らない**〔要件 REQ-DL-678・681〕

### 3-6. 倉庫マスタ側と配送サイクル設定側の境界

**切り分けの原則は「暦・日付にかかわるものは配送サイクル設定、倉庫そのものの属性は倉庫マスタ」**〔サイクル §2.3・§2.3A〕〔要件 REQ-DL-686〕

| 設定項目 | 持ち場 | 単位 | 理由 |
|---|---|---|---|
| **出荷不可枠（A1〜D7）** | **配送サイクル設定（画面01）の倉庫タブ** | 倉庫ごとに**1組**。設定対象期間の全体に適用 | 枠が日付ではなく**サイクルスロット**なので、カレンダーの上でないと「どの日が止まるか」を確認できない |
| **日別の出荷不可日**（棚卸し・設備点検など） | **配送サイクル設定（画面01）の倉庫タブ** | 倉庫ごと。**開始日〜終了日の期間**で登録できる | 同上。ある倉庫の棚卸し日が他の倉庫のピッキングを止めることはない |
| 祝日にどの倉庫が休むか | **配送サイクル設定（画面01）** | 倉庫ごと | 対象期間の祝日をまとめて不可日に登録する操作を置く |
| サイクル休止期間・納品祝日扱い日 | **配送サイクル設定（画面01）** | **全社共通** | 配送サイクル（28スロット）自体が全社共通のため |
| **件数しきい値**（既定300件／日） | **倉庫マスタ** | 倉庫ごと | 日付と関係ない**倉庫の能力値**。資材配送は件数に含めない |
| **出荷指示リードタイム**（既定3日） | **倉庫マスタ** | 倉庫ごと | 同上。**出力のタイミング**を決める（`locked` の起点ではない） |
| **連携**（出荷指示CSVの出力単位・取消の扱い・再送の締切） | **倉庫マスタ** | 倉庫ごと | 同上 |
| **リードタイム（ピッキング→納品）** | **契約の配送区分** | 契約（拠点）ごと・区分（冷蔵／冷凍／資材）ごと | **倉庫マスタも中継先も持たない。既定値の自動補完もしない** |
| **便種別 `service_form`** | **配送区分（delivery channel）** | 配送区分ごと | **契約のルートには置かない**〔決定v2.1 #7〕 |

| **納品不可曜日**・受取不可日・**前倒す・後ろ倒す** | **契約（拠点）** | 契約（拠点）ごと | 納品日のみを制御する |

- **倉庫マスタでは出荷不可枠を編集させない。** 倉庫を新規に追加すると未設定になるため、一覧に「出荷不可枠：未設定」と出して画面01へ誘導する〔要件 REQ-DL-686〕 **登録するのは運営（物流）。** 倉庫にはシステム内の画面がないため、**出荷不可**日の登録も画面04の閲覧も運営が行う。**倉庫タブは絞り込みでしかない**〔決定v2.1 #2〕〔要件 REQ-DL-680・885〕

### 3-7. 拠点の受取時間帯（子テーブル）

受け取れない日（納品不可曜日・受取不可日）とは別に、**受け取れる時間帯と納品のしかた**を拠点の項目として持ち、**配送データへ写し取ってドライバーに見せる**〔サイクル §3.1C〕〔要件 REQ-DL-838・877・878〕〔決定v2.1 #8〕

| 項目 | 持ち方 | 必須 | 説明 |
|---|---|---|---|
| **受取時間帯** | **子テーブル `site_receive_windows(site_id, from_time, to_time, sort_order)`** | ○ | その拠点が荷物を受け取れる時間帯（例 `09:00`〜`12:00` と `13:00`〜`16:00`）。**1拠点に複数行持てる** |
| **納品条件** | text | ○ | 受け取りのしかた（例：「裏口から搬入」「守衛所で受付票を提出」「担当者不在時は置き配不可」）。搬入経路図そのものは「地点の資料」として別に持つ |

| 論点 | 決まり |
|---|---|
| **1組持ちの禁止** | **`from`/`to` を1組だけ持つ形にしない。** 午前・午後で分かれる拠点があり、1組では表せないため |
| 配送データ側 | **`delivery_receive_windows(delivery_id, from_time, to_time, sort_order, snapshot_at)`** |
| **スナップショットのタイミング** | **配送データを作るとき（確定生成）に、`site_receive_windows` をリストごと `delivery_receive_windows` へ写し取る**（住所と同じ扱い）。1行だけ選ぶのではなく、その時点の**全行を `sort_order` ごと**コピーする |
| 予定（`draft`）段階 | **スナップショットしない。** 予定は拠点マスタを参照して表示する |
| 複製したとき | 再配達・分納・代替便で作る子の配送データは、**親のスナップショットをそのままコピー**する（複製時点の拠点マスタを引き直さない） |
| ドライバーへの表示 | **納品先カードに全部の時間帯を `sort_order` の順に出す。** ドライバーが拠点マスタを見に行かなくてよい状態にする |
| 日付計算との関係 | **受取時間帯は日付の計算には使わない。** 納品日の決定は受取不可日・**納品不可曜日**で行う。当日の回り順をドライバー・委託配送会社が決めるための情報 |
