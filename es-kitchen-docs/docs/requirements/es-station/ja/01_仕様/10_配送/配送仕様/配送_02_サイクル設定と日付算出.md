## 4. 配送サイクル設定（画面01・システム管理者）

画面01は、納品日とピッキング日のもとになる**配送サイクル**を作る唯一の画面である。左にカレンダー、右に設定パネルを置いた単一画面の左右分割構成で、左で結果を確認しながら右を操作する〔サイクル §2.0A・§2.1〕。ここで作った日付が納品予定（`plan lifecycle`＝`draft`）になり、オーダー開始日に配送データへ確定生成される。**この設定が入っていない月は、納品予定も配送データも作られない。法人にも表示されず、変更申請もできない**〔サイクル §2.0B〕。

呼称は **「配送サイクル」に統一**する（ファイル名 `納品サイクル設定_仕様書.md` はそのまま）〔決定 #20〕〔要件 REQ-DL-848〕。「納品日」「納品予定」「納品スロット」「納品祝日扱い日」など、サイクル以外の「納品」は変えない。**この章で扱う状態は `plan lifecycle`（`shipping_plans.lifecycle`＝`draft` / `published` / `locked`）だけ**であり、配送データ側の `delivery status`（出荷待／出荷済／…／納品済）とは別の状態機械である。**両方をまとめて「ステータス」とは呼ばない**〔決定v2.1 S5〕〔要件 REQ-DL-883〕。

**`倉庫管理者` というロールは存在しない**〔決定v2.1 #2〕〔要件 REQ-DL-885・680〕。出荷不可枠・出荷不可日の登録も画面01の保存も、**すべて運営（物流）が行う**。画面の「**倉庫タブ**」は**データの絞り込みでしかなく、権限の単位ではない**（タブを切り替えても見える人・できることは変わらない）〔サイクル §11-3〕。

### 4-1 サイクルの持ち方

| 項目 | 決まり | 出典 |
|---|---|---|
| 枠の数 | **28枠**。4週（A/B/C/D）× 7日（1〜7）で `A1`〜`D7` | 〔サイクル §0・§2.3〕〔要件 REQ-DL-101・501・632〕 |
| 枠の読み方 | **週 × 曜日**。`A6`＝週Aの土曜、`B5`＝週Bの金曜。**同じ曜日でも週ごとに稼働・休みを変えられる**（曜日だけの指定では、B週・D週の隔週の休みを表せない） | 〔サイクル §0・§2.3〕〔要件 REQ-DL-632〕 |
| 1サイクル | **4週＝28日**（休止がなければ） | 〔サイクル §4.2〕 |
| `A1` の曜日 | **必ず月曜。** 月曜以外を入力したら直前の月曜へ丸めて生成し、丸めた結果を画面に出す（旧：日曜開始〔要件 REQ-DL-203〕。2026/09/12 改定） | 〔要件 REQ-DL-614〕 |
| スロットが決めるもの | **納品日だけ。** ピッキング日は常に `納品日 − リードタイム` で逆算する。この向きは全モードで不変 | 〔サイクル §0〕 |
| 初回 `A1` の初期値 | **前回サイクルの続き**（直前サイクルの `D7` の翌日）。根拠を併記し手で変更できる。変更したらバッジを「前回のサイクルの続き」→「手入力」に切り替え、**続きとの差分日数**と予定の作られない期間ができないかを確認させる。「続きに戻す」で復帰。根拠の表示例：『前回のサイクル：10月サイクル（2026-09-28 A1 〜 2026-10-25 D7）。その翌日 2026-10-26 から続けます。』開始月を変えたときは、手入力していなければ初回 `A1` も追随する〔原典：納品サイクル設定 §2.1〕 | 〔サイクル §2.1〕 |
| サイクルの本数 | **1本。出荷用と納品用を別に持たない。** 出荷不可も同じ `A1`〜`D7` のグリッドで、**ピッキングする日そのものの枠**で判定する（「暦＋出荷不可曜日」案は読み方が二重になるため、「出荷専用サイクルをもう1本」案は初日・休止・ずれを2本とも管理することになるため、いずれも不採用） | 〔サイクル §2.3〕〔要件 REQ-DL-804〕 |

#### サイクル月＝14番目の枠 `B7` が属する月

**`cycle_month` ＝ 14番目の枠 `B7` が属する月**と定義する〔決定v2.1 #11〕〔要件 REQ-DL-881・839・864〕〔サイクル §4.2・§7〕。**例外の分岐は作らない。**

| 論点 | 決まり |
|---|---|
| 定義 | **`B7` の日付が属する年月**（`yyyy-mm`）。`delivery_cycles.b7_date` から導出する |
| 「日数が多い月」との関係 | **常に同じ結果になる。** 28日の前半14日と後半14日の境目が `B7` と `C1` のあいだにあるため、日数が多いほうの月には必ず `B7` が入る |
| 14対14 の同数 | **自動的に前の月**になる（`B7` が前の月の末日に来るため）。**同数のための場合分けは持たない** |
| 数える対象 | **枠の日付だけ。** サイクル休止日は枠を消費しないので数に入れない。休止で暦上の長さが伸びても `B7` の位置は枠の並びで決まるため、サイクル月は変わらない |
| 子契約ID | `契約ID-yyyymm` の `yyyymm` も同じ規則。**1サイクル＝1子契約**で、月をまたいでもサイクル月の子契約に載せる |
| 例 | `A1`＝2026-09-07 → 9/07〜10/11（休止 9/21〜27 を除く28日。9月17日・10月11日）／`B7`＝2026-09-20 → **2026年9月**（2026/10/01 暦を統一）。**同数**の例は `A1`＝2027-01-18 → 1/18〜2/14（14日・14日）／`B7`＝2027-01-31 → **2027年1月**（前の月） |
| 旧との関係 | 第1次 #41「日数が多い月。14対14 は未決・暫定で `B7` の月」を、第2次で「`B7` が属する月」に一本化して未決を解消した。**v2.0 の ⚠️要確認 #10 は削除する** |

### 4-2 生成対象期間

| 項目 | 決まり | 出典 |
|---|---|---|
| 長さ | **開始月を含む6ヶ月（基本6ヶ月）**。設定・法人への表示・変更申請の範囲をすべて同じ6ヶ月に揃える（旧：最大12ヶ月〔要件 REQ-DL-306〕。2026/09/12 改定・2026/09/21 確認） | 〔要件 REQ-DL-615〕 |
| 超過時 | 開始月＋5ヶ月へ丸め、通知を表示する | 〔サイクル §2.3〕 |
| 延長 | **終了月を進めるだけ。** 新しい設定を作るのではない（配送サイクル設定は常にひとつ） | 〔サイクル §2.0A〕〔要件 REQ-DL-717〕 |
| ローリング生成 | **しない。** 予定が作られるのは**保存したときだけ**で、対象は設定した期間の分に限る。**バッチが期間の末尾へ自動で足すことはなく**、バッチは日付を計算せず既にある予定を確定させるだけ（旧：月次バッチで末尾へ1ヶ月分を追加〔要件 REQ-DL-608〕。2026/09/19 廃止） | 〔要件 REQ-DL-809〕 |
| 「設定済み」の判定 | ①初回 `A1` ②配送サイクル ③必須となる休止・出荷不可設定 ④対象月の配送日算出結果 — がそろい、**配送日を正常に算出できる**こと。入力値があっても**算出エラーがあれば未設定と同じ扱い**とし、手動・自動公開とも不可。穴の月・生成対象期間より先の月も「未設定」 | 〔サイクル §2.0C-5〕 |

**開始月の初期値＝まだ設定していない最初の月**〔要件 REQ-DL-821〕〔サイクル §2.0C-1〕

| 状況 | 初期の開始月 | 例（確定済み〜2026-10 のとき） |
|---|---|---|
| **穴がある**（確定済みと設定済みのあいだが空いている） | **穴の最初の月** | 設定済み 2026-12〜2027-05 → 2026年11月〜2027年4月 |
| **穴がない** | **設定済みの最終月の翌月** | 設定済み 2026-11〜2027-04 → 2027年5月〜10月 |
| **まだ何も設定していない**（初期導入） | **下限の月（＝翌々月）** | 2026年8月時点 → 2026年10月〜2027年3月 |

**翌々月は初期値ではなく下限。** メニュー公開済みの月は編集不可で、メニュー公開＝オーダー開始が前月1日のため、**当月（配送運用中）と翌月（公開済み）が編集不可**になり、下限が翌々月になる。当月・翌月はドロップダウンにも月タブにも出さない〔要件 REQ-DL-709・803〕。開始月を変えて選択中の月が期間の外になった場合は開始月へ戻す。選択欄の近くに設定可能期間のヒント（例：`メニュー公開済みの月は変更できません。2026年10月以降を選択してください。`）を出す〔原典：納品サイクル設定 §2.0C-2〕。**設定状況の帯で月をクリックすると開始月がその月に移る**〔要件 REQ-DL-822〕。設定済みの月の中身を直すときの入口で、戻したことで確定済みとのあいだに穴ができる場合は穴の警告を出す。**対象期間に設定済みの月が含まれるときは保存前プレビューに明示する**〔要件 REQ-DL-823〕（`この期間には設定済みの月が3件含まれます（2027-02〜2027-04）。これらの納品予定は作り直されます。`）。

- **「受注または配送処理が開始されている月」＝オーダー期間が始まった月**（オーダー開始＝メニュー公開＝前月1日）。初回受注の有無・出荷指示の発行では判定しない〔hong 回答 2026-10-03〕〔要件 REQ-DL-708（09/14）〕。

#### 設定状況の帯〔サイクル §2.0B〕〔要件 REQ-DL-718〕

画面01の**最上部に全幅**で表示する。別画面には分けない。上段＝配送サイクル設定の状況（運用開始月〜生成対象期間の終了月＋6ヶ月を月単位のセルで色分け）、下段＝同じ月の並びでメニューの公開状況（運用中／公開済み＝編集不可／公開準備中／未公開）。**配送サイクルが未設定の月には `!` を付ける**。

| 月の状態 | 意味 |
|---|---|
| 確定済み（編集不可） | 配送運用中の当月・メニュー公開済みの月・受注／配送処理が開始されている月。**権限にかかわらず**編集不可（「受注／配送処理が開始されている」＝オーダー期間が始まった月〈月間メニューの `orderFrom`。メニューがまだなければ前月1日〉〔hong 回答 2026-10-03〕。すでに配送データを作った月も編集不可） |
| 設定済み（編集可） | 生成対象期間に入っていて、まだ運用に入っていない月 |
| 未設定（穴） | 確定済みと生成対象期間のあいだが空いている月。**予定も配送データも作られない** |
| 未設定（今後） | 生成対象期間より先の月。まだ設定していないだけ |
| 帯の下に出す内容 | 設定対象期間／初回 `A1`／確定済みの範囲とその理由／この設定の内容（サイクル休止◯件・納品祝日扱い◯日・倉庫別の出荷不可枠と日別の出荷不可日）。確定した月の設定は変更できないが、内容は**変更履歴**（いつ・誰が・どこを・何を・影響件数）に残り、過去の予定の根拠はこの履歴で追う〔サイクル §2.0A〕 |
| 穴の警告 | `設定のない月があります：2026-11　この月は納品予定も配送データも作られません。法人にも表示されず、変更申請もできません。`（開始月の初期値がこの月になるので、そのまま保存すれば埋まる） |

**期間切れの事前警告は、画面内の表示だけ。ダッシュボード通知は作らない**〔決定 #14〕〔要件 REQ-DL-844〕〔サイクル §2.0B〕

| 出すもの | 出さないもの |
|---|---|
| **①設定済みの最終月 ②残りヶ月数**（帯の下に常時表示）。**残り2ヶ月を切ったら警告色**。文言：`設定済みの最終月は 2027年1月（残り 5ヶ月）。確定済み（編集不可）は 2026年10月まで、変更できるのは 2026年11月以降です。` | ダッシュボード通知／メール・プッシュ／**日数を数えて催促する仕組み**。設定漏れは**メニュー公開の入口で必ず止まる**ため（4-3）催促は要らない。帯の常時表示は「催促」ではなく「状態の表示」として残す |

### 4-3 メニュー公開との接続と仮の締切

**節目はメニュー側が正。サイクル生成時に実日付を写し取って保持する**〔決定 #33〕〔要件 REQ-DL-840〕〔サイクル §4A-2〕

| 節目 | 出どころ | デモの既定値 | 2026年9月サイクル（`A1`＝2026-09-07）の例 |
|---|---|---|---|
| **メニュー公開＝オーダー開始** | メニュー側（オーダー期間 開始） | 前月1日 | 2026-08-01 |
| （メニュー登録） | メニュー側 | 公開日まで | 〜2026-08-01 |
| **オーダー締切**（数量確定＋日付変更の受付終了） | メニュー側（オーダー期間 終了） | 前月15日 | 2026-08-15 |

**毎回メニューを引きに行くのではない。** サイクルを生成した時点のメニューの設定日を**サイクルに保持**し（`delivery_cycles.menu_open_date` ／ `order_start_date` ／ `order_close_date`）、保持した値を画面・バッチ判定・法人カレンダーで使う。写し取り元が分かるよう `marker_source`（`menu` ／ `provisional`）と `marker_copied_at` を併せて持つ〔サイクル §7〕。サイクル（4週）とメニュー（暦月）は周期が違うため、**サイクル月のメニュー**をそのサイクルの節目として使う（サイクル月の決め方は 4-1）。**実装では定数の日付を使わず、保持した実日付で判定する。** なお**変更締切は持たない**（旧：`A1` の6日前。2026/09/15 に廃止しオーダー締切へ統合）。メニュー公開とオーダー開始は**同じ日**で、「公開〜オーダー開始前」という段階も持たない。

#### 仮の締切（`marker_source = provisional`）でできること・できないこと

メニューが未登録の月はオーダー締切日が取れないため、**前月15日を仮の締切**として保持して判定を続ける〔決定 #33〕〔要件 REQ-DL-811〕。**ただし仮の締切で走らせてよい処理は限定する**〔決定v2.1 #9〕〔要件 REQ-DL-879〕〔サイクル §4A-2E〕。

| 処理 | 仮の締切（`provisional`） | 本当の締切（`menu`） |
|---|---|---|
| **変更受付の締め切り**（日付変更モードを OFF にする） | **走らせる** | 走らせる |
| **検査の起動**（`plan_recheck` などの突き合わせ・要確認の生成） | **走らせる** | 走らせる |
| **数量確定**（`order_finalize`・標準数量／AIモードでの確定） | **走らせない** | 走らせる |
| **確定メールの送信**（法人・委託配送会社への確定通知） | **走らせない** | 走らせる |
| **出荷指示**（トーマスへの送信。したがって `plan lifecycle`＝`locked` にもしない） | **走らせない** | 走らせる |

- **メニューから本当の締切が来るまで、数量確定・確定メール送信・出荷指示は走らせない。** 仮の締切は**内部判定の既定値**であって、法人や倉庫に約束した日付ではない。仮の日付で数量を締めて出荷指示まで流すと、あとからメニューが登録されて締切が動いたときに取り返せない〔要件 REQ-DL-810・812〕。画面では締切日に **「仮（前月15日）」** と添えて表示し、メニューが登録された時点で実日付へ差し替える。差し替えて `marker_source = menu` になってから、`order_finalize` 以降が初めて対象として拾う。**（旧：第1次 #33 には「仮の締切でやってよい範囲」の制限が無かった。第2次で上表のとおり限定した）**

#### 公開の前に設定を検証する〔サイクル §2.0C-3・§2.0C-4〕〔要件 REQ-DL-711・712〕

| 場面 | 挙動 |
|---|---|
| 手動公開 | エラーダイアログ「メニューを公開できません／2026年9月の配送サイクルが設定されていません。配送サイクルを設定してから、もう一度公開してください。」＋「配送サイクルを設定する」「キャンセル」。前者で**対象月を指定した状態で画面01へ遷移** |
| 自動公開 | 公開を中止し対象メニューを**未公開のまま**にする。管理画面に理由を表示（`2026年9月のメニューは、配送サイクルが未設定のため自動公開されませんでした。`）。**他の月の公開は止めない**。管理者への通知機能がある場合は、同じ内容を通知する〔原典：納品サイクル設定 §2.0C-3〕〔要件 REQ-DL-713（09/14）〕 |
| 事前警告 | 公開準備画面・メニュー一覧でも未設定を表示し（`公開準備エラー：2026年9月の配送サイクルが未設定です`）、**公開ボタンを非活性**にする。非活性理由と画面01への導線を出す |

### 4-4 稼働日・納品不可曜日

`納品祝日扱い日 ＝ システム登録済み祝日（既定ON）＋ 手動休日でONにした日 － 日別OverrideでOFFにした日`

| 決まり | 内容 | 出典 |
|---|---|---|
| 曜日の自動判定 | **行わない**（倉庫はほぼ休業しないため）。土日の可否は契約側の**納品不可曜日**で制御する | 〔サイクル §2.3〕 |
| 効き方 | 全社一律の納品不可ではない。**契約の「祝日納品不可」が ON の会社だけ**納品日を振り替える。OFF の会社には通常どおり納品する | 〔サイクル §2.3〕 |
| 手動休日 | 休日名＋日付に加え「納品の祝日」「出荷不可」を個別に選択して追加。**少なくとも片方を必須**とする | 〔サイクル §2.3〕 |
| 全社共通の範囲 | **サイクル休止期間と納品祝日扱い日は全社共通**。配送サイクル（28枠）自体が全社共通のため、倉庫ごとの休みは出荷不可枠・出荷不可日で表す | 〔サイクル §2.3〕 |
| 祝日データ | **公開されている祝日の API から取得して祝日マスタへ登録**（年1回の自動取得＋画面の「祝日を再取得」）。運営が追加・修正・削除できる（2026/10/01 変更・運営確認 D3-3。旧：【暫定】内閣府の公開データを年1回・手動で登録、外部API取込は作らない）。画面には対象期間の祝日件数と一覧、最終取得日時と「祝日を再取得」ボタンを出す | 〔決定 #9〕〔hong 回答 2026-10-03〕〔サイクル §6〕〔要件 REQ-DL-307〕 |

受取側は**契約（拠点）単位**で持つ〔サイクル §3.1・§3.1C〕。項目名は **「納品不可曜日」「前倒す・後ろ倒す」** に統一する（「受取不可曜日」「振替方向」は使わない。物理名 `ng_weekdays` ／ `holiday_shift` は変更しない）〔決定 #31〕〔要件 REQ-DL-849〕。

| 項目 | 内容 |
|---|---|
| **納品不可曜日** | 既定：土＝ON・日＝ON・祝＝ON。**納品日のみを制御**し、ピッキング日は制御しない。法人一律ではない |
| **拠点の受取不可日** | 受け取れない日付（休業・棚卸し・工事・年末年始）。`date` ／ `range` ／ `dow` の3種別と `none` ／ `yearly` の繰り返しを持つ。**納品日の生成条件として効くため、サイクル設定を作り直しても自動で避けられる** |

| 受取時間帯・納品条件 | 日付の計算には**使わない。** 受取時間帯は子テーブル `site_receive_windows(site_id, from_time, to_time, sort_order)` で**複数持ち**、配送データ作成時に `delivery_receive_windows` へ**リストごとスナップショット**してドライバーアプリに出す。**from/to を1組だけ持つ形にしない**〔決定v2.1 #8〕〔要件 REQ-DL-877・878〕 |

| **1. 休止中は納品もピッキングもしない（最優先）** | 休止期間中の日付には**納品スロットを割り当てない**。**他のどの設定よりも優先する**ため、納品祝日扱い日・出荷不可が重なっても休止が勝ち、休止日は**祝日・出荷不可の判定そのものを行わない** | 〔サイクル §2.2・§4.2〕〔要件 REQ-DL-307〕 |
| **2. 休止日は枠を消費しない** | 止まった枠は**休止が明けた翌日から順に再開する**（続きの枠へ進めるのではない）。**サイクル全体が休止日数ぶん後ろへずれ、納品回数は減らない**。そのサイクルの納品回数・プラン数量・請求は変わらない | 〔サイクル §2.2・§4.2〕〔要件 REQ-DL-807〕 |
| **3. 登録した日だけ止める** | 週単位には丸めない。止まった枠はその翌日から順に戻る。ただしこのままでは枠と曜日の対応がずれるため、ルール4の調整を必ず併せて行う（**7の倍数に満たないと保存できない**） | 〔サイクル §2.2〕〔決定v2.2 #2〕 |
| **7. 登録時に影響件数をまとめて確認する** | 保存前のプレビューに**丸めた後の休止期間（調整日数）**と後ろへずれる予定の件数を出し、**個別の「要確認」に落とすのは例外だけ**とする。1件ずつ確認させない | 〔要件 REQ-DL-808〕 |

**ルール4：1回の休止は7日の倍数にする。不足分の「（調整）」休止は、システムが日数を算出して表示するだけで、置き場所は管理者が決める**〔決定v2.2 #2〕〔サイクル §2.2「ずれの調整」〕〔要件 REQ-DL-819・820・887〕

> **不足日数 ＝ `7 −（休止日数 mod 7）`**　例：3日休止 → **4日**足りない
> **システムは算出して表示するだけで、自動では挿入しない。** **置き場所は管理者が決める** — 休止の直後／その週の中に散らす／月末にまとめる、などケースバイケースでよく、**あとから編集できる**。
> **7の倍数に満たない状態では保存できない。** 保存時に不足日数を返す。
> 調整用の休止は `adjust_for_pause_id` で**どの休止の埋め合わせか**を持つ。
> **（旧：`7 −（休止日数 mod 7）` 日の調整を休止の直後に自動で挿入する。2026/09/22 第3次決定で取消）**

| 例（初回 `A1`＝2026-08-03 月／`B1`＝8/10・`B2`＝8/11 まで実施） | `B3` の日 | 次の `A1` |
|---|---|---|
| 休止なし | 8/12（水） | 8/31（月）＝ 8/3 + 28日 |
| 8/12〜8/14 を休止（3日）だけ | 8/15（土）… **曜日がずれる** | 9/3（木）… **月曜でなくなる** |
| 直後に 8/15〜8/18 を**調整用に休止**（4日） | **8/19（水）** ← 曜日どおり | **9/7（月）** ← 月曜のまま |

週まるごと休止した場合は、明けた週が同じ週コードで再開する（例：週A 8/3〜8/9 → 休止 8/10〜8/16 → 週B 8/17〜、B1 は月曜）〔原典：納品サイクル設定 §2.2〕。

**丸め後の進み方**：8/12〜8/14 休止 → 8/15〜8/18 調整 → `B3`＝8/19（水）→ `B4`＝8/20（木）→ `B5`〜`B7`＝8/21・8/22・8/23 → 次の `C1`＝8/24（月）。**カレンダー週（月曜始まり）に丸めるのではなく、休止の初日から数えて7日にする**（すでに実施済みの `B1`＝8/10、`B2`＝8/11 を巻き込まないため）。**不足日数はシステムが算出して表示するだけ**で（`8/12〜8/14（3日）は7日単位ではありません。あと4日ぶんの「調整」を置いてください`）、**どこに置くかは管理者が決める**〔決定v2.2 #2〕。調整用の休止は区分「調整」で保持し、`adjust_for_pause_id` でどの休止の埋め合わせかを持ち、カレンダー・変更履歴で区別して表示する。上の例は**休止の直後に置いた場合**の進み方であって、唯一の置き方ではない。

**置き場所による違い（管理者の判断材料）**：休止の直後に置くと、8/15 以降の枠が最短で元の曜日へ戻る。月末にまとめると、止まる日数（合計7日）も次の `A1`（9/7 月）も同じだが、8/15〜8/27 が**3日ずれたまま**になり（`B4` が日曜、`A6`・`A7` が水・木に当たる）、その期間は出荷不可枠の判定・納品不可曜日の判定・法人カレンダーの表示・変更申請の候補日・件数しきい値のすべてが曜日どおりでなくなる。**既定の提案は「休止の直後」**とし、倉庫が実際には稼働している日を調整で止めたくない場合などに管理者が動かす。

**ルール5：休止と祝日扱いの使い分けは「何日ずらせば納品できるか」で決める**（週まるごとか一部かでは決めない）〔サイクル §2.2〕

| 状況 | 登録の仕方 | サイクルの進み方 | 納品日 |
|---|---|---|---|
| **1〜2日**ずらせば納品できる短い休み（単発の祝日など） | **納品祝日扱い日**（＋必要なら倉庫の**出荷不可日**） | 進める（枠を消費する） | 契約の「前倒す・後ろ倒す」へ振り替える |
| **3日以上**ずらさないと納品できない長い休み（GW・シルバーウィーク・年末年始・夏季休業） | **サイクル休止** | **止まる**（枠を消費しない） | 休止明けの翌日から止まった枠を再開する |
| （注） | この「1〜2日／3日以上」は**どちらで登録するかの運用上の目安**であり、**振替を打ち切るしきい値ではない**。振替日数にシステム上の上限は置かない〔要件 REQ-DL-806〕 | — | — |

**ルール6：休止明けに再開した枠は後倒しのみ**〔サイクル §4.4〕〔要件 REQ-DL-825〕

休止で枠がずれた回は、そのあとの祝日・納品不可曜日・拠点の受取不可日の振替を**後倒しだけで探す**。**契約が「前倒す」設定でも、この回に限っては前倒ししない。** その枠は休止で**止まっていた**枠であり、休止より前の日に納品するのは「止めた枠を止める前に届ける」ことになるため（例：9/19〜9/25 の休止明けに再開した `C6`（土）が納品不可曜日だと、前倒しでは休止をまたいで 9/18（金）まで戻ってしまう）。休止にかからない通常の回は**契約の「前倒す・後ろ倒す」**に従い、個別指定（毎月N日／末日）が休止日そのものに当たった場合も**契約の設定**で動かす（指定日は枠ではないため、休止より前に戻ってよい）。そもそも**休止日には `seed`（スロットの日）が立たない**ため「休止による振替」は起きず、振替が起きるのはスロットの日が納品祝日扱い日・納品不可曜日・拠点の受取不可日に当たったときである。

| 2 | **拠点の受取不可日**（日付・期間・年次繰り返し） | 契約（拠点）単位 | **納品日**を契約の「前倒す・後ろ倒す」へ振替。サイクルを作り直しても自動で避ける | 〔サイクル §3.1C・§4.3〕 |
| 3 | **出荷不可枠**（`A1`〜`D7`） | 倉庫別 | **まずピッキング日を前倒し。差0で収まらなければ納品日も振り替える**（4-6・4-8） | 〔決定 #15〕〔要件 REQ-DL-842〕 |
| 3 | **日別の出荷不可日** | 倉庫別 | 同上。**ピッキング日・納品日の両方が振替の対象** | 〔決定 #15〕〔サイクル §4A-5B〕 |
| — | **個別稼働Override** | 倉庫別 | 出荷不可枠・出荷不可日を打ち消してその日を稼働にする（`isPickClosed` の先頭で `false`） | 〔サイクル §4.3〕 |
| — | **祝日扱いOverride** | 全社共通 | 公開祝日を納品祝日扱いにしない（`override` が既定判定より優先） | 〔サイクル §2.3・§4.3〕 |

**順1と順2・3の関係は「優先」ではなく「排他」。** 休止日はスロットを持たないので、そもそも祝日・出荷不可の判定に入らない。**順2どうしに優劣はない**（いずれか1つでも当たれば `isCompanyClosed` が真になり、同じ振替処理へ入る）。**順2は納品日だけ、順3はピッキング日を起点に両方**を動かす。両方が同時に成立する場合は 4-8 のループで納品日候補を1日ずつ送りながら、両方の条件を満たす組を探す。**振替・不可・要確認には必ず理由を添える。** 形式は「納品祝日扱い：〈祝日名〉」「納品不可曜日：〈曜日〉曜」「出荷不可枠 〈スロット〉（〈倉庫〉）」「出荷不可日：〈理由〉」「サイクル休止：〈期間名〉」「保管量 要確認」。表示の長さは**一覧＝短く**（`前倒し 2日`）、**詳細・ツールチップ＝フルに**（`本来 B3（2026-09-17）から 2日 動いています`）〔決定 #27〕〔要件 REQ-DL-846〕。

### 4-8 日付ヘルパーとサイクル生成アルゴリズム

すべての日付演算は **UTC固定**（`Date.UTC`）で行い、タイムゾーンによるずれを排除する。`mk(y,m,d)`＝日付生成／`fmt(dt)`＝`"YYYY-MM-DD"`／`addDays(dt,n)`／`diffDays(a,b)`（いずれも 86400000ms 単位）〔サイクル §4.1〕。

```
buildSchedule():                                    # サイクル §4.2
  d = 初回A1（必ず月曜）; end = 生成対象期間の末日; i = 0; cycleNo = 0
  while d <= end:
      if 休止中(d):                                  # ← 枠(i)を進めない＝消費しない
          SCHED[fmt(d)] = { pause:期間名, wouldBe:slotCode(i), adjust:調整用か }
          d = addDays(d,1);  continue
      si = i % 28;  wi = floor(si / 7)               # 0=A, 1=B, 2=C, 3=D
      if si == 0:   cycleNo++;  a1[cycleNo] = d
      if si == 13:  b7[cycleNo] = d;  cycleMonth[cycleNo] = ym(d)   # ★14番目の枠＝B7
      SCHED[fmt(d)] = { code:"ABCD"[wi]+(si%7+1), week:"ABCD"[wi],
                        cycleNo:cycleNo, first:(si==0) }
      i++;  d = addDays(d,1)
  # cycle_month は b7_date から導出して delivery_cycles に保持する（§7）。
  # 「日数が多い月」を数える実装も、14対14 の場合分けも持たない。
```

- **サイクル月は `B7` から導出する**〔決定v2.1 #11〕〔要件 REQ-DL-881〕。`si == 13` の日が `B7` であり、その年月が `cycle_month` になる。`delivery_cycles.b7_date` に日付を残し、画面・子契約採番（`契約ID-yyyymm`）はこの値を使う。**28日を数えて多いほうを採る実装にはしない**（同じ結果になるうえ、同数の分岐が要らなくなるため）。
- 休止は7日の倍数でなければ保存できないため（4-5 ルール4）、**ずれも7日単位になり、`A1`＝月曜・`A6`＝土曜という週×曜日の対応は保たれる**。**納品祝日扱い日・出荷不可日でもスロットは割り当てる**（振替は契約・倉庫ルール側で行うため）。**スロットを割り当てないのはサイクル休止日だけ**で、そのセルには `wouldBe`（**休止明けに再開する枠**）を表示する。休止中は枠が進まないため休止期間のどの日も同じ枠を指し、文言は **「再開は `B3`」** とする（**「本来 `B3`」とは書かない**。その日に `B3` を実施する予定だった、と読めるため）〔サイクル §4.2〕。

```
isDeliveryHoliday(dt) = override に fmt(dt) があればその値、無ければ 祝日マスタに存在する
isPickClosed(dt):                                   # 出荷のみ不可（倉庫別）
    if 個別稼働Override に fmt(dt) がある:  return false
    if 日別の出荷不可日 に fmt(dt) がある:  return true
    return 出荷不可枠[ サイクル日[fmt(dt)].slot_code ]
isCompanyClosed(dt, contract):                      # 契約ごとの納品判定
    if contract.祝日納品不可 and isDeliveryHoliday(dt):  return true
    if isSiteBlocked(dt, contract):                      return true   # 拠点の受取不可日
    return contract.納品不可曜日[ dt.getUTCDay() ]                      # 0=日, 6=土
# 納品不可枠の自動判定（4-6）＝「直前スロットが出荷不可で自身は可の枠（A1 の直前は D7）」
#   ＋「リードタイム分を遡ったピッキング枠が不可になる納品枠」。出荷不可枠・契約リードタイム
#   の変更時に再計算し、画面01の影響表示と契約のスロット選択制御へ即時反映する〔サイクル §4.3〕。
isSiteBlocked(dt, contract):                        # 拠点の受取不可日〔原典：納品サイクル設定 §4.3〕
    状態が有効かつ適用開始（effective_from）以降の受取制約だけを見る
    yearly は月日（MM-DD）で、range は開始日〜終了日で、それ以外は日付で一致を判定する

badDeli(dt) = isCompanyClosed(dt,contract) or isPause(dt)             # サイクル §4.4
badPick(dt) = isPickClosed(dt)             or isPause(dt)
LT_SLACK = 0（原則：実−契約＝0） ／ LT_SLACK_MAX = 1（やむを得ないときの上限）
seed  = (mode=="cycle") ? スロットの日 : 指定日
shift = 契約の「前倒す(−1)／後ろ倒す(+1)」 ※休止で枠がずれた回は +1 固定（4-5 ルール6）
for i in 0..20:                                   # nudge の上限と同じ20日
    d = addDays(seed, i * shift)
    if not canDeliver(d):  continue               # 休止・祝日扱い・納品不可曜日・受取不可日
    pk = nudge(addDays(d, -leadTime), -1, badPick)        # ピッキング日は常に前倒しで探す
    g  = diffDays(d, pk) - leadTime
    if not best or g < best.gap:  best = { deli:d, pick:pk, gap:g }
    if g <= LT_SLACK:                  return { ...best, ng:false }                  # ①
    if g <= LT_SLACK_MAX and not ok1:  ok1 = { deli:d, pick:pk, gap:g, slack:true }  # ②
return ok1 ? ok1 : { ...best, ng:true }   # ②＋1日／③要確認。ピッキング不可日は残さない
```

| 段階 | 条件 | 採り方 | 表示 |
|---|---|---|---|
| ① 原則 | 実リードタイム − 契約リードタイム ＝ **0** | 契約の「前倒す・後ろ倒す」へ順に探し、**最初に見つかった日**を採る | 印なし |
| ② やむを得ず | ①の日がひとつも無い | 差 **＋1日**で収まる最初の日を採る（**自動確定してよい**） | 黄「やむを得ず＋1日（許容内）」 |
| ③ 要確認 | ②も無い | 差が**いちばん小さい**組を採る | 赤「実 N日（契約 M日・＋K日）」＋**要確認** |

- **20日以内に納品できる日が1つも見つからないときは「予定生成不可」として要確認に出す。自動で日付を決めない。** 対象の契約・拠点・サイクル・理由を添えて運営スケジュールの「要確認」に載せ、運営が配送回数やスロットを調整する〔決定 #19〕〔要件 REQ-DL-843・824〕〔サイクル §4.4〕。
- `nudge(dt, dir, bad)` は `bad(dt)` が偽になるまで `dir` 方向へ1日ずつ移動し、移動日数とともに返す（**上限20日**）。**本来の枠の日から3日を超えて動いた場合は要確認**にする。移動日数そのものに上限は置かない〔要件 REQ-DL-806〕。**前倒しできない場合のフォールバック**：契約が前倒し設定でも在庫・保管量の理由で前倒しが成立しない場合は**自動的に後倒しへ切り替え**、「方向反転」として警告・通知する〔要件 REQ-DL-202〕。**温度帯**：冷凍と冷蔵は別レコードとして生成するため、同じ納品日でもピッキング日・倉庫が異なりうる〔要件 REQ-DL-301〕。

### 6-0. どのリードタイムを使うか

計算に使うリードタイムの優先順位〔決定v2.3 #12〕：

1. **`deliveries.lead_time`** — その配送データ**1件だけ**のリードタイム。運営が「日付を個別に指定」（15-6）で入れたときだけ入る。**予定（`shipping_plans`）には存在しない**
2. **`contract_month_delivery_channels.lead_time`** — 子契約があればその月の値
3. **`contract_delivery_channels.lead_time`** — 親契約の既定値

倉庫マスタはリードタイムを**持たず、自動補完もしない**〔決定 #10〕。`deliveries.lead_time` が契約の値と違うときは画面に**調整済**と出し、以後スケジュール画面で日付を動かしても**この個別リードタイムを保つ**〔要件 REQ-DL-750〕。

### 6-1. 出荷予定の生成手順（疑似コード）

すべての日付演算は **UTC固定**（`Date.UTC`）で行う〔サイクル §4.1〕。生成の単位は**配送明細 × 配送区分**で1件〔サイクル §3.1B〕。

```js
function badDeli(dt){ return isCompanyClosed(dt, contract) || isPause(dt); }  // 納品できない日
function badPick(dt){ return isPickClosed(dt)    || isPause(dt); }            // 出荷（ピッキング）できない日

// ① 納品日の決定（基準）
var seed = (mode === "cycle") ? Slotの日 : 指定日;       // on_demand は資材オーダー時に確定
var shift = contract.holiday_shift;                      // -1＝前倒す ／ +1＝後ろ倒す
                                                         // ただし休止明けに再開した枠は +1 固定（§6-3）

// ② 候補を順に探す（上限20日）
var best = null, ok1 = null;
for (var i = 0; i <= 20; i++) {
  var d = addDays(seed, i * shift);
  if (badDeli(d)) continue;                              // 休止・祝日扱い・納品不可曜日・受取不可はスキップ

  var pk = nudge(addDays(d, -leadTime), -1, badPick);    // ③ ピッキング日の逆算。不可なら常に前倒す
  var g  = diffDays(d, pk) - leadTime;                   // ④ 実リードタイム − 契約リードタイム

  if (!best || g < best.gap) best = { deli:d, pick:pk, gap:g };
  if (g <= LT_SLACK)                  return { ...best, ng:false };            // 段階① 差0
  if (g <= LT_SLACK_MAX && !ok1) ok1 = { deli:d, pick:pk, gap:g, slack:true }; // 段階② ＋1日
}
return ok1 ? ok1 : (best ? { ...best, ng:true } : 予定生成不可);               // 段階③／§6-4
```

- `LT_SLACK = 0`（原則）／`LT_SLACK_MAX = 1`（やむを得ないときの上限）〔要件 REQ-DL-824〕。`nudge(dt, dir, bad)` は `bad(dt)` が偽になるまで `dir` 方向へ1日ずつ移動し、**移動日数とともに返す**（上限20日）。
- **出荷（ピッキング）できない日付は絶対に残さない**〔サイクル §4.4〕。**出荷不可**の判定は**ピッキングする日そのものの枠（A1〜D7）**で行い、出荷専用のサイクルは別に持たない〔要件 REQ-DL-804〕。
- サイクル休止日には**そもそもスロットが割り当たらない**（枠も消費しない）ため、`seed` が休止日になることはない〔要件 REQ-DL-807〕。
- **生成・再生成のキーは `contract_id` + `line_no` + `channel_id` + `cycle_id` + `occurrence_key`**（`occurrence_key` はスロット `A1`〜`D7` または「毎月N日／末日」）。**`(contract_id, delivery_date)` は使わない**（1契約が同じ日に複数の温度帯・配送区分を持ちうるため）。再生成は追加ではなく**置換**〔決定v2.1 #6〕〔要件 REQ-DL-873〕。ルートのスナップショット元は §5-2 のとおり**子契約優先・親はフォールバック**（`route_snapshot_source`）〔決定v2.1 S2〕。

### 6-2. 振替とリードタイムの2段階

> **①まず差0で探す。②どうしても無理なときだけ＋1日まで許容する。③それも無理なら要確認。**〔要件 REQ-DL-824〕

| 段階 | 条件 | 採り方 | 表示 | 自動確定 |
|---|---|---|---|---|
| **① 原則** | `実リードタイム − 契約リードタイム = 0` | 契約の**前倒す・後ろ倒す**の向きへ順に探し、**最初に見つかった日**を採る | 印なし | ○ |
| **② やむを得ず** | ①の日がひとつも無い | 差 **＋1日** で収まる最初の日を採る | 黄「やむを得ず＋1日（許容内）」 | ○（印は残す） |
| **③ 要確認** | ②も無い | 差が**いちばん小さい**組を採る | 赤「実 N日（契約 M日・＋K日）」＋**要確認** | ×（運営が確認） |

- **出荷不可**日を避けてピッキング日だけを前倒すと**実リードタイムが伸びる**。倉庫の連続した出荷不可枠（例：B週の木〜日）の直後に納品があると4〜6日前に作ったものを届けることになり、**短消費期限の商品では成立しない**。そこで**リードタイム差を優先**し、収まらないときは納品日のほうを動かす〔サイクル §4.4〕。
- ②は自動で確定してよい範囲だが、**あとから「なぜ1日伸びたか」が分かるように印を残す**。＋1日は祝日・定休日が1日だけ挟まる例外を流すための幅で、**最初から当てにする幅ではない**。③は自動では確定させず、**差の日数を必ず表示**し（例 `実 5日（契約 2日・＋3日）`）、運営が見て問題なければその日付のまま確定できる。

### 6-3. 振替の制約

| 制約 | 内容 | 出典 |
|---|---|---|
| **移動日数の上限** | **業務上の上限は置かない。** 探索の上限だけ 20日（`nudge`） | 〔要件 REQ-DL-806〕 |
| **リードタイム厳守** | 自動振替でも妥協してリードタイムを縮めない。**成立する日が見つかるまで振替を続ける**。20日先まで探して差0が無いときだけ＋1日を許容する | 〔要件 REQ-DL-824〕 |
| **出荷不可日はピッキング日・納品日の両方を振り替える** | ①まずピッキング日だけを前倒して差0で収まるか見る → ②収まらなければ**納品日のほうを契約の向きへ動かし、両方を振り替える**。「止まるのはピッキングだけ」という整理は取消 | 〔第1次 #15〕〔要件 REQ-DL-842〕 |
| **休止明けの枠は後ろ倒しのみ** | 休止で枠がずれた回は、そのあとの祝日・受取不可の振替を**後ろ倒しだけで探す**。契約が「前倒す」でもこの回に限り前倒さない（**止めた枠を止める前に届ける**ことになるため）。個別指定日が休止に当たった場合は従来どおり契約の設定に従う | 〔要件 REQ-DL-825〕 |
| **個別指定は契約の設定に従う** | 毎月N日／末日が納品不可曜日・受取不可日・納品祝日扱い日に当たった場合も、**契約の「前倒す・後ろ倒す」**で振り替える。個別指定専用の方向は持たない | 〔サイクル §3.2〕 |
| **方向反転のフォールバック** | 前倒す設定でも在庫・保管量の理由で前倒しが成立しない場合は**自動的に後ろ倒しへ切り替え**、「方向反転」として運営へ通知する | 〔要件 REQ-DL-202〕 |
| **サイクル境目の向き**（2026/10/01 追加・P10-5） | **A1・C1 で前倒しになる場合は後ろ倒し、D7 で後ろ倒しになる場合は前倒し**に自動で反転する（前半後半・サイクルの境をまたがない）。方向反転として運営へ通知 | 〔要件定義まとめ RD-DL-024〕 |
| **3日超の移動** | 本来の枠の日から**3日を超えて動いた場合は要確認**（連休・年末年始で数日先まで戻ることがあるため） | 〔要件 REQ-DL-806〕 |

**出荷不可日をあとから追加・変更したときの扱い**〔サイクル §4A-5B〕

| `plan lifecycle` | 扱い |
|---|---|
| `draft`（オーバーライドなし） | **自動で振り替える**。法人カレンダーの表示も自動で更新される |
| `draft`（オーバーライドあり・調整済） | まずピッキング日だけを前倒す。差0で収まらず納品日も動かす必要がある場合は自動では動かさず**提案中**へ |
| `published` | **動かさない。**「要確認」に出し、運営が一括変更で対応する |
| `locked` | **対象外。** 電話連絡＋取消、または複製で処理する |

- 保存前に**影響件数をプレビュー**する（作り直す予定／自動で前倒し／法人と合意済み〈適用・失効・提案中の内訳〉／出荷指示済み・変更不可／前倒しできない）。**失効・提案中が1件以上あるときは「確認して保存」＋チェック必須**（保存自体はブロックしない）〔要件 REQ-DL-775〕。**不可日を解除しても、一度前倒した予定は自動で戻さない**（`draft` は再生成で結果的に戻るが、`published` は戻さない）。

### 6-4. 20日で候補なし ＝ 予定生成不可

> **20日以内に納品できる日が1つも見つからないときは「予定生成不可」として要確認に出す。自動で日付を決めない。**〔第1次 #19〕〔要件 REQ-DL-843〕

| 項目 | 内容 |
|---|---|
| 出し先 | 運営スケジュールの**「要確認」** |
| 添える情報 | 対象の契約・拠点・配送サイクル・配送区分・**理由**（納品祝日扱い／**納品不可曜日**／受取不可日／出荷不可枠〈スロット・倉庫〉／出荷不可日／サイクル休止） |
| 運営の対応 | 配送回数・納品スロットの調整、または受取不可日の見直し |
| 同じ扱い | 出荷不可日の追加で前倒せない件（前日も不可、リードタイムが伸びすぎる等）〔サイクル §4A-5B〕 |

- 1〜2日ずらせば納品できる短い休みは**納品祝日扱い日**、3日以上ずらさないと納品できない長い連休は**サイクル休止**として登録する。システムが振替を打ち切るのではなく、**登録の仕方で分ける**〔サイクル §2.2・§4.4〕。

|---|---|
