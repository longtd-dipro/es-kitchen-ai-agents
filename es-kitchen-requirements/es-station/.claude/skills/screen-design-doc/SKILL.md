# 画面設計書を作る（デモ → 確認 → データ → Excel JA／VI・HTML）

狙いは3つ。
1. **未確認のまま資料にしない**：作る前に、食い違い・未決をまとめて確認する
2. **お客様（日本語）にも開発（ベトナム語）にも渡せる**：Excel は日本語版とベトナム語版を別ファイル、入力項目には「データ例」
3. **ページを増やさない・文言を揃える**：1機能＝1シート、共通の動きは共通パターンに1回、メッセージは共通の1か所

## セッションの決まり（長くしない。使用量の大半は 150k 超のセッションが使う）
- **1セッション＝1つの話題**（1機能、または1つの作業。例：「集金管理の spec」「データ cleanup」）。話題が変わったら新しいセッションを開く。コンパクト化より、新規のほうが軽い
- **文脈の目安は 150k まで**。近づいたら、区切りのいいところで止める。大きな点検（全機能の `--check`・luồng の追い）は読み取りをサブエージェントに任せ、本体には結論だけを入れる
- **終わる前に、状態をファイルに書いて commit・push**：やったこと・残り・次の一手を `docs/05_画面設計書/点検_整合性とやること_<日付>.md`（なければ作る）か、その機能の `確認メモ` に。次のセッションは**そのファイルと `kd_ask.py digest <画面コード>` から始める**（前の会話を当てにしない）
- 新しいセッションの最初の依頼は、「◯◯ファイルを読んで、△△をする」の1文にする

## 質問する前の決まり（最優先。同じことを何度も聞かない）
スレッド（セッション）は前の会話を覚えていない。**覚えているのは台帳・受付簿・各画面の `DECISIONS` だけ。** 聞く前に、必ず次の順で。
1. **始めたら最初に** `python3 scripts/kd_ask.py digest <画面コード>`（その画面で決まっていること）と `who <画面コード>`（重なる他のブランチ）
2. **聞きたいことを下書きにして**、`python3 scripts/kd_ask.py gate "語 語 | 質問" …`。✔答えあり → 聞かず適用／◇共通 → 聞かず受付簿へ（`references/common_answers.md`）／? だけ確認表に入れる（→ `confirm_flow.md` §1-0）
3. **共通の話題（一覧・日付・金額・文字数・権限・削除・メッセージ、そして画面の共通部品＝ヘッダー・ボタン・タブ・モーダル・0件/エラー表示など）は、機能のスレッドで聞かない。** 答えの場所は `references/common_answers.md` と `データ/_共通パターン.py`（画面の共通部品は、まずここを読んで同じ動きにそろえる。書き足すのも共通パターン側に1回だけ）
4. **答えをもらったら、すぐ台帳か受付簿へ書いて push**。`DECISIONS` に書くだけでは足りない（共通の話題は台帳 M-1／K にも）
5. 聞き直すのは、台帳と食い違う**新しい事情**があるときだけ。「前は〜と答えました」と言うときは、前の答えを引用する（できなければ言わない）

## トークンと時間を使いすぎないための決まり（先に読む）
- **データは日本語だけで書く**（`vi` は `""`、`ex` の説明も空）。ベトナム語・データ例は**最後に1回、サブエージェント（Sonnet。Haiku は不可）にまとめて頼む**（→ 手順3）
- **骨組みは script で出す**：`scripts/kd_scaffold.py`。LLM が項目を1つずつ書かない
- **確認は表にして一括**で聞く（→ `references/confirm_flow.md`）
- **繰り返しは `--check`（ブラウザ不要）**。見てもらうときは `--only html`、Excel は release のときだけ。撮影は変わった状態だけ撮り直す
- **PNG を Read しない**（画像は重い）。見つからない番号と画面との差は `make.py` の出力だけで足りる。目で見るのはユーザー（HTML）
- 機械的な作業（翻訳・`CHANGES`・データの転記）はサブエージェントに任せ、本体の会話を膨らませない

## 黙って待たせない決まり（ユーザーは、ツールが終わるまで何も見えない）
実行中のコマンドの途中では、こちらからメッセージを出せない。**長い処理を前景（foreground）で走らせると、その間ユーザーには何も見えず、「止まった？」と聞かせてしまう。**
- **15 秒以上かかりそうなものは、すべて `run_in_background: true`**（撮影 `--capture`・`--book`・`--release`・`npm run dev` の起動・build）。**始める前に1行**：何を始めるか・目安の時間（例「撮影を始めます。18状態で約1分」）
- **待つあいだは `Monitor` で進み具合を流す**：撮影は `[3/18] … 残り約 61 秒` が出る。サーバーの起動待ちは `until curl --noproxy '*' -sf http://localhost:3000/ >/dev/null; do sleep 2; done`。`sleep` を並べない（止められる）
- **約 1 分ごと、または区切りごとに短く報告**（「撮影 10/18 済み・残り約 25 秒」）。終わったら結果を1〜2行で
- **複数の手順がある作業は、最初に `TaskCreate` で予定を出す**（例：確認 → 撮影 → レビュー → 作成）。ユーザーが今どこか見える。終わるたびに更新
- サブエージェント（翻訳・レビュー）に任せるときも、「◯◯を頼みました。完了したら続けます」と先に伝える
- 長い処理の前に、**まとめて聞くこと（確認表）を先に済ませる**。撮影の途中でユーザーを待たせる質問を挟まない

## 失敗したときの決まり（動かない・理由がわからない、をなくす）
- **長い処理の前に `make.py --doctor`**（約10秒）：部品・ブラウザ・サーバー・ログイン・ほかの撮影を点検し、だめなものは「原因と対処」で出る。20〜80秒走ってから失敗するより早くわかる
- **どの実行も、最後の行が結果**：`✔ 完了` か `✖ 失敗：原因／→ 対処：…`。背景で動かしたら `Monitor` で `grep -E "✔ 完了|✖ 失敗|✖ 止まりました"` を待つ。**結果は必ずユーザーに報告する**（成功も失敗も1〜2行。黙って終わらせない）
- **失敗したら**：原因と対処をそのまま伝え、直せることは1回だけ直して再実行。**同じ失敗が2回続いたら止めて、ユーザーに状況を伝えて聞く**（同じことを繰り返さない）
- エラーの全文は `出力/.last_error.log`（または /tmp/.last_error.log）。**全文を読まず、最後の10行まで**（token を使わない）。出力を受け取るときは `2>&1 | tail -15`
- 進み具合は5状態ごとだけ出る（`KD_PROGRESS_EVERY=1` で毎回）

## 複数のスレッドで動かすときの決まり（重なり・聞き直し・ID の衝突を防ぐ）
別のスレッドの作業は、**そのブランチを push するまで見えない**（main に入るまで台帳にも出ない）。実際に、同じ商品マスタを2スレッドが何日も進め、台帳に「1商品＝1仕入先」と「複数の仕入先」が並び、ID も重なった（`引き継ぎ_商品マスタ_二つのスレッドの突き合わせ_20261008.md`）。読み取りだけの `scripts/kd_ask.py`（git grep／diff。チェックアウトしない）で防ぐ：
1. **作業を始める前**に `python3 scripts/kd_ask.py who <機能コードかパス>`（例 `AW_PROD`・`app/ops/masters/products`）。同じファイルを触っている他のブランチがあれば、**始める前にユーザーに「◯◯ブランチと重なっています。どちらが続きますか？」と聞く**（黙って続けない）。push の前にも `who`（引数なし＝自分の変更）
2. **ユーザーに聞く前に必ず** `python3 scripts/kd_ask.py gate …`（まとめて判定。1語だけ探すなら `check <語…>`）（main と、他のスレッドの未マージの台帳・受付簿・確認メモ）。**答えがあれば聞かない**。出どころ（ファイル・日付・ブランチ）を言って進める。新しい事情で台帳と食い違うときだけ「○/○ に △ と決めています。□ に変えますか？」と**1回**。ユーザーの答えを「前と違う」と言うときは、前の答えを引用する（引用できないなら言わない）
3. **答えをもらったら、すぐ**台帳か受付簿へ1行書いて commit・push（次の作業の前に）。push するまで他のスレッドには見えない
4. **ID（message の E/W/I/Q/S・受付簿の番号）を決める前**に `kd_ask.py ids --next E --range <領域の範囲>`。決めたらすぐ push。push の前に `kd_ask.py ids`（他のブランチと重なっていないか）
5. **共通・権限の質問は、機能のスレッドで聞かない**：先に `check 共通 <話題>`・`check 権限 <話題>`（台帳 K・M-1、`運営Web_権限表`）。なければ、推奨を「仮」として進め、質問は受付簿に【共通質問】として1行（状態＝受付）残す。どのスレッドも同じ行を使い、ユーザーには**まとめて1回**だけ聞く
- `make.py --doctor` も、同じファイルを触っている他のブランチを知らせる

## 作業フォルダ

```
<作業フォルダ>/
  データ/
    _共通_メッセージ.py   … システム全体で1つ（assets/_共通_メッセージ_ひな形.py から作る）
    _共通パターン.py       … システム全体で1つ（assets/_共通パターン_ひな形.py から作る）
    <機能>.py              … 1機能1ファイル（assets/_ひな形.py から作る）
  出力/                    … make.py が作る（直接直さない）。出力/.capture_cache/ は撮影のキャッシュ（コミットしない）
```

作業フォルダの場所はユーザーに聞く（既存の資料フォルダを勝手に上書きしない）。ツールは `scripts/`：`python3 <スキル>/scripts/make.py …`
初回だけ（了解を取ってから）：`pip install playwright openpyxl pillow`。ブラウザは Google Chrome（なければ `/opt/pw-browsers` の Chromium を自動で使う）。scenario-flow と共用。
ブラウザを使う処理は重いので、デモ・打ち合わせの直前には実行しない。

## 元にするもの：デモ（HTML）か、本物の Web（es-station-dev のコード）か

| | デモ（HTML 1ファイル） | 本物の Web（コード） |
|---|---|---|
| `DEMO_FILE` | `"02_デモ/部品/XX_XXX.html"` | `"http://localhost:3000"` |
| `VIEWPORT`（任意） | 省略（1440×900） | スマホのアプリは `(390, 844)`（`make.py --width/--height` でも指定できる） |
| 状態の作り方 | `setup`（JavaScript） | 状態ごとに `url`＋必要なら `setup`（async）。別アカウントは `login`、デモの「今日」は `today` |
| ログイン | 不要 | `LOGIN = {"site": "ops", "loginId": "Ad00010"}`（見本の ID は `lib/domain/seed/account.ts`） |
| 項目の読み取り元 | デモの HTML | **コード**（`app/<site>/.../page.tsx`・`lib/<site>/`・`lib/domain/`。入力チェック・初期値・選択肢はここが正） |
| 撮影の速さ | — | 変わった状態だけ撮るので、ふつうは `npm run dev` のままでよい（→ 下の「サーバーの動かし方」） |
| 撮影のキャッシュ | デモの HTML の中身が変わったら撮り直す | `CODE_PATHS = ["app/ops/masters/plans", "lib/domain/seed"]` に機能のコードだけ書くと、他の機能を直しても撮り直さない（省略時は app・lib・components 全体） |

コードと決定台帳・仕様が違うところは、デモとの差と同じ扱い（ユーザーに確認 → データを直すか `demo_ok`）。

## サーバーの動かし方（本物の Web を撮るとき）
**デモの「今日」・データのリセット（`today`・`reset_data`）は、`NEXT_PUBLIC_DEMO=1` のビルド／起動でしか動かない**（ふつうの本番ビルドでは 404）。必ず付ける。
- **既定：`NEXT_PUBLIC_DEMO=1 npm run dev`**（バックグラウンドで起動：`run_in_background: true`）。初回は各ページのコンパイルで遅いが、2回目からはキャッシュで撮らない
- **全部撮り直すとき（状態が多い）だけ**：`NEXT_PUBLIC_DEMO=1 npm run build`（バックグラウンド）→ `NEXT_PUBLIC_DEMO=1 npm run start`（バックグラウンド）。コンパイル待ちがなくなる。速さはまだ計っていない
- **待ち方**：`sleep` を並べない。`Monitor` で `until curl -sf http://localhost:3000/ >/dev/null; do sleep 2; done` を待つ（長いコマンドは `run_in_background`）
- **止め方**：`fuser -k 3000/tcp`（`lsof` は cloud でポートを見つけられないことがある）。確認は `curl --noproxy '*' -s -o /dev/null -w '%{http_code}' http://localhost:3000/`（`--noproxy` なしだとプロキシ経由で 200 が返ることがある）。**`pkill -f "next dev"` は使わない**（コマンド自身の文字列に一致して、自分のシェルを落とす）
- 撮り終わったら止める。止める前に、ユーザーが同じサーバーを使っていないか確かめる
- **複数の作業（セッション）を同時に動かすとき**：デモのデータは**チェックアウトの `data/es.db`** にあり、撮影のたびに見本へ戻す・日付を変える。**同じサーバー（同じフォルダ）を2つの作業が使うと、互いのデータを消して違う画像になる。** 同じサーバーの撮影は自動で順番待ちになる（待つだけで速くはならない）。**並べて撮るなら、作業ごとに別のフォルダとポートにする**：
  1. `git worktree add ../wt2 HEAD --detach` → `cp -al node_modules ../wt2/node_modules`（**`ln -s` のシンボリックリンクは使わない**：Turbopack が `Symlink node_modules … points out of the filesystem root` で止まる。`cp -al` は一瞬・追加の容量なし。`make.py --doctor` がリンクを見つけて知らせる）
  2. `cd ../wt2 && NEXT_PUBLIC_DEMO=1 npx next dev -p 3001`（作業ごとに 3000・3001・3002…）
  3. `KD_BASE=http://localhost:3001 python3 …/make.py --capture …`（`127.0.0.1` ではなく `localhost`：Next が別のホスト名を止めて、ログイン画面が出ない）
  実測：別のフォルダ・別のポートの2つは待ち合わず同時に撮れ、データも別（`data/es.db` が別）

## 流れ

### 1. 範囲を決める
デモ（またはコード）・対象の画面・Screen Code・システム（`SITE`）をユーザーと決める。
**状態の一覧**（id・作り方）を先に見せる。後から足すと番号がずれる。1回の作業は**小さな機能1つ**にする。

### 2. 洗い出して、まとめて確認する
`references/confirm_flow.md` の手順で、食い違い・未決・（案）・仮・Message List との差を全部リストにし、**表で一括して聞く**（1行に 元の文の引用・出どころ・選択肢・推奨）。
ユーザーは「OK 全部、#3 と #7 だけ別」と返せる。影響が大きいものだけ単独で聞く。`input_standard.md` に基準があるものは聞かずに適用する。
- 答えはデータへ反映し `DECISIONS` に記録。「お客様に聞く」は `open`（`ask`）。推測で埋めない
- 確認が済むまでは `chk` に書く → `make.py` が作らない

### 3. データを書く（日本語だけ → 骨組み → 翻訳）
1. **骨組み**：`python3 scripts/kd_scaffold.py <URL か HTML> [--login-id …] [--setup "JS"] > 骨組み.txt`（ラベル・必須・最大文字数・選択肢・セレクタが入る）
2. **日本語を足す**（`assets/_ひな形.py` のキー）：詳細・条件・バリデーション・`err`・`pattern`・状態名・補足。`vi` は `""` のまま
   - メッセージは ID だけ（`err`）。文言は `_共通_メッセージ.py`（`references/message_style.md`）。法人・拠点（SITE=corp）は `ja_c`、他は `ja_o`
   - 共通の動きは `pattern`。文字数・数値・日付・ファイルは `references/input_standard.md`。番号は振り直さない（増えたら末尾）
   - 入力項目には `ex`（データ例）。**例の値は日本語で今書く**（本番に入りそうな現実の値）。説明は空でよい
3. **翻訳を1回で（サブエージェントは Sonnet。Haiku は使わない）**
   - 理由：Haiku に頼んだら、3ファイルが壊れ、約54か所で欄を取り違えた（詳細に項目名が入った等。hong 2026-10-06）
   - 1ファイルにつき1エージェント。依頼文に書くこと：「`vi` と `ex` の2つ目（説明）だけを埋める。**`detail` には同じ項目の `detail` の日本語だけを訳して入れる（項目名や他の欄を入れない）。** `ja`・`sel`・`no`・キー名は触らない」
   - `ex` の説明は「何の値か・どんな形か」。例 `["カブシキガイシャエービーシー", "Tên công ty viết bằng Katakana toàn góc (ví dụ: công ty ABC)"]`
4. **受け取る前の確認（自動）**：`make.py --check` が、訳の入れ違い（詳細の訳が項目名と同じ・別の欄と同じ）と、長さの異常（日本語 12 字以上で、ベトナム語が日本語の 0.5 倍未満・6 倍超。人が訳したデータは 0.53〜3.8 倍）を**誤りとして止める**。止まったら、その項目だけ訳し直す。通ったあとも `git diff` で `ja` が変わっていないことを確かめる
5. 翻訳後、`--check` が二か国語の抜けも止める

### 4. 確認する → 役割レビュー（データ段階）（ブラウザ不要・何度でも）
`python3 scripts/make.py --check <作業>/データ/<機能>.py`：「データの誤り」「未確認」「共通メッセージの決まり違反」が 0 になるまで 2・3 に戻る。
**撮影の前に、役割レビューの「データ段階」を済ませる**（`make.py --review <データ>.py`＝token 0、必要ならサブエージェント1つ → `references/role_review.md`）。理由：**撮影がいちばん遅い**うえ、レビューの指摘（項目・`sel`・名前の直し）は撮影のキャッシュを無効にするので、先に直すほど撮り直しが減る。直した結果は `--check` で確かめてから 5 へ。表示の確認（D1〜D9）は撮影の測定が要るので、5 のあとに出す。

### 5. 画面で確かめる（変わった状態だけ撮る）
```bash
python3 scripts/make.py --capture <データ>.py              # 変わっていない状態は撮り直さない
python3 scripts/make.py --capture --views 003,007 <データ>.py  # 指定した状態だけ
python3 scripts/make.py --capture --force <データ>.py          # 全部撮り直す
```
- **撮り直さない状態の「やり直し」（replay）**：あとの状態が前の操作の結果（登録したデータなど）を見るので、前の撮影で**データを変えた状態**（`data/*.db` の変更回数で判定。API の名前では決められない）だけは、撮らずに操作をやり直す。見るだけの状態はやり直さない。実測：1状態の撮り直し 44秒 → 12秒。`--no-replay` で全部やり直さない（あとの状態が前の結果を見ないとき）。データベースが見えない（別のマシンのサーバー）ときは安全側で、やり直す
- **撮影のあと**に `make.py --review --display-only <データ>.py`（token 0）：入力欄が最大文字数ぶん見えるか・文字切れ・横スクロール・必須の位置・主ボタンの見た目（D1〜D9）。直す箇所が画面（コード）なら、直してからその状態だけ `--views` で撮り直す
- **時間**：1状態あたり約3秒（全部撮り直しで 20状態＝約1分）。進み具合と残り時間が `[3/18] … 残り約 61 秒` と出る。**長い撮影は `run_in_background`** にして、ユーザーには「約◯秒かかる」と先に伝える。直したときは `--views` で**直した状態だけ**撮る（全部撮り直さない）
- 出力は「見つからない番号」と「画面との差」だけ。**PNG は見ない**。番号が見つからない → `sel` を直す（直した状態だけ撮り直される）
- **`sel` の書き方**：`#id`／`input[aria-label="…"]`（手がかりがあるものを優先）、`ボタン::検索`（`セレクタ::文字`。**`css::` と書かない**）、**`input@3`（見えている input の3番目）**、末尾 `^`（1つ上）。**`DateInput` は input が2つ**（見える文字入力＋カレンダー用の隠し `type=date`。`aria-hidden`）。`@N` と `kd_scaffold` は隠しものを数えないので、`input:nth-of-type` のような順番の指定をしない
- 画面にない定義（CSV の列など）は `sel: "-"`。デモとの差 → ユーザーに確認し、データを直すか `demo_ok` に理由
- `SHEETS` で追加のシート（初期データなど）を足せる
- 本物の Web は、撮り直す状態があるときだけサーバーにつなぐ。つながらなければ止まる

### 6. 作る（段階で作るものを変える）
**1サイト＝1ファイル（1機能＝1シート）。** 運営管理者Web は領域ごとに複数ファイルでよい（分け方は増えた時点で確認）。1機能を2つに分けない。

| 段階 | 作るもの | コマンド |
|---|---|---|
| 作業中（何度も） | なし（`--check` だけ） | `make.py --check …` |
| ユーザーに見てもらう | **HTML だけ**（日越切替・コメントの窓口） | `make.py --only html --book 法人Web <データ>/CW_*.py` |
| 開発・お客様に渡す（版をつける） | **Excel JA・VI と HTML** | `make.py --release 1.1 --book 法人Web <データ>/CW_*.py`（→ 手順7） |

- **Excel は渡すとき（release）だけ作る。** お客様向けは JA、開発向けは VI。社内のレビューは HTML で行う（ユーザーは Mac で xlsx をすぐ開けない）
- 1機能だけ下見：`make.py --only html <データ>/<機能>.py`
- 撮影は `--capture` と共用のキャッシュを使うので、同じ状態を2回撮らない。HTML は共通の CSS を1つにまとめて入れる（スナップショットの重複なし）
- できるもの：`画面設計書_…_JA.xlsx`・`…_VI.xlsx`・`.html`・`出力/_共通/メッセージ・メール一覧`

### 7. 役割レビューの仕上げ — 見てもらう・渡す前に
データ段階は手順4で済んでいる。ここでは、撮影のあとの **表示の確認**（`--review --display-only`）の指摘と、データ段階で未決だったもの（`open`・受付簿）が残っていないかを確かめて、1つの表（最大15件）にしてユーザーに見せる。仕様・台帳は直接直さない（決めた行だけ `決定の受付簿` へ）。

### 8. 開発に渡す・見てもらう
**`references/release_and_review.md` を読む**（版の決まり `--release`・`CHANGES`・HTML へのコメントの処理・Drive）。
最後に、作ったファイル・項目数・OPEN の件数と中身・Message List への追加案の件数を短く報告する。

## 直すとき
- 決定が出た → データを直し、`DECISIONS` に1行、`open` を消す。開発に渡し済みなら `CHANGES` にも1行 → 4〜6
- デモ・コードが変わった → `--capture`（変わった状態だけ撮り直される）→ 6
- メッセージを直した → `_共通_メッセージ.py` を直すと全画面に効く。全部の機能を作り直す
- **コメントは1日分をまとめて**：まとめて処理 → 台帳と受付簿へ1回で書く → 1回だけ作り直す
- Excel・HTML を直接直さない（作り直すと消える）

## ツール（scripts/）
- `make.py` — `--check`・`--capture`（`--views`／`--force`）・作成・`--release`。未確認や改訂履歴の書き漏れがあれば作らない（社内の下見だけ `--draft`）
- `kd_ask.py` — 質問ゲートと複数スレッドの確認：`digest`（その画面で決まっていること）・`gate`（質問ごとに 答えあり／共通／聞く）・`who`（同じファイルを触る他のブランチ）・`check`（他のスレッドの答え）・`ids`（ID の衝突・次の空き番号）
- `kd_scaffold.py` — 画面から項目の骨組みを出す
- `kd_review.py` — `make.py --review`：役割レビューの機械分（抜けの疑い）。ブラウザ・LLM 不要
- `kd_capture.py`・`overlay.js` — 番号を重ねて撮影（Playwright）。`出力/.capture_cache/` に記録を残し、変わっていない状態は撮らない
- `kd_rules.py`・`kd_build.py`・`kd_common.py`・`ml_export.py`・`common_template.html`・`viewer_template.html` — 確認のルール／Excel と HTML／メッセージ一覧
