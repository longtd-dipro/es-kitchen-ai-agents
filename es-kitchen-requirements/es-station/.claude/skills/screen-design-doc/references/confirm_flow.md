# 作る前に確認する（未確認を残したまま資料にしない）

ユーザーの方針：**資料を作ってから「要確認」が並ぶのは困る。わからないことは、作る前に1つずつ確認する。**

## 1. 洗い出す（データを書く前）

**0. 質問ゲート（表を作る前に必ず。ここを通ったものだけ聞く）**
1. `python3 scripts/kd_ask.py digest <画面コード>`：この画面で**もう決まっていること**（各画面の `DECISIONS`・台帳・受付簿）。読んで頭に入れる。ここにあることは聞かない
2. 聞きたいことを全部下書きにして、**まとめて** `python3 scripts/kd_ask.py gate "語 語 | 質問" "語 語 | 質問" …`（`-f 質問.txt` も可。語は2〜3個、言い換えを1回は変えて探す。例：並び順→並べ替え・ソート）。main と他のスレッドの未マージ分、各画面の `DECISIONS`、`input_standard.md`・`message_style.md` まで見る
3. 判定で分ける：
   - **✔ 答えあり** → 聞かない。**適用して**、表の下に「適用した決定」として1行ずつ（出どころ付き）。hong が違えば直す
   - **◇ 共通の話題** → 機能のスレッドでは聞かない。`common_answers.md` を見て、なければ受付簿に【共通質問】1行・推奨を「仮」で進める
   - **? 聞いてよい** → これだけが確認表に入る
4. 「答えあり」の行を読んで、**質問の中身が本当に同じか**を確かめる（語が合っただけで別の話のことがある）。同じなら聞かない。台帳と食い違う新事情があるときだけ「○/○ に △ と決めています。□ に変えますか？」を**1回**。ユーザーの答えを「前と違う」と言うときは、前の答えを引用する（引用できないなら言わない）

**確認表を出す前の自己チェック（1つでも「はい」なら、その行を表から外す）**
- 台帳・受付簿・`DECISIONS`・基準のどれかに答えがある？
- 共通の話題（`common_answers.md`）？ 他の画面で同じことを聞いたことがある？
- コード／デモ／ファイルを読めばわかる？
- 同じ表の中に、同じ質問が2行ない？（画面が違っても答えが同じなら、1行にまとめる）

次を読み、「決まっていない・食い違っている」ものを全部リストにする。

| 見るもの | 探すもの |
|---|---|
| デモ（DEMO_FILE） | 画面・タブ・モーダル・エラー時の状態。項目名・必須表示・選択肢・最大文字数 |
| 決定（ES なら `01_仕様/00_決定/決定_*.md`、新しい日付から） | その画面の項目・動き・権限・メッセージに関する決定。**古い決定を新しい決定が上書きしていないか** |
| 仕様（`01_仕様/` の各領域・入力チェック仕様・メール一覧） | 桁数・必須・形式・バリデーション |
| Message List（Excel） | 使うメッセージの番号と文言 |
| 共通の決まり（`基本設計_全体の定義_*.md`） | メッセージの出し方・権限・入力の共通ルール、共通パターン |
| 課題一覧（`00_確認してほしい/`） | その画面に関係する未決の課題 |

リストに入れるもの：
- デモと仕様・決定が違う
- 決定どうしが食い違う（日付の新しい方が正とは限らない。対象が違うだけのこともある）
- 数字・上限・URL・初期値・形式が決まっていない
- 仕様に「（案）」「要確認」「未定」「仮」とある
- Message List と文言が違う／Message List にない
- Screen Code が仮

## 2. まとめて確認する（表で一括）

ユーザーの方針：**資料を作る前に確認する。ただし1問ずつ聞くと往復が増えて時間も token もかかる。**

- 洗い出したものを **5〜10 件ずつの表** にして1メッセージで聞く。列：`#`｜何が食い違う／未決か（元の文を短く引用）｜出どころ（ファイルと節）｜選択肢｜**推奨（既定）**｜推奨の理由
- ユーザーは「OK 全部。#3 は B、#7 はお客様に聞く」のように返せばよい。**推奨を既定として、返事がない行は推奨どおり**にしてよいかを表の最初に1行で確認する
- **単独で聞くもの**：他の機能・台帳の決定をひっくり返す／お金・権限・法務に関わる／選択肢ごとの影響が大きい
- **聞かずに適用するもの**：`input_standard.md` に基準がある（文字数・数値・日付・ファイル）／台帳に決定がある／ファイルを読めばわかる
- 台帳の決定と違う答えが来たら、`CLAUDE.md` の決まりどおり「○/○ に △ と決めています。□ に変えますか？」と確認してから変える
- ユーザーが「お客様に聞く」と答えたら、その項目は `open`（確認先 `ask`）。推測で埋めない

## 3. 記録する

- **答えをもらったら、次の作業の前に**台帳か受付簿へ1行書いて commit・push（そのスレッドの `DECISIONS` だけに書くと、ほかの画面・スレッドから見えず、また聞かれる）。共通の話題なら `common_answers.md` にも場所を1行足す

- 答えはその場でデータに入れる：決まった内容を項目に反映し、`DECISIONS` に1行（日付・対象・質問・答え・根拠「hong 回答 YYYY/MM/DD」）
- プロジェクトに決定の置き場がある場合（ES は `01_仕様/00_決定/`）は、そちらへの記録もユーザーに提案する（勝手に作らない）
- `chk` を消す。お客様に聞くものは `open` に移す

## 4. 作る

- `make.py --check` で「データの誤り 0・未確認 0」になってから作る
- デモを開いて撮影したときに出る「デモとの差」も同じ扱い：ユーザーに確認し、データを直すか、「仕様が正しい（デモを直す）」なら `demo_ok` に理由を書く
- `--draft` は社内の下見だけ。お客様・開発に渡すものには使わない（表紙と各シートに「ドラフト」と出る）
