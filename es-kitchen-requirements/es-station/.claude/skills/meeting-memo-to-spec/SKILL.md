# 議事録メモ → 要件仕様 反映スキル

自動生成された会議メモ（Gemini のメモなど）を、プロジェクトの要件仕様書群に
一貫した形で反映するためのスキル。狙いは「毎回の会議で出た決定を、正しい
ドメインの仕様書へ、正しい採番で、誤認識を補正しながら追記する」こと。

自動文字起こしの**要約部分は圧縮による誤りを含む**という前提で動くのが肝心。
要約だけを信じて仕様に書くと、固有名詞や数値の聞き違いがそのまま仕様の
バグになる。だから常に文字起こし本文で裏を取り、確信が持てない箇所は
消さずに「要確認」として残す。

## 全体の流れ

> **2026-10-03 から：会議の決定を仕様書へ直接書かない。** まず `docs/決定の受付簿.md`（受付簿）に入れ、
> hong が「採用」にしたものだけを台帳（`docs/決定台帳.md`）と仕様へ反映する。
> 理由：決まった話題が会議でまた開かれることがある／仕様を直してもコードを直すきっかけが残らない。
> ES の場合のファイル・手順の細部は `ÉS/議事録/CLAUDE.md` が正。

1. 入力メモを読む（抽出）
2. 台帳と仕様を把握する（いま何が決まっているか・どこに書くか）
3. 決定事項を拾い、ドメインへ振り分ける
4. 誤認識を裏取り・補正する
5. **受付簿に1件1行で入れる**（台帳と比べて 新規／変更／再オープン／確認 を付ける。仕様は直さない）
6. hong に確認する（変更・再オープンは必ず個別に）→ 採用分だけ台帳・仕様へ反映し「実装待ち」にする
7. 統合まとめ（会議一覧・OPEN一覧）を更新し、自己検証して報告する

## 1. 入力メモを読む

`.docx` なら同梱スクリプトで本文を取り出す。Gemini のメモは
「概要 / 決定事項 / さらなる議論が必要 / 調整済み / 次のステップ / 詳細 /
文字起こし」の見出しで並ぶ。要約（上部）と**文字起こし（下部）の両方**を読む。

```bash
python scripts/extract_docx.py "<メモ.docx>"                 # 全文
python scripts/extract_docx.py "<メモ.docx>" --section 文字起こし   # 発言本文だけ
python scripts/extract_docx.py "<メモ.docx>" --grep 返金,ESQR,締め   # 争点の周辺だけ
```

`.txt` やチャット貼り付けならそのまま読む。会議日付（例 2026/09/29）を必ず
掴む — 採番ではなく「いつの決定か」を全行に残すために使う。

## 2. 対象の仕様書群を把握する

既存の仕様書がどこにあるか・どんな構成かを最初に調べる。ユーザーの
プロジェクトでは、ドメイン別の「◯◯_詳細要件仕様.md」と、横断の
「議題別・議事録統合まとめ_….md」に分かれていることが多い。

```bash
# 仕様書の棚卸し
ls <仕様フォルダ>
# 既存の採番と章末を確認（どのプレフィックスがどのファイルか）
python scripts/next_req_id.py <仕様フォルダ>/*.md
```

各ファイルの末尾付近（「要件（YYYY/MM/DD 追加）」節や OPEN 一覧）を読み、
**追記の定型**（表のカラム、ステータス語彙、日付の書き方）に合わせる。
勝手に新フォーマットを作らず、既存に寄せるのがこのスキルの価値。

> ファイルの正規化（macOS の NFD など）で `grep`/glob が空振りすることがある。
> その場合は `find <root> -name '*.md'` で実体を探してから読む。

## 3. 決定事項をドメインへ振り分ける

メモの「決定事項／調整済み／次のステップ／詳細」から、仕様に落とす粒度の
決定を拾い、ドメインごとに仕分ける。判断は**内容**で行い、キーワードだけで
機械的に振り分けない。プロジェクトごとのプレフィックスと振り分け方針は
`references/routing.md` にテンプレートがある（最初に読んで、プロジェクトの
実際のファイル名・プレフィックスに合わせて使う）。

- 「決定事項／調整済み」→ ステータス「決定済み」で要件行に
- 「さらなる議論が必要」→ OPEN 一覧へ（ステータス「OPEN」）
- 「次のステップ（担当つき）」→ アクション／OPEN として担当・期日つきで

## 4. 誤認識を裏取り・補正する（最重要）

要約に出てくる固有名詞・数値・社名・用語は、**文字起こし本文**で確認してから
書く。自動文字起こしは同音異義・カタカナ語・英単語を取り違えやすい。

- **確信がある訂正**（明らかな誤字・既知の社名）は本文で確認のうえ正す。
  例と判断の根拠は `references/glossary.md` に蓄積する（プロジェクト固有の
  用語集。見つけた対応を追記して育てる）。
- **確信が持てない語・数値**は、勝手に確定させない。元の表記を残しつつ
  「（要確認）」を併記し、OPEN 一覧にも用語確認として1件立てる。
- **金額・個数・日付・率**は会議の例示値か確定値かを区別し、例示なら
  「（例）」と明記する。

やってはいけないのは、聞き違いをそのまま仕様の確定事項として書くことと、
逆に不確実なのに断定して「要確認」を省くこと。迷ったら要確認を残す。

## 5. 受付簿に入れる（仕様はまだ直さない）

決定（「決定」「暫定」「取消」）を `docs/決定の受付簿.md` の表に1件1行で足す。状態は「受付」。

- **台帳（`docs/決定台帳.md`）と必ず比べて種別を付ける**：
  新規（台帳にない）／**変更**（台帳と違う。「台帳の現在」列に旧の決定と決定日を書く）／
  **再オープン**（決まった話題をまた議論し、結論が出ていない）／確認（同じ内容の再確認）。
- 「反映先」に台帳の行と仕様の章（例：`配送仕様/配送_06` §12-2）を、「影響する画面・コード」に
  直すことになる画面・API を書く（わかる範囲。わからなければ「要調査」）。
- 「要件案」「OPEN」「要確認」は受付簿に入れず、OPEN 一覧へ（手順7）。

## 6. hong に確認し、採用分だけ反映する

- 受付簿の「受付」の行をまとめて見せ、採用／保留／却下を聞く。**変更・再オープンは1件ずつ**、
  台帳の決定日と旧内容を引用して聞く（「○/○ に △ と決めています。□ に変えますか？」）。
- **採用**になった行だけ：台帳の行を直し（旧の決定は「置き換えた旧決定」へ）、仕様の該当章を直し、
  受付簿の状態を「実装待ち」にする。台帳・仕様・受付簿は**同じコミット**で直す。
- **再オープン**で結論が出ていない話題は、台帳の行に「再オープン中（会議日）」と注記するだけ。仕様は直さない。
- hong が「一気にやって」と言ったときも、変更・再オープンだけは確認してから反映する。

### （参考）仕様書に要件行を足すときの書き方

採用分を、まだ REQ 採番を使っている仕様書へ反映するときは、ドメインごとに次の採番を取り、既存の表形式に合わせて行を足す。
**凍結（原典）と書かれた仕様書には足さない**（正のファイルへ）。

```bash
python scripts/next_req_id.py <対象ファイル>.md --prefix CT   # 次の REQ-CT-xxx
```

追記は「その会議日の節」を1つ作ってまとめるのが読みやすい。各節の冒頭に
**背景メモ**（会議日・扱った論点・誤認識の補正対応表）を1段落置くと、
後から誰が見ても判断の根拠を追える。既存の章見出し・表カラム・ステータス
語彙に必ず合わせる。

節の形（例・既存に合わせて調整）:

```markdown
### 要件（YYYY/MM/DD 追加）

背景メモ：本節は YYYY/MM/DD 定例（扱った論点…）に基づく。要約中の
「<誤>」は <正>（elepay 等）、金額・個数は例示値。

| 要件ID | 要件区分 | 要件内容 | 対象者 | 対象サイト | ステータス |
|---|---|---|---|---|---|
| REQ-CT-271 | 運用要件 | … | … | … | 決定済み |
```

編集の安全策：追記対象のファイルは編集直前に読み、既存行を壊さない。
番号の重複・順序（日付の昇順）に注意する。

## 7. 統合まとめを更新し、自己検証して報告する

横断の「議題別・議事録統合まとめ」には、(a) 会議一覧へ1行、(b) OPEN 一覧へ
新規の未決事項、を追記する。会議一覧の行には、その回の決定を**圧縮せず**
主要論点を網羅して書く（後でここだけ見れば回を思い出せる密度にする）。
OPEN 一覧には担当・期日・発生日（会議日）を入れる。用語の要確認（手順4）も
ここに1件として残す。

### 自己検証

反映後、最低限これを確認する:

- 受付簿の全行に種別・状態が付いているか。変更・再オープンを hong に確認したか
- 採用した行の台帳・仕様・受付簿を同じコミットで直したか
- 追記した REQ-ID に重複・欠番がないか（`next_req_id.py` で再確認）
- 各行のステータス語彙・表カラム数が既存と揃っているか
- 「要確認」「（例）」が必要箇所に付いているか、断定しすぎていないか
- 会議一覧の日付順、OPEN の通番

最後に、変更したファイルを提示し、何をどのドメインへ入れたか・誤認識を
どう補正したか・何を要確認として残したかを簡潔に報告する。細かな全文の
再掲はしない（ユーザーがファイルを直接見られるため）。

## 参照ファイル

- `references/routing.md` — ドメイン振り分けと採番プレフィックスのテンプレート。
  プロジェクトの実ファイル名に合わせて最初に調整する。
- `references/glossary.md` — 自動文字起こしの誤認識→正しい表記の対応集。
  見つけた対応を追記して育てる、プロジェクト固有の用語集。

## 同梱スクリプト

- `scripts/extract_docx.py` — .docx から本文/節/該当行を抽出。
- `scripts/next_req_id.py` — 仕様書群から次の REQ 採番を算出。
