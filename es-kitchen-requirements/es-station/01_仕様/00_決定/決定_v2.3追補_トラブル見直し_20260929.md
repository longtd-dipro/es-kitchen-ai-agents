## 27. みなし完了の後に「届いていない」と分かったとき（C-1）

- 法人・拠点から「届いていない」と連絡があったら、運営が代理でトラブル報告を登録し、**ヤマト（運送会社）に調査を依頼する**。
- 調査の結果、紛失・未配達と分かった場合、**みなし完了（`completion_source = presumed`）の `納品済` に限り**、運営（物流）の解決で **`再配達待`** または **`中止`** へ進められる。
  - 〔上書き〕#21 の「納品済 から選べる解決は全量納品だけ」に例外を1つ足す。**ドライバーの報告で納品済になったもの（`reported`）・法人の受領確認（`customer`）は対象外**のまま。
  - `再配達待` を選んだときは、ほかの再配達と同じく子（`確認中`）を作る／自動子があれば使い回す。
- 請求は実績に従うので、`再配達待`・`中止` にした分は請求しない。**すでに請求が確定していれば、遡って書き換えず翌月の調整（返金・相殺）で直す**（統合 §14-3）。
- **未決**：箱の一部だけ届かなかった場合（`一部納品済` へ進めるか）は決めていない。

## 28. 子（再配達・分納など）でもう一度トラブルが起きたとき（C-2）

- **子からは複製しない。親の次の枝番を作る**（親子1階層のルールは維持）。
  - 例：`DL-…-0014-1` でトラブル → 新しい子は `DL-…-0014-2`（親 `-0014` の子）。内容（納品先・納品条件・受取時間帯・`delivery_legs`）は **トラブルが起きた子** からコピーする。
- トラブルが起きた子そのものは、ほかの配送と同じく解決で閉じる（`再配達待`・`中止` など）。
- 自動子（#30）も同じ規則で、親の次の枝番として作る。
- 枝番が9を超える場合は `DOMAIN_BRANCH_LIMIT` とし、要確認に出して運営が判断する。

## 29. 1件の配送に複数のトラブル報告があるとき（C-3）

- **解決は配送単位でまとめて行う。** その配送の未解決のトラブル報告をすべて、1回の解決で閉じる（同じ解決内容・解決日時・解決者を各報告に記録）。
- **自動子は「トラブルが起きた配送1件」につき、生きているもの（`取消` 以外）を1件まで。** 2件目の報告が来ても子は増やさず、既存の子を使い回す。
  - 〔上書き〕9/24 の「1つのトラブル報告に子は最大1件（`UNIQUE(source_trouble_report_id)`）」を、**配送単位の一意**に変える。

## 30. 自動子は報告と同時に、種類ごとに作る・作らないを決める（C-4）

- **時間（SLA）を待たずに、トラブル報告を登録した時点で自動子を作る。** 期限の計算（`auto_duplicate_due_at`）・運用設定の分数（`trouble_auto_duplicate_after_minutes`）・バッチ `trouble_auto_duplicate` は**廃止**する。
  - 〔上書き〕#22「期限までに解決されないトラブルは自動子を作る」・#25「バッチ `trouble_auto_duplicate` を新設」を取り消す。
- **作るかどうかはトラブル種別マスタ（6区分）で決める。**

| 種別 | 自動子 | 理由 |
|---|---|---|
| 誤配送 | **作る** | 回収＋再配達がほぼ必ず要る |
| 不在・受け取り不可 | **作る** | 再配達がほぼ必ず要る |
| 破損・品質不良 | **作る** | 代替品・再配達の準備が要る |
| 数量相違（不足・過剰） | **作らない** | 1〜2個なら送らないこともある。運営が解決のときに「送る／送らない」を選び、送るときだけ子を作る（#31） |
| 遅延（渋滞・事故・天候） | **作らない** | 当日中に届けば不要。当日中の納品報告で自動解決（#32） |
| その他 | **作らない** | 運営が個別に判断 |

- **報告の時点の種別は、ドライバーアプリの選択肢から決める**（統合 §13-1 の対応表）。2区分にまたがる「商品不足・誤配送」は**種別未定として作らない**。運営があとで6区分を付け、その種別が「作る」なら、**その時点で自動子を作る**。
- 運営の代理登録では、運営が選んだ種別で判定する。
- 自動子の中身は 9/24 と同じ：`確認中`・`duplicate_type = trouble_pending`・納品先スナップショット・納品条件・受取時間帯・`delivery_legs` をコピー（送り状・割当・添付はコピーしない）・候補日と数量は仮・**確定するまで出荷指示・送り状・割当・請求・通知・みなし完了の対象外**（#23・#24 はそのまま有効）。
- 作らない種別でも、**未解決のトラブル報告は要確認に残る**（要確認の区分「トラブル報告（未解決）」を新設）。対応漏れはここで防ぐ。

## 31. 解決に「一部納品（残りは送らない）」を足す

- 数量相違などで、**不足分を送らずに閉じる**解決を追加する。
  - 親：`一部納品済`（実納品数で確定）。**子は作らない**。自動子があれば同じトランザクションで `取消`。
  - 何個までなら送らないかの**しきい値は持たない**。運営が解決のときに選ぶ。**理由は必須**。
- 納品しなかった分は請求しない（実績で請求）。
- 起点は 出荷済／受取済（#21 の一部納品と同じ）。

## 32. 遅延の報告のあとに納品報告が入ったら自動で解決する

- 未解決のトラブル報告が**遅延だけ**の配送に、ドライバーから**全量の納品報告**が入ったら、システムがその遅延の報告を**「全量納品」で自動解決**する（解決者はシステム・監査は `actor_type = system`）。
- 遅延以外の未解決の報告が残っている場合や、納品数が予定と違う場合は自動解決しない（運営が解決する）。
- 当日中に届かなかった遅延は、未解決のトラブル報告として要確認に残る。運営が再配達などで解決する。

## 33. データモデルと API（詳細は DEV §12〜§18）

| 対象 | 変更 |
|---|---|
| `trouble_types`（新設） | `code`（6区分）・`name`・`default_action`・**`auto_child`（boolean）**・`sort_order`・`status`。初期値は #30 の表 |
| `trouble_app_reasons`（新設） | `app_reason_raw` → `type_code`（`NULL`＝種別未定。「商品不足・誤配送」） |
| `trouble_reports` | **`auto_duplicate_due_at` を削除**。`type_code` は `NULL` を許す（種別未定）。`resolution` に `partial_no_resend` を追加。`resolved_by` はシステムも可 |
| `deliveries` | `creation_source` の `trouble_timeout` を **`trouble_auto`** に改称。**`source_trouble_delivery_id`** を追加（トラブルが起きた配送）。一意制約を **`UNIQUE(source_trouble_delivery_id) WHERE creation_source = 'trouble_auto' AND status <> '取消'`** に変更（`UNIQUE(source_trouble_report_id)` は廃止） |
| `review_items.kind` | **`trouble_open`**（未解決のトラブル報告・対象は配送）を追加。`trouble_auto_child_pending` は残す |
| 運用設定 | `trouble_auto_duplicate_after_minutes` を削除 |
| バッチ | `trouble_auto_duplicate` を削除。`delivery_presume_complete`／`delivery_detect_missing` の条件（未解決のトラブル報告が無いもの）はそのまま |
| 遷移 | 追加：`納品済`（`presumed`）→ `再配達待`／`中止`（運営の解決）。`出荷済`／`受取済` → `一部納品済`（`partial_no_resend`・子なし） |
| トランザクション | **トラブル報告の登録＝報告＋（`auto_child` の種別なら）自動子＋要確認2件＋監査**。種別の付け直しで「作る」になったとき＝種別の更新＋自動子＋要確認＋監査 |
