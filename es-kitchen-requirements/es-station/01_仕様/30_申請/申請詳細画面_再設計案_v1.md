## 2. いちばん大きいズレ：「適用開始年月」がなくなったこと

いまのデモは、**申請詳細画面の中で「いつから効かせるか」を決める**作りです。
プラン変更のデモでは、東京本社 2026/11/01・福岡営業所 2026/12/01 と拠点ごとに日付を入れ、それを申請が持っていました。

最新の仕様では、こうなります。

```
プラン変更の申請が来た
  ↓
運営は 拠点情報編集 →「契約」タブ → 子契約の一覧 から
  効かせたいサイクル月の子契約（例 CP0000001-202611）を開く
  ↓
「契約」タブの プランID を変えて保存
  ↓
後ろのサイクルの子契約が生成済みなら、ダイアログが出る
  ┌ この子契約だけ        … 2026年11月サイクルだけ変える
  └ この子契約以降すべて  … 生成元（拠点・親契約・プラン）も更新し、
                            先に作ってある未確定の子契約も直す（確定・請求済は直さない）
  ↓
変更履歴に「2026-11 のみ」／「2026-11 以降すべて」と残る
```

**日付を入れる欄はどこにもありません。**「どの子契約を開いたか」が適用月そのものになります。

このため、変更系を申請詳細画面の中で完結させると、**同じことを2か所で決められる状態**になります。
これは引き継ぎ資料 §4-3「持ち主は1つだけ」に正面からぶつかります。

## 3. 画面の置き場所をどうするか（3案）

### 案A（推奨）　申請詳細画面は「新規申込の受付」だけにする

| | |
|---|---|
| 申請詳細画面が扱う | **新規申込（本導入・お試しキャンペーン）**／**お試し → 本導入の切替** |
| 変更系（プラン変更・休止・解約・再開） | 申請詳細画面では扱わない。**変更申請の承認画面**（小さいもの）で承認 → 実際の変更は拠点・子契約画面で行う |
| 作るデモ | ① 新規申込の受付（切替を含む）　② 変更申請の承認（1画面） |

**そう考える理由**

- 新規は「まだ何もない」→ 作る。変更は「あるものを直す」→ 既にある画面で直す。画面の性格が違います。
- 変更を直す場所は既に `12_運営_法人拠点契約.html` にあります（拠点「契約」タブ・子契約4タブ）。二重に作る必要がありません。
- 承認画面に必要なのは入力欄ではなく、**承認したら何が起きるかの予告**です。具体的には
  - 取り消される**先行子契約の件数**（REQ-CT-232-5）
  - 削除される**納品予定（draft）の件数**
  - 自動で立つ**返却予定日**（停止日＋1ヶ月）
  - **違約金の判定**（設備ごと・合算）

### 案B　いまの6区分・1画面の構成を維持し、中身だけ新モデルに合わせる

| | |
|---|---|
| 利点 | 会議で見せやすい。1本の流れで6区分を比較できる |
| 欠点 | 変更系で「適用開始年月」に代わるものを画面に置くことになり、**子契約の保存ダイアログと二重**になる |
| 折衷 | 変更系は**入力させず、子契約へのリンクだけ**置く（「2026年11月サイクルの子契約を開く →」）。実質は案Aに近づく |

### 案C　申請詳細画面をフェーズ2の対象から外す

項目一覧の6画面（法人・拠点・子契約・機種・オプション・値引き）に申請詳細画面は入っていません。
フェーズ2の実装対象が6画面で確定しているなら、申請詳細画面のデモは**今の版を「フェーズ1の受付フローの記録」として残し、作り直さない**という選択もあります。

### 比較

| | 案A（推奨） | 案B | 案C |
|---|---|---|---|
| 作る量 | 中（2画面） | 大（6区分すべて作り直し） | 小（なし） |
| 最新仕様との整合 | ◎ | △（二重入力の危険） | ○ |
| 「持ち主は1つ」ルール | ◎ | △ | ◎ |
| 会議での見せやすさ | ○ | ◎ | △ |
| 項目一覧への反映 | 申請・承認の項目を足す必要あり | 同左（量が多い） | 不要 |

### 4-1. 画面1　新規申込の受付

申込フォーム1本から、**法人1・拠点3・親契約3・子契約3** が生まれるところを見せます。

**A画面（申込内容の確認）**

| ブロック | 内容 |
|---|---|
| 申請ヘッダー | 申請番号 `AP-20260904-0090`／申請日／申込法人／**契約種別（本導入／お試しキャンペーン）**／対象拠点数 |
| 拠点別の開始スケジュール | 拠点ごとの **契約開始日・最初のサイクル月・A1（月曜）・子契約の生成基準日・初回請求月** を1表で |
| 拠点ごとのアコーディオン | 申込内容（プラン・コース・配送・設備・住所・担当者）。いまのデモと同じ構造を流用 |
| 右サイド | 法人情報・請求条件（**請求先は拠点が持つ**・請求書の発行単位は法人）・申込担当者 |

**B（仮登録の確認モーダル）** — 作られるものを4階層で見せる

```
法人      1件   CU00001   株式会社サンプルフーズ

親契約    3件   CP0000001 / CP0000002 / CP0000003     ← 契約種別＝本導入
子契約    3件   CP0000001-202610 / CP0000002-202610 / CP0000003-202611
                （最初のサイクル分だけ。以降は日次バッチが生成）

```

**C（完了モーダル）** — 上の結果テーブル ＋「次の自動生成：2026-11 を 2026/10/01 に作成予定」

**D（拠点ごとの詳細設定）** — タブは**拠点と子契約に分ける**

| どこ | タブ | この画面で埋めるもの |
|---|---|---|
| 拠点 | 基本情報 | 住所・アプリの利用設定・担当者・アカウント |
| 拠点 | 契約（親契約） | 契約種別・契約開始日・最低利用期間・代理店コード |
| 拠点 | 資料・履歴 | 搬入経路資料（顧客向け／委託業者向け）・設置場所写真 |
| 子契約 | 契約 | プランID・コース・配送ルート設定（配送種別ごと）・納品サイクル |
| 子契約 | 料金・請求 | ① 固定額（前払い）の費目行／② 実績精算（後払い） |
| 子契約 | 設備・オプション | 設備の異動（新規貸出）／オプション・割引の異動 |

**E（確定）** — 拠点単位で確定（前回の決定どおり）。確定すると親契約が「仮登録 → 有効」になります。

### 4-2. 画面2　お試しキャンペーン → 本導入の切替

**新しい親契約番号を採番する**ところが山場です。

```
お試し   CP0000001（契約種別＝お試しキャンペーン）  … 2026/09/30 で終了。履歴として残る
                ↕ 「お試し・本導入の切替（参照）」でお互いを指す
本導入   CP0000012（新規採番）                      … 2026/10/01 開始・最低利用期間はここから数える
```

- 拠点設定（ゲストモード・ES-QR など）は**引き継ぐ**
- プラン・設備は運営が切替時に**設定し直せる**（CSC120 → CSC180）
- 設備の貸出は**拠点が持ち主**なので、親契約が変わっても貸出は続く（冷蔵庫は置きっぱなし）
- 切替は**拠点ごとに個別**

### 4-3. 画面3　変更申請の承認

法人Webから来た変更申請を運営が承認する画面です。**入力はほとんどなく、予告を見せるのが仕事**です。

| 申請 | 承認画面に出すもの | 承認後に起きること |
|---|---|---|
| プラン変更 | 対象の子契約（サイクル月）・変更前後・差額 | その子契約のスナップショットを作り直す。未請求の先行子契約も（適用範囲の選択に従う） |
| 休止 | 休止開始サイクル月・**取り消す先行子契約の件数**・削除する納品予定の件数・**返却予定日**（停止日＋1ヶ月） | 親契約 → 利用休止。未確定の先行子契約を取消。draft を削除 |
| 解約 | 解約日・**違約金の判定（設備ごとの内訳と合算）**・最終請求の①②・回収対象の設備 | 親契約 → 解約手続き中 → 停止。同上 |
| 再開 | 再開サイクル月・**再設置が要る設備**（拠点の貸出一覧から自動判定） | 親契約 → 有効。子契約の生成を再開 |
