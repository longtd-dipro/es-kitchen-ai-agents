### 0-2. v2.0 からの変更（2026/09/21 第2次決定）

v2.0 の時点で、原典どうしの食い違い84件は片づいていた。そのあと出た**第2次決定（11件＋併せて直すこと5件）**を反映したのが本書 v2.1 である。効いたのは次の点。

| | v2.0 まで | **v2.1** |
|---|---|---|
| `locked` の起点 | 2週間分をまとめて出力した時点 | **出荷指示が初めて送信成功した時点だけ。**送り状番号では `locked` にせず、出荷指示より先に送り状が現れたら **anomaly** として検知 |
| みなし完了 | 便種別（委託便）で判断 | **final leg（最終区間）で判断。**ESドライバーアプリ＝みなしにせず翌朝未完了は missing queue／運送会社の直接配達＝みなし完了 |
| 締切後の日付変更 | 運営が1件ずつ・理由は任意 | ~~締切前＝1件でも一括でも／締切後・`locked` 前＝運営だけが1件ずつ・理由必須・要確認のレコード限定／`locked` 後＝取消＋複製~~　**→ 2026/09/22 第3次決定で「締切後は変更しない」に再改定（0-2B）** |
| 複製 | `draft` からもできる | **`draft` からは不可。**`draft` は「予定のコピー／変更」だけ。複製は `published`／`locked` から |
| 予定の一意キー | (契約ID, 納品日) | **`contract_id`＋`line_no`＋`channel_id`＋`cycle_id`＋`occurrence_key`** |
| 便の軸 | 便種別は契約が持つ | **3軸：`delivery_regime`（self／partner_driver／parcel_carrier）を新設、`service_form` は配送区分に置く、relay は route legs から導出（保存しない）** |
| 受取時間帯 | from/to を1組 | **子テーブル `site_receive_windows` ＋ `delivery_receive_windows` へスナップショット** |
| 仮の締切 | 制限なし | **`marker_source=provisional` では数量確定・確定メール・出荷指示を走らせない** |
| 支払期限 | 1枚の請求書に前払い／実績精算 | **請求書を `billing_type`／`payment_due_date` で分ける。1請求書＝1支払期限** |
| サイクル月 | 日数が多い月（14対14 は未決） | **14番目の枠 `B7` が属する月。**同じ結果になり、14対14 では自動的に前の月。例外分岐は作らない |
| 倉庫ロール | 「ロールは設けない」 | **`倉庫管理者` を完全に削除。**倉庫タブはデータの絞り込みでしかない |
| 予定の数量 | 「予定は数量を持たない」と読めた | **`shipping_plans.estimated_qty` を内部に持つ。**`draft` で法人に見せないだけ |
| 状態 | まとめて「ステータス」 | **2つの状態機械に分ける**：`plan lifecycle`（draft／published／locked）と `delivery status`（出荷待〜納品済） |

反映の作法として、**1つの規則につき ①業務の説明 ②state／batch の表 ③データモデル の3か所を同時に直す**ことを決めた。先頭だけ直って末尾が古い論理のまま、という事故を防ぐため。

- 3か所：①§9・§12 ②権限表 ③ロール定義。

#### 3. `locked` の起点

- **トリガーは1つだけ：出荷指示が初めて送信成功した時点。**
- **送り状番号が付いても `locked` にはしない。**
- 出荷指示より先に送り状番号が現れたら **anomaly（異常）として検知・通知**する。
- 〔上書き〕第1次の「`locked` の起点＝2週間分をまとめて開始の3日前（金）に出力した時点」は、**出力ではなく“送信成功”が起点**という形に改める（2週間まとめ出力は「いつ送るか」の話として残す）。
- 3か所：①§8-2・§10-1 ②状態遷移・バッチ条件 ③`deliveries.locked_at` と出荷指示ログ。

#### 4. みなし完了と欠配（final leg で判断する）

| final leg（最終区間）の運び手 | 完了の扱い | 欠配の扱い |
|---|---|---|
| **ES のドライバーアプリ** | **みなし完了にしない** | 翌朝になっても完了していなければ **missing queue（要確認）へ** |
| **運送会社が直接配達** | **みなし完了にする** | 顧客・配送会社から異常の連絡があったときだけ **確認中** へ落とす **（2026/09/24 追補で変更：状態は変えず、トラブル報告と要確認を開く〔決定v2.3 #20〕）** |

#### 5. draft からの複製

- **draft から配送データを複製できない。** draft でできるのは **「予定のコピー／変更」だけ**。
- `parent_delivery_id`・枝番・状態 **確認中** を伴う **複製は `published` か `locked` からのみ**。
- 〔上書き〕第1次の「複製は `draft` / `published` / `locked` のいずれからでも実行できる」は **取消**。
- 3か所：①§8-3 ②状態遷移表 ③`parent_delivery_id` の制約。

#### 6. 予定（plan）の一意キー

- **`contract_id` + `line_no` + `channel_id` + `cycle_id` + `occurrence_key`** をキーにする。
- **`(contract_id, delivery_date)` は使わない。** 1契約が同じ日に複数の温度帯・配送区分を持ちうるため。
- 〔上書き〕REQ-DL-721 の「納品予定は (契約ID, 納品日) で一意」は **取消**。
- 3か所：①§7-2 ②再生成（置換）の条件 ③`shipping_plans` の一意制約。

#### 7. 便の3軸

- **`delivery_regime` を追加**：`self`（自社）／`partner_driver`（委託ドライバー）／`parcel_carrier`（運送会社）。
- **`service_form`（便種別＝COOL便／ES配送便）は配送区分（delivery channel）に置く。契約のルートには置かない。**
- **`relay`（中継）は route legs から導出する。状態としては保存しない。**
- 〔上書き〕第1次 #29「便種別は契約（子契約）が持つ入力項目」は、**持ち場を「配送区分」に限定**する形へ。中継の有無から導出しない点は変わらない。
- 3か所：①§5-3・§11-1 ②便種別による分岐 ③`delivery_channels` の列・`delivery_legs`。

#### 8. 受取時間帯が複数あるとき

- 子テーブル **`site_receive_windows(site_id, from_time, to_time, sort_order)`** を作る。
- 配送データを作るときに**リストごとスナップショット**する（`delivery_receive_windows`）。
- **from/to を1組だけ持つ形にしない。**
- 〔上書き〕第1次 #22「受取時間帯を項目として持つ」を、**子テーブル方式**に具体化。
- 3か所：①§5-5・§12-2 ②スナップショットのタイミング ③2つのテーブル。

- 3か所：①§4-3・§7-4 ②バッチの発火条件 ③`delivery_cycles.marker_source`。

#### 10. 支払期限（入金期限）

- **請求書を `billing_type` または `payment_due_date` で分ける。**
