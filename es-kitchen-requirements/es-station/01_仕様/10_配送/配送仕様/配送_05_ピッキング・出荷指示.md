## 9. ピッキング

### 9-1. ピッキングの位置づけ

ピッキング日は独立した暦を持たない。**配送サイクルの枠の中で、納品日から逆算して決まる。**

| 項目 | 内容 | 出典 |
|---|---|---|
| サイクルの本数 | **サイクルは1本。** 出荷専用のサイクルを別に持たず、出荷不可も納品と同じ `A1`〜`D7` のグリッドで持つ | 〔サイクル §2.3〕〔要件 REQ-DL-804〕 |
| 枠の単位 | **28スロット＝4週（A〜D）× 7日**（`A1`〜`D7`）。スロットは「週 × 曜日」で読む（`A6`＝週Aの土曜） | 〔サイクル §2.3・§4.2〕〔要件 REQ-DL-501・REQ-DL-632〕 |
| ピッキング日の決まり方 | **納品日から契約の配送区分のリードタイム分を逆算**する。`ピッキング日 = 納品日 − リードタイム` | 〔サイクル §4.4〕〔要件 REQ-DL-101〕 |
| 判定の軸 | **ピッキングする日そのものが属する枠**で出荷不可を判定する（納品日の枠から逆に決めない） | 〔サイクル §2.3 `isPickClosed`〕〔要件 REQ-DL-804〕 |
| サイクル初日 | `A1` は**月曜固定**。月曜以外を入力したら直前の月曜へ丸める | 〔サイクル §2.3〕〔要件 REQ-DL-614〕 |
| サイクル月 | **14番目の枠 `B7` が属する月**。「28日のうち日数が多い月」と同じ結果になり、14対14 のときは自動的に前の月になる。**例外の分岐は作らない** | 〔決定v2.1 #11〕〔要件 REQ-DL-881・REQ-DL-864〕 |
| リードタイムの持ち主 | **契約の配送区分（冷蔵／冷凍／資材）ごと**。**倉庫マスタは持たない**。既定値の自動補完もしない。範囲は **0〜7日** | 〔決定 #10／#16／#52・#4〕〔要件 REQ-DL-831・REQ-DL-832・REQ-DL-627〕 |
| 中継があるとき | リードタイムは**合計1つが正**。中継分は参考値として表示するだけで逆算には使わない | 〔決定 #21〕〔要件 REQ-DL-837〕 |

- **週単位の設定方式（「第1週の水曜日」・A週／B週＋日単位）は廃止した。** サイクル枠の選択方式へ移している〔要件 §8E-1・REQ-DL-501〕。
- 既定の出荷不可枠は **`A6`・`A7` ／ `B4`〜`B7` ／ `C6`・`C7` ／ `D4`〜`D7`**。**土曜・日曜は既定値であって固定値ではない**ので、画面・判定のどこでも曜日から決め打ちしない〔サイクル §2.3・§5.3〕〔要件 REQ-DL-818〕。
- **B週・D週に木・金まで出荷しないのは、その週の配送件数が少なく倉庫が隔週で休んでいるため。** 曜日ではなく週×曜日で持つのは、この隔週の休みを表すためである〔サイクル §2.3〕。

### 9-2. ピッキング倉庫 — 倉庫のロールは存在しない

**`倉庫管理者` というロールは存在しない。倉庫の操作はすべて運営（物流）が行う。**〔決定v2.1 #2〕〔要件 REQ-DL-885・REQ-DL-680〕

| 論点 | 決定 | 出典 |
|---|---|---|
| 倉庫ロール | **完全に削除する。** ピッキング完了の登録・出荷不可日の登録・ピッキングスケジュール（画面04）の閲覧を含め、**すべて運営（物流）**が行う | 〔決定v2.1 #2〕〔要件 REQ-DL-885〕 |
| 倉庫タブ | **データの絞り込みでしかなく、権限の単位ではない。** タブを切り替えても操作できる範囲は変わらない | 〔決定v2.1 #2〕〔要件 REQ-DL-623・REQ-DL-885〕〔サイクル §5.2〕 |
| 理由 | **倉庫にはシステム内の画面がない。** 倉庫への指示は出荷指示CSVで渡るため、倉庫側がログインする画面を持たない | 〔要件 §8H-7B〕〔サイクル §2.3〕 |
| 倉庫の担当者 | 倉庫マスタの担当者（メイン／サブ）は**運営が手動で設定**する。**必須ではない**。ログインの主体ではなく連絡先である | 〔要件 §8G-6・§8H-7B〕〔サイクル §2.3A〕 |
| 権限表・日付変更モードの表 | **倉庫管理者の列を削除する** | 〔決定v2.1 #2〕〔要件 REQ-DL-885〕 |

倉庫そのものの整理は次のとおり。

| 項目 | 内容 | 出典 |
|---|---|---|
| 拠点数 | **基本2拠点（関東・関西）**。今後増える可能性はある | 〔要件 §8H-1〕 |
| 倉庫の決まり方 | **商品ごとに出る倉庫が決まる**（商品 × 倉庫は多対多。関東専用・関西専用の商品がある） | 〔要件 §8H-5・REQ-DL-675／676〕 |
| 契約での持ち方 | 契約は**配送区分（温度帯または資材 × 倉庫 × 配送会社〈1次・中継・2次〉）**の一覧を持つ | 〔要件 REQ-DL-626〕〔サイクル §3.1B〕 |
| 代替倉庫 | **持たない。** 割当倉庫が出荷不可でも自動で別倉庫へ振り替えず「要確認」として運営が判断する | 〔要件 REQ-DL-629〕〔サイクル §2.3〕 |
| 別倉庫から出すとき | 契約の配送区分で倉庫を変更するか、配送データを複製して倉庫を変える。**複製できるのは `published` か `locked` の配送データからだけで、`draft` からは複製できない** | 〔決定v2.1 #5〕〔要件 REQ-DL-872〕 |
| 倉庫変更の適用 | **適用月から**。適用月の単位は**サイクル月**で、切り替わるのは**そのサイクルの `A1` から**（暦月の1日ではない） | 〔サイクル §2.3・§4A-6〕〔要件 REQ-DL-630〕 |
| 倉庫マスタが持つもの | ピッキング倉庫専用は**倉庫コード・件数しきい値・出荷指示リードタイム・連携**だけ。**リードタイム（エリア別を含む）は持たない** | 〔要件 REQ-DL-628・REQ-DL-666・REQ-DL-831〕〔サイクル §2.3A〕 |
| 出荷不可枠・日別の出荷不可日 | **配送サイクル設定（画面01）の倉庫タブ**で管理する。倉庫マスタでは編集させない | 〔要件 REQ-DL-686〕〔サイクル §2.3〕 |
| 対応温度帯 | 倉庫マスタは**持たない**。商品の取扱倉庫から導出し、配送区分では「その倉庫でその温度帯の商品を1件以上扱っているか」で判定して0件なら警告する | 〔要件 REQ-DL-668〕〔サイクル §2.3A・§2.3C〕 |

- 同じ契約の冷凍と冷蔵を別倉庫から出すことは**なくはない**ため、配送区分 × 倉庫の構造は維持する〔要件 §8H-1〕。
- **倉庫ごとに定休日・稼働曜日が違う**ため、出荷不可枠は倉庫別に持つ。日別の不可日（棚卸し・設備点検）も倉庫ごとで、ある倉庫の棚卸し日が他の倉庫のピッキングを止めることはない〔要件 §8H-1〕〔サイクル §2.3〕。

### 9-3. 件数しきい値とアラート

**食数ではなく「件数」で判定する。資材は含めない。**〔要件 REQ-DL-616・REQ-DL-818〕〔サイクル §5.2〕

| 項目 | 内容 | 出典 |
|---|---|---|
| 判定単位 | **件数**（食数・プラン数ではない） | 〔要件 REQ-DL-616〕〔サイクル §5.2〕 |
| しきい値の持ち主 | **倉庫マスタ**（日付と関係ない倉庫の能力値のため）。**倉庫ごと**に設定する | 〔要件 REQ-DL-623・REQ-DL-628〕〔サイクル §2.3A〕 |
| 初期値 | **300件／日**（1日の処理件数が300件程度のため）〈旧：150件／日〉 | 〔要件 REQ-DL-616・REQ-DL-671・§8H-3〕〔サイクル §5.2〕 |
| 表示の単位 | **倉庫タブごと**に当月件数と超過日数を出す。タブは絞り込みであって権限ではない（→ 9-2） | 〔要件 REQ-DL-623〕〔決定v2.1 #2〕 |
| 超えたとき | **アラート表示のみ。システムは何もしない。** 運営が手動で日付を調整する（処理は止めない） | 〔要件 REQ-DL-616・§8H-3〕〔サイクル §5.2〕 |
| 資材配送 | **件数に含めない**（倉庫からヤマトへ直送で、ピッキングの手間が食材と同じではないため）。件数表示・超過判定のいずれからも除外し、**資材の行は一覧には出すが件数には数えない** | 〔要件 REQ-DL-818〕〔サイクル §5.2〕 |
| 人員・車両 | **システムでは扱わない** | 〔要件 §8H-3〕 |

- しきい値は**警告の線であって上限ではない**。超えても出荷指示・確定生成は止まらない〔要件 REQ-DL-616〕。
- ピッキング日を手動で移動した結果、移動後のピッキング日＋リードタイムから計算した配送日が顧客希望日より遅くなる場合は、**画面上でアラートを出すだけで処理は止めない**〔要件 REQ-DL-105〕。

### 9-4. ピッキングリスト

**管理画面での確認のみ。PDF出力は作らない。**〔決定 #50〕〔要件 REQ-DL-850・REQ-DL-318〕〔サイクル §5.2〕

| 項目 | 内容 | 出典 |
|---|---|---|
| 出力の形 | **画面04と日別一覧モーダルで確認する。PDF出力は作らない**（REQ-DL-103 の「PDFで自動作成」は**取消**） | 〔決定 #50〕〔要件 REQ-DL-850・REQ-DL-103〕 |
| 画面から取れるもの | **CSV出力まで**（日別一覧モーダルのCSV出力） | 〔サイクル §5.2・付録A-2〕 |
| 紙を出さない理由 | 倉庫への指示は**トーマスへの出荷指示CSV**で渡るため、紙のリストをシステムから出す必要がない | 〔サイクル §5.2・§4D-3〕〔要件 §8C-8〕 |
| 食材と資材 | **別管理・別ピッキング。** 資材は食材と別リストにする | 〔要件 §2-2〕 |
| 冷凍と冷蔵 | **ピッキングおよび出荷指示を別々に行う**（→ 10-6） | 〔要件 REQ-DL-301・§8C-1〕 |
| 絞り込み | **荷物区分（冷蔵／資材）**・**発送予定日（期間指定）** | 〔要件 REQ-DL-103・§2-2〕 |
| 表示単位 | 件数は**プラン数ではなくアイテム数**。ピッキング予定は1カードとして表示 | 〔要件 REQ-DL-104・§2-2〕 |
| ピッキングの進み | **完了／未完了を色分け**表示する | 〔要件 REQ-DL-104〕 |

**短消費期限の分割**

- **分割するかどうかはシステムは自動判定しない。運営が判断する。** 分割後は**別レコード**として扱う〔要件 REQ-DL-618・REQ-DL-624〕。
- **ただし「短消費期限を含む」ことはシステムが知らせる**〔決定v2.3 #35〕：**出荷日から納品日までの日数 ＞ 商品の消費期限日数（`products.shelf_life_days`）− 安全日数** の商品を含む配送（または予定）を、要確認 **`shelf_life_warning`** に出す。安全日数は**全社共通の運用設定1つ**（`shelf_life_safety_days`・**既定2日**）。判定するのは**予定の生成・再計算**（振替でリードタイムが伸びたとき）、**倉庫の変更**、**複製**のとき。自動で分割はしない（旧：条件が未決〈§18 No.6〉。2026/09/29 解消）。
- **受付締切は「オーダー期間の締切」に合わせる**〔要件 REQ-DL-624〕。
- このため**リードタイム差を優先する**。納品日の移動量に上限は置かず、本来の枠から3日を超えて動いた場合に要確認へ出す〔要件 REQ-DL-806〕。
- 不可・振替・要確認には**理由を必ず併記**する（納品祝日扱い／納品不可曜日／出荷不可枠・出荷不可日／サイクル休止／保管量）〔要件 REQ-DL-617〕。

### 9-5. 画面04 ピッキングスケジュール（運営が見る画面）

**見るのも日付を動かすのも運営（物流）である。**〔決定v2.1 #2〕〔要件 REQ-DL-885〕〔サイクル §5.2〕

| 項目 | 内容 | 出典 |
|---|---|---|
| 主担当 | **運営管理者（物流）。** 倉庫ロールは存在しないため、この画面に倉庫側のユーザーは現れない | 〔決定v2.1 #2〕〔要件 REQ-DL-885・§8H-7B〕 |
| 集計の軸 | 月次カレンダー（7列）を**ピッキング日**で集計 | 〔サイクル §5.2〕 |
| 絞り込み | **倉庫タブ**で切り替える（拠点ごとに割当倉庫が異なり、倉庫をまたぐと不可日の理由が読み取れないため）。**タブは絞り込みであって権限の単位ではない** | 〔決定v2.1 #2〕〔要件 REQ-DL-623〕〔サイクル §5.2〕 |
| 不可の表示 | 出荷不可日は**紫の破線枠**（`出荷不可`）、休止期間は**黄**（`休止`）。**不可のセルには理由を表示する** | 〔サイクル §5.2〕〔要件 REQ-DL-617〕 |
| 理由の長さ | **セルは短く**（`B1 月（納品不可）`）、**詳細はツールチップ**で出荷不可枠・倉庫名・リードタイムを出す | 〔決定 #23〕〔要件 REQ-DL-847〕 |
| 振替の文言 | **一覧は短く**（`前倒し 2日`）、**詳細画面・ツールチップはフルに**（`本来 B3（2026-09-17）から 2日 動いています`） | 〔決定 #27〕〔要件 REQ-DL-846〕 |
| 納品祝日扱い日 | **ピッキングは可能** | 〔サイクル §5.2〕 |
| 件数警告 | しきい値を超えた日を枠線と件数で示す（→ 9-3） | 〔要件 REQ-DL-616・REQ-DL-623〕 |
| 日付を動かせる範囲 | **スケジュール画面からはオーダー締切前だけ。** 締切後〜出荷日の前日は配送データ詳細の「編集」から運営が1件ずつ・理由必須・同じサイクルの同じ前半／後半で変更できる（8-3）〔決定v2.3 #63〕（旧：締切後はスケジュール画面・配送データ詳細のどちらからも日付を変更できない。2026-10-03 台帳に合わせて修正） | 〔決定v2.2 #1〕〔要件 REQ-DL-865・REQ-DL-886〕 |
| オーダー締切後 | **出荷日の前日までは1件ずつ変更できる（上の行）。出荷日の当日以降は取消＋複製**（`locked` の前後で扱いを分けない）〔決定v2.3 #63〕（旧：日付は変更しない。取消＋複製で対応する。2026-10-03 台帳に合わせて修正） | 〔決定v2.2 #1〕〔要件 REQ-DL-866〕 |

- 画面05（納品スケジュール）は**同じデータを納品日で集計した別ビュー**。出荷（ピッキング）と納品でカレンダーを分ける〔要件 REQ-DL-308〕〔サイクル §5.3〕。
- **日曜・土曜を固定の「出荷不可」「受取不可」として描かない。** どの表示でも、その倉庫の出荷不可枠とその契約の納品不可曜日を見て判定する〔要件 REQ-DL-818〕〔サイクル §5.3〕。

### 9-6. 出荷不可との関係

**出荷不可日に当たったら、ピッキング日・納品日の両方を振り替える。**〔決定 #15〕〔要件 REQ-DL-842・REQ-DL-689〕〔サイクル §4A-5B・§4.4〕

「止まるのはピッキングだけで納品日は動かさない」という旧来の整理は取消した。**出荷不可日も納品日の振替対象**に含める。

| 順 | 手順 | 結果 | 出典 |
|---|---|---|---|
| ① | まず**ピッキング日だけを前倒し**して、契約リードタイムの**差0**で収まるか見る | 収まればここで終わり（例：ピッキング 8/19→8/18／納品 8/21 のまま） | 〔要件 REQ-DL-824〕〔サイクル §4.4〕 |
| ② | 差0で収まらなければ、**納品日を契約の「前倒す・後ろ倒す」へ動かし**、ピッキング日と納品日の**両方を振り替える** | 例：ピッキング 8/18／納品 8/20 | 〔決定 #15〕〔要件 REQ-DL-842〕〔サイクル §4A-5B〕 |
| ③ | ②でも差0の日が無ければ **＋1日まで許容**（「やむを得ず＋1日（許容内）」と印を残して自動確定してよい） | 黄ピル | 〔要件 REQ-DL-824〕〔サイクル §4.4〕 |
| ④ | ③も無ければ差が**いちばん小さい**組を採って**要確認** | 赤ピル `実 N日（契約 M日・＋K日）` | 〔要件 REQ-DL-824〕〔サイクル §4.5〕 |
| ⑤ | **20日以内に納品できる日が1つも見つからない**ときは **「予定生成不可」として要確認に出す。自動で日付を決めない** | 対象の契約・拠点・サイクル・理由を添える | 〔決定 #19〕〔要件 REQ-DL-843〕 |

**`plan lifecycle` ごとの扱い**（`delivery status` とは別の軸。→ 10-2）

| `plan lifecycle` | 出荷不可日を途中で追加・変更したときの扱い | 出典 |
|---|---|---|
| `draft`（オーバーライドなし） | **自動で前倒し。** 法人カレンダーの表示も自動で更新する | 〔要件 REQ-DL-689〕〔サイクル §4A-5B〕 |
| `draft`（承認済みオーバーライドあり） | まずピッキング日だけを前倒し。納品日も動かす必要がある場合は自動では動かさず**「提案中」** | 〔要件 REQ-DL-612〕〔サイクル §4A-5B〕 |
| `published` | **動かさない。**「要確認」に出し、運営が対応する。不可日を解除しても自動では戻さない | 〔要件 REQ-DL-689〕〔サイクル §4A-5B〕 |
| `locked` | **対象外。** すでに出荷指示を送信済みのため、電話連絡＋取消、または複製で処理する | 〔要件 REQ-DL-689・REQ-DL-866〕〔サイクル §4A-5B〕 |

- **ピッキング日は常に前倒しで探す。** 後ろにずらすと納品に間に合わないため。1日を超えるときはピッキング日ではなく**納品日を動かす**〔サイクル §4.4〕。
- **サイクル休止との違い**：休止日はスロットを割り当てず**枠も消費しない**（納品もピッキングもしない）。出荷不可日は枠を消費したまま出荷だけが止まる〔要件 REQ-DL-807〕〔サイクル §2.2・§4.2〕。
- **休止明けに再開した枠は、休止より前に戻さない。** 枠が休止でずれた回に限り、祝日・納品不可曜日の振替は**後倒しだけ**で探す〔要件 REQ-DL-825〕。
- 保存前に**影響件数をプレビュー**する（自動で作り直す `draft`／自動でピッキング日を前倒し／承認済みオーバーライドの適用・失効・提案中／**すでに出荷指示済み〈`locked`・変更不可〉**／前倒しできない）〔要件 REQ-DL-688・REQ-DL-724〕〔サイクル §4A-5B〕。

### 9-7. 廃棄・残数

| 事象 | 扱い | 出典 |
|---|---|---|

### 10-2. `locked` の起点 — 出荷指示の初回送信成功だけ

**`locked` になるトリガーは1つだけ。出荷指示が初めて送信成功した時点である。**〔決定v2.1 #3〕〔要件 REQ-DL-867〕〔サイクル §4A-3・§4D-3〕

ここでいう `locked` は **`plan lifecycle`**（`draft` / `published` / `locked`）の値であり、**`delivery status`**（出荷待／出荷済／受取済／納品済／一部納品済／再配達待／確認中／中止／取消）とは別の軸である。1件の配送データは両方の値を同時に持つ（例：`lifecycle = locked` かつ `delivery status = 受取済`）。**2つをまとめて「ステータス」と呼ばない**〔決定v2.1 S5〕〔要件 REQ-DL-883〕〔サイクル §4A-3・§4A-3B〕。

| # | イベント | `ship_orders` の記録 | `plan lifecycle` | 出典 |
|---|---|---|---|---|
| 1 | 出荷指示CSVを**出力した**（ファイルを作っただけ） | `send_status = pending` | **`published` のまま。`locked` にしない** | 〔決定v2.1 #3〕〔要件 REQ-DL-867〕 |
| 2 | **初回の送信が成功した**（トーマスが受領した） | `send_status = ok`／`sent_ok_at` を記録 | **`published` → `locked`（唯一のトリガー）** | 〔決定v2.1 #3〕〔要件 REQ-DL-867〕〔サイクル §4A-3〕 |
| 3 | **送信に失敗した** | `send_status = failed` | **`published` のまま。** 再送で成功するまで `locked` にしない | 〔決定v2.1 #3〕〔サイクル §4A-3・§7〕 |
| 4 | **再送した**（`rev` を上げる） | 新しい `rev` で記録 | **`locked` のまま。起点（`locked_at`）は動かさない** | 〔要件 REQ-DL-867・REQ-DL-662〕〔サイクル §4D-3〕 |
| 5 | **中止を数量0で再送した** | `is_zeroed = true` | **`locked` のまま**（→ 10-3） | 〔要件 REQ-DL-662〕〔サイクル §4D-3〕 |
| 6 | **送り状番号が付いた**（出荷指示の送信成功記録あり） | — | **変わらない。送り状番号では `locked` にしない** | 〔決定v2.1 #3〕〔要件 REQ-DL-867〕 |
| 7 | **送り状番号が付いた**（送信成功記録が無い） | — | **`locked` にしない。anomaly（異常）として検知・通知し要確認へ出す** | 〔決定v2.1 #3〕〔要件 REQ-DL-868〕 |

### 10-8. ヤマトへ渡す項目・受け取る項目

〔ルート案メモ §3B〕から取り込んだ（2026/09/23。元の論点メモは `99_過去/` へ移動した）。**項目そのものはヤマトの確認待ち**で、**2026/09/29 追補4 で暫定案を決めて実装を進める**ことにした（§18 No.19 は「暫定」）〔決定v2.3 #46〕：①営業所止めの宛名＝**受け取りに行く委託配送会社**、記事欄に拠点名と配送No ②お届け予定日＝**営業所に着く日**（1次のリードタイムの参考値から出す） ③トーマスのCSVに欄が無ければ**送り状用のCSVを別に出す**。
