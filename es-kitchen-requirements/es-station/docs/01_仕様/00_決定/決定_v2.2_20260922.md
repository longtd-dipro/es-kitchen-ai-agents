## 1. オーダー締切後の日付変更 — **不可に統一**

| 段階 | できること |
|---|---|
| **締切前** | 運営が1件でも一括でも変更できる |
| **締切後** | **日付は変更しない。** 取消＋複製で対応する |

- 〔上書き〕**決定v2.1 #1 の「締切後・`locked` 前は運営だけが1件ずつ・理由必須・要確認のレコード限定で変更できる」を取消。**
- 区切りは **オーダー締切ただ1つ**。`locked` は出荷指示の節目であって、日付変更の節目ではなくなる。
- これにより §18 No.2（件数が多いとき運営の手が回るか）は**解消**。
- 3か所：①§9-2 ②§15-4 の guard・権限表から「締切後・lock前」の行を削除 ③`deliveries` の変更可否条件。

## 2. 調整日（`adjust`）の作り方 — **自動で入れない**

- サイクル休止の1回あたりの停止日数は **7の倍数でなければならない**（でないと次サイクルの A1 が月曜にならない）。
- 足りないときは、**システムは不足日数 `7 − (停止日数 mod 7)` を算出して表示するだけ**。**自動では挿入しない。**
- **置き場所は管理者が決める** — 休止の直後・その週の中・月末にまとめる、など**ケースバイケース**。あとから編集できる。
- 7の倍数に満たない状態では**保存できない**。
- `adjust` は `adjust_for_pause_id` でどの休止の埋め合わせかを持つ。
- 〔上書き〕2026/09/19 の「`7 − (pause_days mod 7)` 日の調整を休止の直後に自動で挿入する」を**取消**。
- これにより §18 No.4（調整で止まる日に出荷したいとき）も**解消**：その日に出荷したいなら、管理者が `adjust` を別の日へ動かす。
- 3か所：①§5-2 ②§15-3 の保存 guard ③`delivery_cycle_pauses.adjust_for_pause_id`。

## 3. 出荷指示の後の変更 — **できる**

| 変えるもの | 扱い |
|---|---|
| 配送会社②・配送スタッフ | そのまま変更できる。`ship_order_diff` を立てて再送 |
| **納品先の住所** | 変更できる。ただし**新しい版の出荷指示を出し、既存の送り状を `voided` にして再発行する** |
| ピッキング倉庫 | **変更しない。** 取消＋複製 |
| 納品日 | **変更しない**（上記1） |

- 理由：急な変更は実際に起きる。住所は送り状に印字済みなので、データだけ直すと現物と食い違う。
- 3か所：①§15-14（新設） ②§19-2 の再送ルール ③`delivery_tracking_numbers.status(active|voided)` を追加。

## 4. 出荷指示の再送期限 — **倉庫のピッキング開始時刻では区切らない**

- 再送は **その配送の出荷実績を受け取るまで**できる。受け取ったら締める。
- 倉庫のピッキング開始時刻はシステムでは持たない（そこまでは見ない）。
- 請求の締め日は既定どおり **実際の納品日の暦月**なので、あらためて決める必要はない。
- これにより §18 No.22 は**解消**。
- 3か所：①§10-3 ②§15-7 の guard ③（新しい列は不要）。

## 5. 同一Slotの重複割当 — **現行どおり**

- 同じ契約で2つの配送が同じ枠（Slot）に当たっても**問題にしない**。**警告タグを出して保存できる**（現行の挙動のまま）。
- 〔取消〕§18 No.21 に書いた提案「同一Slot＋同一配送区分はエラー」は**採らない**。
- 技術的にも支障なし：予定の一意キーは `contract_id + line_no + channel_id + cycle_id + occurrence_key`（決定v2.1 #6）なので、同じ枠の2件は別レコードとして成立する。
- 3か所：①契約の配送回数設定画面の仕様 ②（バッチ条件に変更なし） ③`contract_delivery_lines` にコメントを追記。

## 6. 「変更申請（未処理）」の件数バッジ — **期限が来た未処理だけ数える**

- バッジは **処理期限が来ていて、まだ処理していない件数**だけを数える。
- 総件数は一覧画面で見る。
- 画面まわりの話なので DEV 仕様書には入れない。**異論があれば差し替える。**
