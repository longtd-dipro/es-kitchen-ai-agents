## 20. トラブル報告で親の状態を変えない

- 親は**トラブル発生時の状態のまま**：`出荷済` または `受取済`。**納品後の連絡（クレーム）は `納品済` のまま**。トラブル報告を記録し、要確認を開く。
- 〔上書き〕「出荷済／受取済 → 確認中（トラブル報告）」「納品済 → 確認中（納品後の連絡）」を廃止。
- **`確認中` はトラブルの流れでは、未出荷（`shipped_date IS NULL`）の子・リカバリ候補だけが使う。**
- 最終状態は従来どおり `納品済`／`一部納品済`／`再配達待`／`中止`／`取消`。納品後の連絡は要確認を開くが、`納品済` を `確認中` に戻さない。

## 21. 運営（物流）が親を直接解決する

バッチは親の解決方法を決めない。**解決するのは運営（物流）**。自動子（#22）がある場合は同じトランザクションで扱う。

| 解決 | 親 | 自動子の扱い |
|---|---|---|
| 全量納品／代替品で全量 | `納品済` | `取消`（理由 `auto child not needed`） |
| 一部納品 | `一部納品済` | **使い回す**：`duplicate_type=remainder`、数量・明細＝残数 |
| 全量を再配達 | `再配達待` | **使い回す**：`duplicate_type=redelivery`、数量・明細＝全量 |
| 当日中に再訪 | `受取済` | `取消` |
| 納品しない | `中止` | `取消` |

- 起点：一部納品・再配達・中止・当日再訪は `出荷済`／`受取済` から。全量納品は `出荷済`／`受取済`／`納品済` から。
- **自動子があるのに2件目の子は作らない。** 手動の複製 API も、そのトラブルに子があれば使い回し、2件目は拒否する（`DOMAIN_TROUBLE_CHILD_EXISTS`）。
- 自動子がなければ、一部納品・再配達では従来どおり複製で子を作る。

## 22. 期限までに解決されないトラブルは自動子を作る

- `auto_duplicate_due_at = reported_at + trouble_auto_duplicate_after_minutes`。**SLA（分）は運用設定で必須、バッチにハードコードしない**。時刻は他の業務マイルストーンと同じく UTC。
- 条件：正式なトラブル報告がある／親が `出荷済`・`受取済`・`納品済`／報告が未解決／`auto_duplicate_due_at` を過ぎた／その報告の子がまだない。**配送が未完了というだけでは作らない。**
- 自動子：`確認中`、`duplicate_type=trouble_pending`、`creation_source=trouble_timeout`、`schedule_confirmed=false`、`quantity_confirmed=false`。
- 複製と同じく納品先スナップショット・納品条件・受取時間帯・`delivery_legs` 全部をコピー。送り状・割当・添付はコピーしない。親子1階層・枝番 1〜9 を守る。
- 候補日は**表示用の仮**。数量は**再送しうる最大量の仮**で、出荷・請求には使わない。
- **1つのトラブル報告に子は最大1件**。バッチの再試行は `source_trouble_report_id` で UPSERT／冪等。
- 要確認 `review_items.kind = trouble_auto_child_pending`（対象は子）を作る・更新する。

## 23. 確定前の自動子は何にも参加しない

`trouble_pending` の子は、運営が確定するまで **出荷指示・送り状・ドライバー割当・請求・通知・みなし完了** の対象外。

- 出荷指示の送信条件に追加：`schedule_confirmed=true` かつ `quantity_confirmed=true`、未解決の `duplicate_type=trouble_pending` がないこと。

## 24. 自動子を `出荷待` へ進める条件

- 運営（物流）が親のトラブルの解決と数量・納品日を確定し、`quantity_confirmed=true`・`schedule_confirmed=true` にしたときだけ `確認中 → 出荷待`。未確定なら `DOMAIN_TROUBLE_CHILD_UNCONFIRMED`。
- 再送が要らない解決（#21 の表）では、同じトランザクションで自動子を `確認中 → 取消`（理由必須）。
- 解決時に要確認 `trouble_auto_child_pending` も同じトランザクションで閉じる。

## 25. バッチ

- **新設 `trouble_auto_duplicate`**（DEV §16.8.1）。本線のジョブチェーンとは独立。**同じ業務日時では `delivery_presume_complete`／`delivery_detect_missing` より前に流す。**
- `delivery_presume_complete`：`status = 出荷済` かつ **未解決のトラブル報告がない**もの（final leg が `parcel_carrier`）。
- `delivery_detect_missing`：`status IN (出荷済, 受取済)` かつ **未解決のトラブル報告がない**もの（final leg が `self`／`partner_driver`）。

## 26. データモデル（詳細は DEV §14）

| テーブル | 追加 |
|---|---|
| `deliveries` | `duplicate_type(remainder｜redelivery｜alternative｜trouble_pending) NULL`、`creation_source(materialize｜ops_duplicate｜trouble_timeout)`、`source_trouble_report_id NULL`、`schedule_confirmed`、`quantity_confirmed`。**`UNIQUE(source_trouble_report_id) WHERE source_trouble_report_id IS NOT NULL`** |
| `trouble_reports` | `auto_duplicate_due_at` |
| `review_items.kind` | `trouble_auto_child_pending` |
| エラーコード | `DOMAIN_TROUBLE_CHILD_EXISTS`、`DOMAIN_TROUBLE_CHILD_UNCONFIRMED` |

- 通常の確定生成は `creation_source=materialize`・`schedule_confirmed=true`・`quantity_confirmed` は数量確定で true。
- トランザクション：自動子の作成＝トラブル報告＋親のロック＋子＋要確認＋監査。自動子のあるトラブルの解決＝親の解決＋子の更新／取消＋要確認の解決＋監査。
