## 13. トラブル・再配達・一部納品・代替品

### 13-1. トラブル種別（マスタ・6区分）

アプリの画面ごとに区分が違っていたものを、**6区分のマスタへ統一**する。**種別はマスタで持ち**、区分ごとに運営の既定対応を紐づける〔サイクル §4A-4B〕〔要件 REQ-DL-657〕〔トラブルフロー §4〕。

| 種別 | 既定の対応 | 自動子（報告と同時）〔決定v2.3 #30〕 |
|---|---|---|
| **数量相違（不足・過剰）** | 不足分を**複製**して追加配送、または**送らない**（1〜2個など・運営判断〔決定v2.3 #31〕）／過剰は次回調整 | **作らない** |
| **誤配送** | **回収 ＋ 複製**して再配達（13-7） | **作る** |
| **破損・品質不良** | **代替品**で対応、または**廃棄登録**（13-6） | **作る** |
| **不在・受け取り不可** | **複製**して再配達（13-4） | **作る** |
| **遅延（渋滞・事故・天候）** | 当日中の再訪、または翌日へ**複製**。**遅延だけの配送に全量の納品報告が入ったら自動で解決**〔決定v2.3 #32〕 | **作らない** |
| **その他** | 理由の入力を必須とし、運営が個別判断 | **作らない** |

**自動子の作る／作らないはマスタ（`trouble_types.auto_child`）で持ち、運営（物流）が変更できる**〔決定v2.3 #33〕。報告の時点の種別は下のアプリの対応表で決め、**「商品不足・誤配送」は種別未定として作らない**（運営が6区分を付けた時点で、作る種別なら作る）。

**アプリの選択肢と6区分の対応** — **ドライバーアプリの画面はそのまま（確定済）とし、運営側でマスタ6区分へ対応づける**〔決定 #66〕〔要件 REQ-DL-853〕。アプリの選択肢を6区分にそろえる改修はしない。

| アプリの選択肢（画面確定済み） | 出どころ | 対応づけるマスタ6区分 |
|---|---|---|
| 箱数不足 | 荷物受取系の報告画面 | **数量相違（不足・過剰）** |
| 誤配送 | 荷物受取系の報告画面 | **誤配送** |
| 荷物破損 | 荷物受取系の報告画面 | **破損・品質不良** |
| 商品不足・誤配送 | 配達系の報告画面 | **数量相違（不足・過剰）** または **誤配送** — **運営が振り分ける**（自動判定はしない） |
| 交通渋滞・事故 | 配達系の報告画面 | **遅延（渋滞・事故・天候）** |
| 不在・連絡不可 | 配達系の報告画面 | **不在・受け取り不可** |
| その他 | 荷物受取系・配達系の両方 | **その他**（理由必須） |

- アプリから上がった値は**原文のまま保持し**（`trouble_reports.app_reason_raw`）、運営がトラブルの処理で6区分の `type_code` を付ける。**区分を付けて解決するまで、トラブル報告は未解決のまま要確認に残る**（配送データの状態は変えない〔決定v2.3 #20〕。旧：区分を付けるまでは 確認中 のまま。2026/09/24 廃止）〔サイクル §4A-4B〕。既定の対応は**候補の提示**であり、最終的に選ぶのは運営（**理由の入力は必須**）。報告者はドライバーだけではなく、**final leg が運送会社の直接配達の便では法人・拠点または配送会社からの連絡**になるため、**運営が代理で登録できる**入口を用意する〔要件 REQ-DL-657〕。

### 13-1B. 実績明細（`delivery_lines`）

納品の実績は**配送データの合計だけでなく、商品ごと**に持つ〔決定v2.3 #8〕〔要件 REQ-DL-902〕。置き場は `delivery_lines`（`UNIQUE(delivery_id, product_id)`）。

| いつ書くか | 何を書くか |
|---|---|
| **確定生成（materialize）** | オーダーの商品別の確定数量を `planned_qty` に入れる。オーダーに商品別の内訳が無ければ、この時点では作らない |
| **出荷実績の取込** | 商品別の内訳があれば `planned_qty` に書く（無ければ確定生成時にオーダーから作った値のまま）〔原典：DEV §11〕 |
| **納品報告（ドライバーアプリ）** | `delivered_qty`／陳列前後の実在庫 `stock_before`・`stock_after`／廃棄 `disposed_qty`（~~納品した分の `expiry_date`~~ 2026/10/01 削除：期限は追跡しない） |
| **数量差異のトラブル（`qty_diff`）** | 商品ごとの `delivered_qty`。**合計は `deliveries.delivered_qty` と一致させる** |

**分納したときは、子の配送データが自分の `delivery_lines` を持つ**（`planned_qty`＝残数）。**親の明細は書き換えない**〔決定v2.3 #8〕。契約側の `contract_delivery_lines`（配送明細の設定）とは**別物**なので混同しないこと。

### 13-2. 対応フロー

> **トラブル報告のあとのドライバーの操作**（2026/10/01 追加・P10-7）：報告後もドライバーはステップ入力・完了を続けられる。運営が解決（`resolution`）を登録したら、その配送の実績はドライバーから直せない（完了後7日の修正期限より優先）。**ドライバーのトラブル報告は、配送を完了したあとも完了から7日までできる**（完了後7日の修正と同じ期限。7日を過ぎたら ES へ電話 → 運営が代理登録）〔台帳 S・#459。#434 を置き換え〕。完了後の報告も完了前と同じ流れ（状態は変えず、トラブル報告を記録して要確認 `trouble_open` を開き、運営が解決する）。トラブルがあっても修正できなくなるのは**トラブルに関わる部分だけ**で、止めるのは運営が解決を登録してから〔台帳 S・#471〕。

**報告の入口**

| 入口 | 誰が | どこから |
|---|---|---|
| ドライバーアプリのトラブル報告 | ドライバー | 配送一覧から対象を選ぶ → 状況報告フォーム → 拠点選択 → 種別＋画像＋備考を送信〔要件 REQ-DL-148〕 |
| 荷物受取の「一部未受取のまま完了」 | ドライバー | 未受取の送り状番号とともに要確認へ〔要件 REQ-DL-644〕 |
| COOL配送便の「一部未配送のまま完了」 | ドライバー | 未配送分は枝番の子レコードとして作る〔要件 REQ-DL-649〕 |
| 代理登録 | 運営 | 法人・拠点・配送会社からの連絡を運営が入力（**final leg が運送会社の便はこれが主**）〔要件 REQ-DL-657〕 |

**運営の判断**（`locked` は「**予定〈日付〉を書き換えない**」という意味であり、実績の登録・`delivery status` の変更・後続レコードの追加はできる。**過去の記録は書き換えず、取消または複製で処理する**）〔サイクル §4A-4B〕〔トラブルフロー §1〕

| 局面 | 手順 |
|---|---|
| **① 出荷前に不可が判明**（倉庫の設備故障・車両を手配できない・大雪など） | ①配送データを**取消**（理由必須・履歴に残す） → ②出荷指示を**数量0で再送**して打ち消す（取消のI/Fは持たない。ピッキング開始後は電話連絡） → ③代わりの便は**複製で新しい配送データ**を作る（元は取消として残す） → ④法人Webには**「配送日調整中」**と表示し、運営コメントで状況を伝える（**法人には「取消」の文字を見せない**。表示名は状態とは別に持つ・15-10）〔決定v2.3 #42〕〔トラブルフロー §2〕（旧：法人へは「確認中」として表示。子だけの状態名「確認中」とぶつかるため 2026/09/29 置き換え） |
| **② 出荷後・配達中のトラブル** | 報告を受けても **`delivery status` は変えない**（出荷済／受取済 のまま。納品後の連絡は 納品済 のまま）。トラブル報告を記録して要確認を開き、運営（物流）が **再配達／代替品／廃棄／中止** のいずれかを選んで**親を直接閉じる**〔決定v2.3 #20・#21〕〔要件 REQ-DL-650〕（旧：`delivery status` を確認中にする。2026/09/24 廃止） |
| **③ `locked` 後の法人からの変更依頼** | システムからの変更申請は受け付けない。運営がシステム外で調整し、②の再配達または①の取消＋複製で処理する。**予定を遡って書き換えない** |

**トラブルの解決 — 運営（物流）が親を直接閉じる**〔決定v2.3 #21〕（**状態は納品できた量で決まる**。代替品と廃棄は状態ではなく、付随して行う処理である）〔サイクル §4A-3B・§4A-4B〕〔トラブルフロー §3.1〕〔DEV §13.2.1・§15.12〕。バッチは親の解決方法を決めない。

| 状況 | 元のレコード（起点） | 複製した子レコード（自動子が無いとき） | 自動子があるとき（同じトランザクション） |
|---|---|---|---|
| 全量を納品できた（代替品を含む）。過剰は次回調整 | **納品済**（出荷済／受取済／納品済 から） | — | **取消**（理由 `auto child not needed`） |
| 一部を納品し、残数を後日送る | **一部納品済**（実納品数で確定。出荷済／受取済 から） | 残数 ＋ **仮の納品日** ＋ **確認中** | **使い回す**：`duplicate_type=remainder`、数量・明細＝残数 |
| 納品ゼロで送り直す | **再配達待**（数量はそのまま。出荷済／受取済 から） | 全量 ＋ **仮の再配達日** ＋ **確認中** | **使い回す**：`duplicate_type=redelivery`、数量・明細＝全量 |
| 納品せずに終了する | **中止**（実績0・理由必須。出荷済／受取済 から） | — | **取消** |
| 当日中に再訪する（遅延など） | **受取済**（出荷済／受取済 から） | — | **取消** |
| **一部を納品し、残りは送らない**〔決定v2.3 #31〕 | **一部納品済**（実納品数で確定。出荷済／受取済 から。しきい値なし・運営判断・理由必須） | — | **取消** |
| **みなし完了の後に未着と確認**〔決定v2.3 #27〕 | **再配達待**／**中止**（**`completion_source = presumed` の納品済 から**。ヤマトへ調査を依頼したうえで） | 再配達待なら 全量 ＋ **確認中** | 再配達待なら**使い回す**／中止なら**取消** |

- **解決は配送単位でまとめて行う**〔決定v2.3 #29〕。その配送の未解決のトラブル報告をすべて1回で閉じ、同じ解決内容・日時・解決者を各報告に記録する。
- 解決の条件：トラブル報告が未解決・親が 出荷済／受取済／納品済・自動子があれば `確認中`・理由必須。親・未解決のトラブル報告・自動子をロックし、**親の解決＋子の更新／取消＋要確認 `trouble_open`・`trouble_auto_child_pending` の解決＋監査を1つのトランザクション**で行う〔決定v2.3 #24・#26・#29〕〔DEV §15.12・§17.1〕。
- **みなし完了の後の未着**請求はしない。すでに請求が確定していれば遡らず、翌月の調整で直す（14-3）。**箱の一部だけ届かなかった場合は未決**（§18 No.23）。**自動子があるのに2件目の子は作らない。**
- （旧：「確認中からの出口」。トラブルを受けた親を 確認中 にし、そこから 納品済／一部納品済／再配達待／中止／受取済 へ出していた。2026/09/24 廃止〔決定v2.3 #20・#21〕）

**報告と同時に作るトラブルの自動子**〔決定v2.3 #23・#24・#28〜#30〕〔DEV §13.2.1・§15.12.1〕（旧：「期限までに解決されないトラブル — 自動子」。`auto_duplicate_due_at`＝報告＋運用設定の分数を過ぎたらバッチ `trouble_auto_duplicate` が作っていた。2026/09/29 廃止）

- **いつ**：トラブル報告を**登録したとき**（ドライバー・委託配送会社・運営の代理登録）と、運営が**種別を付けた／付け直したとき**。期限・分数の設定・バッチは無い。
- **作る条件**：種別マスタで**自動子を作る種別**（誤配送・不在・破損）／トラブルが起きた配送が 出荷済・受取済・納品済／その配送に**生きている自動子がまだ無い**。**配送が未完了というだけでは作らない。** 種別未定（「商品不足・誤配送」）は作らない。作る種別から作らない種別へ付け直しても、作った子は自動では消さない（解決で取消）。
- **作るもの**：`確認中`・`duplicate_type=trouble_pending`・`creation_source=trouble_auto`・`source_trouble_delivery_id`（トラブルが起きた配送）・`source_trouble_report_id`（最初の報告）・`schedule_confirmed=false`・`quantity_confirmed=false`。複製と同じく納品先スナップショット・納品条件・受取時間帯・`delivery_legs` 全部をコピーし、送り状・割当・添付はコピーしない（親子1階層・枝番1〜9・§8-4）。**親は `確認中` にしない。** トラブルが起きたのが子なら、**親の次の枝番**として作る〔決定v2.3 #28〕。
- **仮の値**：候補日は**表示用の仮**。数量・明細は**再送しうる最大量の仮**で、出荷・請求には使わない。
- **1件の配送に生きている自動子は最大1件。** 2件目以降の報告では作らず、既存の子を使い回す。`UNIQUE(source_trouble_delivery_id) WHERE creation_source = 'trouble_auto' AND status <> '取消'` が最後の砦〔決定v2.3 #29〕。
- **作らない種別でも、未解決のトラブル報告は要確認（`trouble_open`）に残る。** 対応漏れはここで防ぐ〔決定v2.3 #30〕。
- **要確認**：`review_items.kind = trouble_auto_child_pending`（対象は子）を作る・更新する。
- **確定前は何にも参加しない**：出荷指示・送り状・ドライバー割当・請求・通知・みなし完了の対象外〔決定v2.3 #23〕。
- **出荷待へ進める**：運営（物流）が親のトラブルを解決し、数量・納品日を確定して `quantity_confirmed=true`・`schedule_confirmed=true` にしたときだけ `確認中 → 出荷待`（未確定は `DOMAIN_TROUBLE_CHILD_UNCONFIRMED`）。再送が要らない解決では同じトランザクションで `確認中 → 取消`（理由必須）〔決定v2.3 #24〕。

**例外の状態には必ず理由と履歴を持たせる**〔サイクル §4A-4C〕〔トラブルフロー §1〕 — ①**種別・理由**は6区分のマスタから選び補足文を添えられる（アプリの原文 `app_reason_raw` も併せて残し、状態の横に**理由・登録日時・登録者**を出す）。②**変更履歴**は状態が変わるたびに1行残す（`受取済 → 中止：受取担当者が不在`）。**履歴に無い状態変化を作らない。** ③**親子のリンク**は、親に複製先・子に複製元を出して相互に画面遷移できるようにし、件数・状態・納品日を添える（トラブル報告の画像は納品完了から**12ヶ月**保存・12-4）。

- **未解決のトラブル報告と `確認中` の子は最終状態ではない。** 対応が決まるまで運営スケジュールの「要確認」に残す。理由の無い中止が残ると、請求と監査で「なぜ届かなかったか」を説明できなくなる〔サイクル §4A-4C〕。なお `01_仕様/10_配送/画面設計書_トラブル報告_V1.0.md` は**顧客が設備の不具合（給排水・空調）を業者へ報告する別画面**の設計書であり、**配送トラブルの資料ではない**〔トラブルフロー §11〕。本節の出典は〔サイクル §4A-4B・§4A-4C〕と〔トラブルフロー §1〜§5〕である。

### 13-3. 一部納品

用語は**一部納品**を使う（「部分納品」とは書かない）。状態値は **一部納品済**〔サイクル §4A-3B〕。

1. **納品できた分は先に進める。** 元のレコードは**実納品数で確定**し、一部納品済としてその場で完了させる（**そのレコードの最終状態**・7-7）。商品ごとの内訳は**実績明細 `delivery_lines`** に入れる〔決定v2.3 #8〕。残数の扱いを決めるまで実績を止めない〔サイクル §4A-4C〕〔トラブルフロー §3.2〕。
2. **残数（子）は「確認中」で作る。** **自動子があれば新しく作らず使い回す**（`duplicate_type=remainder`、`delivery_lines` を残数に）〔決定v2.3 #21〕。対応画面で入れた日付は**仮の納品日**として持ち、ピッキング日は仮の納品日から逆算して置く〔要件 REQ-DL-649-2〕。
3. **要確認に載せる。**「残数の対応待ち」として運営スケジュールの要確認に出す。
4. **運営が確認して確定する。** 出荷待へ進めるには `schedule_confirmed` と `quantity_confirmed` の両方が true であること（10-1）〔決定v2.3 #24〕。結果は3つ — **この日で確定**（→ 出荷待）／**日付を変更**（決め直した時点で → 出荷待）／**中止**（→ 中止）。いずれも理由とともに変更履歴に残す。

- 確認を通すまで出荷待にしないのは、**仮の日付のまま出荷指示（2週間まとめ・開始の3日前の金曜）に流れるのを防ぐため**である。**確認中の複製は出荷指示の対象外**とし、出荷指示の履歴が残っている配送データが確認中である、という状態は作らない〔要件 REQ-DL-801〕。**一部未受取・一部納品は送り状単位で判定する。** 送り状と配送データは**1対多**（1件の配送データに送り状番号が複数＝箱ごと）で、**1つの送り状に複数の配送データは入らない**（＝まとめ出荷はない）ため、送り状から辿る先は常に配送データ1件である〔決定 #54〕〔要件 REQ-DL-833〕。COOL配送便が自動生成していた「未配送分のタグ」は作らず、**枝番の子レコード（複製）**に統一する〔要件 REQ-DL-649〕。

### 13-4. 再配達

| 項目 | 内容 | 出典 |
|---|---|---|

### 13-5. 複製（トラブル対応から見た補足）

複製の手順・コピーする項目／しない項目・枝番の付け方・数量の振り分けは **§8-4 に一本化**している。ここではトラブル対応から見た補足だけを書く。

- **複製できるのは `published` か `locked` の配送データからだけである。`draft` からは複製できない**〔決定v2.1 #5〕〔要件 REQ-DL-872〕（旧：第1次「複製は `draft` / `published` / `locked` のいずれからでも実行できる」は**取消**）。**`draft`（納品予定）でできるのは「予定のコピー／変更」だけ**で、**`parent_delivery_id`・枝番・状態 確認中 を伴う複製は `published` / `locked` からのみ**行う。予定には配送データが無く、送り状も実績も無いため、親子関係を作っても指す先が無く、確定生成のときに親子が二重にできてしまうからである〔サイクル §4A-4C〕。
- **トラブルが起きた配送1件に、生きている子は最大1件。** 手動の複製も、その配送に子（自動子を含む）があれば使い回し、2件目は `DOMAIN_TROUBLE_CHILD_EXISTS` で拒否する〔決定v2.3 #21・#29〕（8-4）。手動の複製は運営（物流）、自動子の作成はシステム（報告の登録と同じトランザクション・監査は `actor_type=system`）〔決定v2.3 #30〕。
- **複製は新規作成であり元を書き換えないため、`locked` でも実行できる。** `locked` 後に日付を変えたいときは、日付の書き換えではなく**取消＋複製**で対応する〔決定v2.1 #1〕（§8-4）。
- 実行できるのは**運営（物流）のみ**で、**理由（分納／再配達／代替便／返送／その他）の選択と理由文の入力を必須**とし、変更履歴に残す〔決定v2.3 #41〕。複製したレコードは**要確認**に載せ、日付・送り状・ドライバーが未設定のまま出荷指示へ流れないようにする〔サイクル §4A-4C〕。使い分けは、**分納**＝納品できた分で元を確定し残りを子に（元は 一部納品済）／**再配達**＝届かなかった分を子に（元は 再配達待）／**代替便**＝出荷前に元を 取消 にして全量を別ルートの子で出す／**返送**＝残った商品を子で本社などの返送先へ送る（`duplicate_type = return`。**このときだけ納品先を返送先に替えられる**。請求しない）〔決定v2.3 #41〕。

### 13-6. 代替品

| 事象 | 扱い | 出典 |
|---|---|---|
| **代替品で対応した** | **元の商品（元の品目）の料金で請求**する。代替品の原価差はES負担（14-2）。代替品を登録し、顧客がダウンロードする納品書へ反映する。**記録のしかた**：`delivery_lines` の1行＝**実際に渡した商品**とし、**`substituted_from_product_id` に代替元の商品**を入れる。**請求は代替元の商品の単価**で計算する。登録するのは、トラブルの解決で「代替品で全量納品」を選んだとき（商品を選ぶ）と、実績の修正のとき（運営のみ・理由必須）〔決定v2.3 #39〕 | 〔サイクル §4D-1〕〔トラブルフロー §7〕〔要件 REQ-DL-316〕〔決定v2.3 #39〕 |
| **代替品設定（商品不良・運営 › メニュー管理）** | 2026/10/01 決定（代替品対応_詳細要件仕様 §7-1）：**① 差し替え／② 補償／③ 除外のみ の3パターン**。注文と配送データの明細を同時に直し、明細に代替元（`substituted_from_product_id`）を入れる（トラブルの代替品と同じ記録）。出荷指示を送ったあとは出荷日の前日まで版番号つきで再送（rev+1）、出荷日以降は補償。補償は次の便に足す（ない・遠いときは追加配送＝複製・配送費 ES 負担）。請求：差し替え＝元の単価、補償＝実績精算に0円の行、除外のみ＝請求しない。拠点に残る不良品は廃棄として記録（管理ロスにしない）。倉庫の不良ロットは出荷停止（返品／廃棄）。納品リスト（ドライバー・委託）と法人Web（お届け詳細・納品書・月次注文・お知らせ・メール X17）に「代替品（元：〇〇）」 | 〔決定_代替品設定_3パターンと下流_20261001〕 |
| **別倉庫から出す場合** | **代替品扱いとする**（不良品対応で別倉庫から出す場合を含む）。移動先の倉庫にその商品の取扱がなければ商品を選び直し、取扱があればそのまま複製できる | 〔サイクル §4A-4C〕〔要件 REQ-DL-678〕 |
| **廃棄** | 廃棄登録して在庫を補正する（冷凍品が溶けた場合など）。**納品していないため請求しない。廃棄した分はどこにも戻らない。** 残った現物は**複製の理由「返送」で本社などへ送る**（`duplicate_type = return`・納品先を倉庫マスタの返送先に替える・数量は残数・**請求しない**。8-4）〔決定v2.3 #41〕（旧：配送データを1件作り配送先を「本社」として送る。作り方が決まっていなかった） | 〔サイクル §4A-4B・§4D-1〕〔決定v2.3 #41〕 |
| **中止** | 納品せずに終了。実績0で確定し、**当月の請求対象から外す。次回への振替はしない**。**運賃は再配達と同じ `freight_billable`**（既定「しない」・「する」は理由必須）。廃棄は `delivery_lines.disposed_qty`、残った商品は「返送」〔決定v2.3 #40・#41〕 | 〔サイクル §4D-1〕〔決定v2.3 #40〕 |

- **代替品と廃棄は `delivery status` ではない。** 状態は納品できた量で決まる（13-2）〔サイクル §4A-4B〕。

### 13-7. 誤配送の回収

**回収はトラブル報告の中に記録するだけとする**〔決定 #68〕〔要件 REQ-DL-854〕。回収日・回収者・回収数量・回収品の行き先などの**専用項目は作らない**。

- 既定の対応は**回収 ＋ 複製して再配達**（13-1）〔サイクル §4A-4B〕〔トラブルフロー §4〕。回収も再配達も**運営（物流）が判断・実行**し、**理由を付けて変更履歴に残す**。誤配送の報告を受けても配送データの状態は変えず、トラブル報告として対応が決まるまで要確認に残る（13-2）〔決定v2.3 #20〕（旧：配送データは確認中になる。2026/09/24 廃止）。再配達分は**枝番の子レコード**として作り、子は**確認中 ＋ 仮の納品日**で起こす（13-3・13-4・§8-4）〔要件 REQ-DL-649-2〕。
