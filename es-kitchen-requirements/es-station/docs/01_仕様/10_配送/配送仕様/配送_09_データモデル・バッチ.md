### 16-3. 便の3軸とルート（レグ）

**便は3軸で表し、「委託便」という区分は使わない**〔決定v2.1 #7〕〔要件 REQ-DL-874〜876〕。

| 軸 | 値 | 持ち主 | 備考 |
|---|---|---|---|
| **`delivery_regime`（配送体制）** | `self`（自社）／`partner_driver`（委託ドライバー）／`parcel_carrier`（運送会社） | `contract_delivery_channels`（既定値）→ **`contract_routes` / `contract_month_routes`（区間ごと）→ `delivery_legs`（配送1件の区間）が優先** → `deliveries`（生成時のスナップショット） | 旧 `service_type(self｜outsourced)` の2値は取消 |
| **`service_form`（便種別）** | `es_delivery`（ES配送便）／`cool`（COOL配送便）／`material`（資材便） | **配送区分（delivery channel）。契約のルートには置かない** | 中継の有無からは導出しない（REQ-DL-785 は取消）〔決定 #29〕 |
| **relay（中継）** | 中継あり／なしの2値 | **持たない（route legs から導出）** | **状態としては保存しない。** 中継先を含む leg が1本でもあれば「中継あり」。途中ステータスは持たない |

**ルートは3本のテーブルで持つ**〔決定v2.3 #1〕。**`delivery_routes`（`contract_id NULL` / `delivery_id NULL` の1本兼用）は廃止**した。列の詳細は `配送_11` 14.2・14.4 が正（§0-3）。

| テーブル | 役割 | 一意制約 | 備考 |
|---|---|---|---|
| **`contract_routes`** | 親契約の配送区分ごとのルート定義 | `UNIQUE(channel_id, leg_no)` ／ `UNIQUE(channel_id) WHERE is_final_leg` | **`driver_id` を持たない** |
| **`contract_month_routes`** | 子契約（サイクル月）へのスナップショット | `UNIQUE(month_channel_id, leg_no)` ／ `UNIQUE(month_channel_id) WHERE is_final_leg` | 同上。`snapshot_at` を持つ |
| **`delivery_legs`** | 配送データ1件の実際の区間 | `UNIQUE(delivery_id, leg_no)` ／ `UNIQUE(delivery_id) WHERE is_final_leg` | **`driver_id` / `assigned_by` / `assigned_at` はここだけ**。**割り当てるのは `delivery_regime` が `self`／`partner_driver` の区間だけ**（`parcel_carrier` は割り当てない）〔決定v2.3 #48〕。★**`picked_up_at` / `picked_up_by`**（NULL 可）＝区間ごとの受取時刻・受取者。状態は増やさず、受取済は最初の受取だけで入る〔決定v2.3 #49〕。`snapshot_source(contract_month｜contract)` で写した元を残す |

**3本に共通の guard**〔決定v2.3 #1〕：`leg_no` は1から連番で飛ばさない／leg 1 は `from_type = warehouse` かつ `from_id = channel.warehouse_id`／leg `n+1` の `from_id` ＝ leg `n` の `to_id`／**`is_final_leg` はちょうど1本**で `to_type = destination`／中継なし＝1レグ、中継あり＝2レグ（フェーズ2）。

**`delivery_legs` の性質**：materialize のときに、**子契約があれば `contract_month_routes` から、無ければ `contract_routes` から**写す。写したあとは**不変のスナップショット**で、`contract_routes` を直しても作成済みの配送データには影響しない。最後のレグの `to_id` は `deliveries.site_id`（スナップショット済み）。**複製（枝番）は legs を全部コピーするが `driver_id` / `assigned_by` / `assigned_at`・`picked_up_at` / `picked_up_by` はコピーしない**〔決定v2.1 #5〕〔決定v2.3 #49〕。

**`is_final_leg`**＝`to_type = destination` のレグ（`leg_no` の最大値と一致）。**みなし完了・欠配検知はこのレグの `delivery_regime` で判定する**〔決定v2.1 #4〕〔要件 REQ-DL-871〕。**割当はレグ単位**で、**運送会社の区間は割り当てず、自社・委託の区間は割り当てる**〔決定v2.3 #48〕（旧：運用は当面2次だけ〔決定 #60〕。2026/09/29 置き換え）。中継があってもリードタイムは契約の合計1つが正（区間ごとの日数は参考値）〔決定 #21〕。**`service_form` はレグに置かない**。

**「この配送だけ」のルート変更は `delivery_legs` を直接 UPDATE する**（監査ログに `before_json` / `after_json`）。**`route_override` は持たない**〔決定v2.3 #2〕。guard は 15-6・15-13 を見ること。

**final leg による分岐**〔決定v2.1 #4〕

| final leg の運び手 | 完了の扱い | 欠配の扱い |
|---|---|---|
| **ES のドライバーアプリ**（`self` / `partner_driver`） | **みなし完了にしない** | 翌朝になっても完了していなければ **missing queue（要確認）へ** |
| **運送会社が直接配達**（`parcel_carrier`） | **みなし完了にする**（`completion_source = presumed`。`status = 出荷済` で未解決のトラブル報告が無いもの〔決定v2.3 #25〕） | 顧客・配送会社から異常の連絡があったときだけトラブル報告と要確認を開く（状態は変えない〔決定v2.3 #20〕。旧：確認中 へ落とす） |

### 17-1. バッチ一覧

**日次の catch-up**（毎日、基準日を過ぎた未処理分を拾う）を前提に設計する。サイクル初日A1は暦の1日と一致しないため、特定の曜日・暦日に回す前提は成り立たない。**祝日でもバッチは毎日実行する**〔サイクル §11-1〕。**全11本**（2026/09/24 追補で `trouble_auto_duplicate` を足したが、2026/09/29 追補で廃止した〔決定v2.3 #30〕）。

- **日次5本**（`contract_monthly_generate` → `plan_rollout` → `delivery_materialize` → `order_finalize` → `plan_recheck`）は**この順のジョブチェーン**で実行し、前段が失敗したら後段は実行しない。`billing_issue` / `billing_gap_detect` と納品実績系4本は独立して動かす〔DEV §16.13〕（旧：`trouble_auto_duplicate` をみなし完了・欠配検知より前に流す。2026/09/29 廃止）。**異常系**：①1契約の処理が失敗 → **契約単位でトランザクションを切り**、他の契約は続行して失敗分だけ記録。②一時的な失敗 → 自動で3回まで再試行（間隔は指数的に延ばす）→ なお失敗なら `batch_errors` に記録し要確認へ「確定生成に失敗：N件」（対象を絞った**手動再実行**ができる）。③実行が重なる → ジョブ単位でロックし、実行中なら次回はスキップしてログに残す。④締切超過の拾い漏れ → **毎日**「締切を過ぎているのに未確定」を必ず再検出する。**実行ログ**は開始・終了・対象件数・成功／失敗件数・所要時間を保存し、画面で**直近30回分**を確認できる。

### 17-2. 変更履歴（監査ログ）

**対象**：納品予定、配送データ、倉庫マスタ、契約配送設定、全社の配送サイクル設定〔サイクル §11-2〕。

| 項目 | 内容 |
|---|---|
| 日時／**操作者** | ユーザーIDとロール。バッチは「システム」＋バッチ実行ID。**省略できない** |
| 対象／操作 | 種別（予定／配送データ／マスタ）とID／作成・日付変更・倉庫変更・ルート変更・オーバーライドの作成／取消／失効・状態遷移・削除 |
| **変更前 → 変更後** | **変更した項目のみ。省略できない** |
| 理由 | 変更申請ID、一括変更ID、バッチ実行ID、または手入力の理由 |

- **理由が任意**：オーダー締切前の「1回だけの変更」（配送ルートの変更・日付の個別指定）。ただし**変更前→変更後と操作者は必ず残す**〔決定 #26〕。**理由が必須**：手動での日付移動・一括変更／承認済みオーバーライドの取消／倉庫マスタの編集／倉庫変更／休止・解約による予定削除／取消・中止・**複製**。保持期間は予定と同じ **24ヶ月**。配送データ詳細の「申請・承認履歴」は**「変更履歴」タブに統合**し、申請とシステム変更を時系列で並べる。スケジュール画面に画面全体の変更履歴は置かない。

### 17-5. 既存データの移行

**対象**：法人・拠点・契約・配送先住所・現行スケジュール・進行中の配送・送り状番号・保冷バッグ／保冷剤番号〔サイクル §11-5〕。

| 2 | 契約を移行し、**配送区分は現行の「倉庫＋配送会社＋温度帯」から機械的に起こす**（基本は1契約1区分、冷凍を扱う契約だけ2区分）。**リードタイムは契約の配送区分へ入れる**（倉庫マスタからは引かない）〔決定 #10〕。**`delivery_regime` は現行の自社／委託の別から起こし、`service_form` は配送区分へ入れる**〔決定v2.1 #7〕 |
