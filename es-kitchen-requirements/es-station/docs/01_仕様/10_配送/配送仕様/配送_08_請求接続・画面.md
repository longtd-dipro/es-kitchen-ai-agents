## 14. 請求との接続

### 14-1. 締めは納品日の暦月

**締めは納品日の暦月**で判定する。**サイクル名**（`2026年10月 配送サイクル`）は物流の都合の**表示ラベル**であり、請求には使わない。**分納は納品実績ベース**とし、**実際に納品した日の暦月**にその数量を計上する。**親子（枝番）は伝票のまとめ方であって、金額の帰属を決めない**〔サイクル §4D-1〕〔要件 REQ-DL-660〕。

| ケース | 結果 |
|---|---|
| 8/20に18食、8/22に残り2食 | どちらも8月請求。合計20食。請求書は1行でも、内訳に 8/20 18食・8/22 2食 を出せる |
| **8/31に18食、9/2に残り2食** | **8月請求18食、9月請求2食。** 実績と一致し、監査でも説明しやすい |
| 残り2食が結局納品できなかった | その2食は**請求しない**（納品していないため） |

| 費目 | 帰属する月 |
|---|---|
| **プラン固定額・オプション・設備・値引き（①前払い）** | **契約・サイクル月**の1ヶ月。請求月＝サイクル月 − 請求書発行リードタイム、確定は請求月の25日 |
| **分納・再配達・スポット費用** | **納品日の暦月**（実績ベース）。スポット費用は行ごとに対象期間を指定できる |
| **実績精算（②後払い）** | 前月21日〜当月20日を対象期間とし、棚卸が締まった後の月に請求 |

- **1枚の請求書に ① と ② が両方入るのが普通**である（別々の子契約から来る）。ただし**支払期限が違えば請求書を分ける**（14-4）。納品済みの**実績は締まらない**（完了日時・納品数・備考は理由付きで修正でき、添付資料は追加・差し替えできる）。ただし**確定済みの請求月にかかる実績修正は請求を遡って書き換えず、翌月以降の調整で反映する**（14-3）〔サイクル §4A-4C〕〔トラブルフロー §6〕。

### 14-2. 中止・代替品・再配達・単価改定の扱い

| 事象 | 請求の扱い | 出典 |
|---|---|---|
| **中止** | 実績0。商品は**当月の請求対象から外す。次回への振替はしない**（振替は追えなくなるため）。**運賃は `freight_billable`**（再配達と共通のフラグ・既定「しない」・「する」は理由必須） | 〔サイクル §4D-1〕〔決定v2.3 #40〕 |
| **締切後にお客様都合で中止** | **請求しない（現行どおり）。「キャンセル料」の項目は作らない** | 〔決定 #69〕〔要件 REQ-DL-857〕 |
| **代替品** | **元の商品（元の品目）の料金で請求**する（代替品の原価差はES負担）。`delivery_lines.substituted_from_product_id`（代替元）の単価で計算する | 〔サイクル §4D-1〕〔トラブルフロー §7〕〔決定v2.3 #39〕 |
| **返送**（残った商品を本社へ） | **請求しない**（`duplicate_type = return` の配送データは請求の対象外） | 〔決定v2.3 #41〕 |
| **廃棄** | 納品していないため**請求しない**。在庫側で補正する | 〔サイクル §4D-1〕 |
| **欠配** | 請求は実績に従うため、**納品していなければ請求しない**（11-5） | 〔サイクル §4D-1〕 |
| **確定前の自動子** | `duplicate_type=trouble_pending` の子は**請求の対象外**。仮の数量は請求に使わない。運営（物流）が確定して出荷待へ進めた後は、ほかの子と同じく実績で請求する | 〔決定v2.3 #22・#23〕 |
| **再配達** | 商品の請求は変えない。運賃は**個別判断**（請求する／しないフラグ **`freight_billable`**・既定「しない」・「する」は理由必須。旧名 `redelivery_billable`） | 〔サイクル §4D-1〕〔要件 REQ-DL-660〕〔決定v2.3 #40〕 |
| **単価改定** | **プランマスタの料金改定（①〜④の世代）で持ち、請求にも載せる。** 契約側に単価を直接書かない | 〔決定 #69b〕〔要件 REQ-DL-858〕 |
| **地域加算**（2026/09/30 追加） | 委託配送先マスタの地域加算（運営が手動で入力・3-3）を目安に、**子契約のオプション（オプションマスタの地域配送料）として請求に載せる** | 〔要件シート 行53・78・決定_要件シート一部反映_回答_20260930〕 |
| **企業負担額と税率**（28-147〜150） | プランマスタが企業負担額（既定100円・税込・1食）と税率（税率マスタ）を持つ。プラン価格（税抜）を **基本料（10%）＋企業負担分（8%）** に分ける。子契約の生成時にスナップショット（`contract_month_plan_snapshot`）。「福利厚生の適用」ON＝請求書に2行、OFF＝1行（税は2つの税率で計算）。詳細は請求の仕様 | 〔原典：DEV §4.9〕 |
| **現金回収差額**（アプリの現金支払い） | **回収予定額とドライバーの実際の回収額が違うときだけ、差額を②実績精算に載せる**（不足＝請求、多く回収＝減額）。一致していれば載せない。アプリで決済済みの支払いは実績精算に出さない | 〔申請まわり 28-135〕 |

- 締切後の中止にキャンセル料を持たないため、**「中止＝請求しない」の1本**で扱い、請求には行が立たない〔決定 #69〕。単価改定を請求側の個別項目として持たないのは、**料金の正がプランマスタの世代**だからである。子契約を生成するときに**そのサイクル月に適用される世代の料金をスナップショット**し、1年一括前払いのように先に作る場合も**各サイクル月に適用される世代をそれぞれ引く**。**改定後の単価は請求明細に、適用した世代が分かる形で出す。** 請求済みの子契約は訂正せず、14-3 の調整で翌月以降に反映する〔サイクル §4D-1〕。

### 14-3. 返金・相殺（調整）

**独立した3つ目の表（③調整）は作らない。①前払い・②実績精算それぞれの中に、調整（返金・相殺）を持てるようにする**〔決定 #70〕〔要件 REQ-DL-835〕。

| 項目 | 内容 |
|---|---|
| 表の構成 | 子契約の請求区分は **①前払い／②実績精算** の2つ。その**内訳として** `adjustment(refund \| offset)` の行を持つ |
| 理由 | 調整は必ず「どの前払い」「どの実績精算」に対する調整かが決まっており、切り離すと対応関係を別に持ち直すことになる。請求書の面でも、それぞれの明細の中に出るほうが読める |
| 原則 | **請求済みの子契約は取り消さない。** 請求書を出したあとに元の請求を消すと **Bill One 側の突合が合わなくなる**ため |
| 起票のタイミング・単位 | **休止・解約の承認時**に、対象サイクル分の調整を**自動で起票**する。単位は**サイクル（子契約）単位**で、休止で飛ばすサイクル・解約で履行しないサイクルの分をそれぞれ1件として作る |
| 返金か相殺か | **法人ごとの判断**なので起票時に運営が選ぶ。**既定は相殺** |

- 調整で吸収するもの：**年一括前払いで休止・解約した分**は **①前払いの中の調整**／**確定済みの請求月にかかる実績修正**（納品後の連絡を受けて実績を直した場合を含む。`納品済` の状態は変えない・11-7〔決定v2.3 #20〕。旧：納品済 → 確認中 へ戻した場合）と、**final leg が運送会社の便のみなし完了で後から見つかった差異**（11-2）は **②実績精算の中の調整**。本仕様書で「③調整」と書いていた箇所は、すべて**①または②の中の調整**を指す〔サイクル §4D-1〕。

### 14-4. 支払期限（入金期限）

**請求書を `billing_type` または `payment_due_date` で分ける。1つの請求書は支払期限を1つだけ持つ**〔決定v2.1 #10〕〔要件 REQ-DL-880〕（旧：第1次 #71「子契約の請求に入金期限を `advance_payment_due_date` / `settlement_payment_due_date` の2項目として持つ」。2026/09/21 第2次で「請求書を分ける」形に具体化）。

| | 何を指すか | どこで管理するか |
|---|---|---|
| **請求書を出す期限** | 子契約の金額を確定し、請求データを作って Bill One へ渡すまでの期限 | **本システム**（**20日締め → 25日確定 → 翌月1日に Bill One で発行**〔台帳〕。旧：請求確定日＝25日 → 月末発行。2026-10-03 台帳に合わせて修正） |
| **入金期限（支払期限）** | 法人がその請求金額を実際に支払う期限 | **本システムが請求書（`invoices.payment_due_date`）に持つ。1請求書＝1支払期限** |
| **入金消込・遅延・督促** | 入金の照合と回収の実務 | **Bill One 側**。本システムには作らない |

- **前払いと実績精算で期限が違うなら、請求書を2枚にする**〔決定v2.1 #10〕。**共通の期限を1つ選ぶ案は採らない。** 1枚の請求書に期限が2つ載ると、**入金の対照（消込）がどちらに当たったのか判定できなくなる**ためである。
- データ上は `invoices(contract_month_id, billing_type, payment_due_date)` を分割キーとし、この組で一意（`UNIQUE`）にする〔サイクル §7〕。請求バッチ `billing_issue`（毎日 04:30）は、**`billing_type` と `payment_due_date` の組ごとに請求書を1枚**起票し、**1請求書に支払期限を2つ載せない**〔サイクル §11-1〕。**持つのは期限の値までで、その先（入金されたか）は Bill One が正**である。口座振替・クレジットの引き落とし日もこの日付を使う〔決定 #71〕。旧版（2026/09/15）の「本システムは支払期限・入金期日・支払サイトの項目を持たない」は、請求書の記載と法人への提示に必要なため **2026/09/21 に撤回**した〔サイクル §4D-1〕。

### 14-5. オーダー確定数量の受け渡し

| 項目 | 内容 | 出典 |
|---|---|---|
| いつ | **オーダー締切日を過ぎたサイクル**を日次バッチ `order_finalize`（毎日 02:45）が拾う | 〔サイクル §11-1・§4A-2〕 |
| 何をするか | オーダーの**数量を確定**し、**配送データへ確定数量を書き込む**（レコードを作るのではない）。同時に**日付変更モードを OFF 固定**にし、**確定数量の出どころ**（`ordered` ／ `standard` ／ `ai`）をデータに保持する | 〔サイクル §4A-2〕〔要件 REQ-DL-810〕 |
| 注文がないとき | **AIモード OFF（既定）＝標準数量**（プラン数量を配送回数で按分した値）／**AIモード ON ＝AIが数量を自動設定**。AIモードは**拠点（契約）ごとの ON／OFF**。法人画面には確定後の数量を表示し、自動で入ったことは伏せない（注文を忘れたことに法人が気づけるようにする）〔原典：納品サイクル設定 §4A-2D〕。（オーダー枠そのものが無いときに `qty_missing` を出すか標準数量で埋めるかは `配送_10` §18-1 で確認中〔DEV §8.2〕） | 〔サイクル §4A-2D〕〔要件 REQ-DL-810〕 |
| **確定数量 0** | 正しい値。出荷前の取消と同じに扱う（数量0で再送・10-3）。データの欠けとは扱わない。確定のとき `deliveries.order_id` にオーダーを入れる | 〔原典：DEV §8.2〕 |
| 下流への受け渡し | 確定数量は**出荷指示（トーマス）**へ渡る。出荷指示は **A＋B週／C＋D週の2週間分をまとめ、開始の3日前（金曜）に出力**する。出力後の変更は**版番号付きの再送で上書き**し、**中止は数量0で再送**する | 〔サイクル §4D-3〕〔要件 REQ-DL-812・662〕 |
| 委託配送会社・請求への受け渡し | 専用サイトの予定が確定するのも**このタイミング**（11-6。確定後は全項目を出す〔決定v2.3 #34〕）。確定数量は請求の直接の根拠ではない（**請求は納品実績ベース**。14-1） | 〔サイクル §4C-4・§4D-1〕 |

**仮の締切（`marker_source = provisional`）では数量確定も確定メールも走らせない**〔決定v2.1 #9〕〔要件 REQ-DL-879・811・840〕。メニュー未登録でオーダー締切日が取得できない場合は**前月15日を仮の締切**として判定し、画面に「**仮**」と表示するが、できることを次に限る。

| 処理 | `marker_source = provisional`（仮） | `marker_source = menu`（本当の締切） |
|---|---|---|
| `order_finalize`（数量確定） | **走らせない（対象外）** | 走らせる |
| **確定メールの送信**（法人・委託配送会社） | **送らない** | 送る |
| **出荷指示の送信**（トーマス連携）。したがって `locked` にもしない | **送らない** | 送る |
| 変更受付の締め切り（日付変更モードを OFF にする） | **走らせる** | 走らせる |
| `plan_recheck` ほかの検査・要確認の生成 | **走らせる** | 走らせる |

- **オーダー締切は「生成のトリガー」ではなく「数量の確定点」**である。法人は生成済みの配送データに対して注文するため、配送データはオーダー開始の時点で存在している必要がある〔サイクル §4A-2〕。
- **仮の締切は内部判定の既定値であって、法人や倉庫に約束した日付ではない。** 仮の日付で数量を締めて出荷指示まで流すと、あとからメニューが登録されて締切が動いたときに取り返せない。メニューが登録された時点で実日付へ差し替え、`marker_source = menu` になってから `order_finalize` が拾う〔サイクル §4A-2E・§11-1〕。

### 15-8. サイクルのライフサイクルと日付変更ポリシー

サイクルは `スケジュール設定（メニュー登録中） → メニュー公開・オーダー開始 → オーダー締切` の順で進む。メニュー公開とオーダー開始は**同じ日**なので、旧版の「メニュー公開〜オーダー開始前」という段階は持たない〔サイクル §5.0〕〔要件 REQ-DL-757〕。節目の日付は**メニュー側が正**で、サイクル生成時に実日付を写し取って保持する（**実装で定数の日付を使わない**）〔決定 #33〕。

> **2026-10-02 改定**：日付の変更の区切りは「オーダー締切」ではなく**「本発注の時期」**になり、スケジュール画面からチェックで選んで動かす形になった。正は `配送_04_予定と配送データ・変更.md` §8-3「いまの決まり」（台帳 L）。下の表は旧い決まり。

**日付変更ポリシー（段階 × 入口）**〔決定v2.1 #1・#3〕〔サイクル §5.0〕〔要件 REQ-DL-865・866〕

| 段階 | スケジュール画面（04・05）の日付変更モード | 配送データ詳細（06）からの1件変更 | 理由の入力 | 対象 |
|---|---|---|---|---|
| スケジュール設定 | **ON固定・OFF不可** | できる | 任意 | 制限なし |
| オーダー開始〜締切前 | 初期OFF・ON/OFF可能。**運営が1件でも一括でも**変更できる | できる | 任意 | **移動先は本日以降。ピッキング日と納品日はリードタイムごと一緒に動く。件数の制限なし。別サイクルへの移動は警告（保存できる・配送は元のサイクル〈子契約〉のまま）、前半後半をまたぐ・他月・過去日はエラー**（2026/10/01 変更・P10-2〔要件定義まとめ RD-DL-040 2026/09/30〕。旧：制限なし） |
| **オーダー締切後** | **OFF固定・ON不可**（一括・ドラッグ操作は不可） | **出荷日の前日まで・1件ずつ・同じ前半／後半**（配送データ詳細の「編集」）〔決定v2.3 #63〕（旧：できない。取消＋複製） | **必須** | 同じ前半／後半 |

- **締切後はスケジュール画面から日付を動かせない**（日付変更モード OFF 固定）。**出荷日の前日までは配送データ詳細の「編集」から1件ずつ変えられる**（同じサイクルの同じ前半／後半・理由必須）。祝日・出荷不可日が後から増えた分もこの方法で直す〔決定v2.3 #63〕（2026/09/29 変更。旧：締切後は画面から日付を動かせない・取消＋複製〈決定v2.2 #1〉）。**（旧：`locked` 前に限り「配送データ詳細からの1件変更だけは運営に残す」。2026/09/22 第3次決定で取消）** 画面の文言：`オーダー締切（…）を過ぎています。スケジュール画面からは動かせません。出荷日の前日までは配送データ詳細の「編集」から1件ずつ変更できます（同じサイクルの同じ前半／後半・理由必須）。` 段階は**対象月ごと**に判定する。固定の状態ではスイッチを操作させず、押したら理由をトーストで返す。スイッチの横に現在の状態（`ON固定`／`切替可能`／`切替可能（運営のみ）`／`OFF固定`）と段階名を出し、タイムラインを常時表示する。**ONのときの操作**：納品日を動かした場合、ピッキング日＝新しい納品日−リードタイムとし、出荷不可日なら前の出荷可能日へ前倒しする。ピッキング日を動かした場合、納品日＝新しいピッキング日＋リードタイムとし、納品不可曜日・納品祝日扱い・サイクル休止・別のサイクルに当たる候補は選べない（納品日は自動でずらさない）。リードタイムはその配送データに効いている値（個別指定があればその値）を使い、複数件は1件ずつ計算する。変更した明細には「変更済」バッジを付け、元の日付をツールチップで示し、元に戻す操作を用意する。変更は変更履歴（いつ・誰が・どこを・何を・影響件数）に残す。画面文言：スケジュール設定＝`まだ配送データがありません（メニュー公開予定 YYYY-MM-DD）。予定の段階なので日付は自由に動かせます。OFFにはできません。`／オーダー開始〜締切前＝`オーダー受付中（YYYY-MM-DD〜YYYY-MM-DD）です。誤操作を防ぐため初期はOFF。変更するときだけONにしてください。`〔原典：納品サイクル設定 §5.0〕〔要件 REQ-DL-730〜732・749〕。ONのときは**動かす側だけでなく一緒に動くもう一方の日付も判定**し、当たる候補は非活性＋理由表示（`納品日 10/25（日）：納品不可曜日：日曜`）。**ピッキング日と納品日はリードタイムを保って一緒に動く**〔サイクル §5.0〕。

**`locked` の起点は1つだけ**〔決定v2.1 #3〕〔要件 REQ-DL-867・868〕

| 事象 | `locked` になるか | 扱い |
|---|---|---|
| 出荷指示の**2週間まとめ出力**（対象期間の開始の3日前・金曜）を作った | **ならない** | 「いつ送るか」の規定として残る。出力しただけでは `locked` にしない |
| **出荷指示が初めて送信成功した**（`ship_orders.send_status = ok`） | **なる** | `deliveries.locked_at ← sent_ok_at`、`locked_source = ship_order_sent` |
| 出荷指示の再送（`rev` を上げる・中止は数量0） | ならない | **起点は動かさない** |
| 送り状番号が付いた | **ならない** | `locked` のトリガーにしない |
| **出荷指示より先に送り状番号が現れた** | **ならない** | **anomaly（異常）として検知し要確認へ出す**（15-9・17-1 `tracking_anomaly_detect`） |

### 15-13. 出荷指示の後の変更（2026/09/22 第3次決定）

**出荷指示を送ったあとでも、配送会社②・配送スタッフ・納品先の住所は変えられる**〔決定v2.2 #3〕〔要件 REQ-DL-888〜890〕。急な変更は実際に起きるため、「`locked` だから何も触れない」とはしない。ただし**現物（送り状）と食い違わせない**ことが条件になる。

| 変えるもの | 扱い | 送り状 | 出荷指示 |
|---|---|---|---|
| **配送会社②・配送スタッフ**（レグの `carrier_id` / `driver_id`） | **そのまま変更できる** | 触らない | `ship_order_diff` を立てて**再送**する（10-3） |
| **納品先の住所** | **変更できる**（この配送だけ） | **既存の送り状をすべて `voided` にし、新しい版の出荷指示が送信成功したあとに再発行する** | **新しい `rev` の出荷指示を出す**（19-2） |
| **ピッキング倉庫**（`warehouse_id`） | **変更しない** | — | **取消＋複製**で作り直す |
| **納品日・ピッキング日** | **変更しない**（オーダー締切後は 8-3 のとおり） | — | **取消＋複製** |

- 住所だけ特別扱いするのは、**送り状に印字済み**だからである。データだけ直すと、倉庫から出ていく現物のラベルと届け先が食い違う。
- **`locked_at` は動かさない。** 住所変更で新しい `rev` を送っても、`locked` の起点（初回送信成功）は最初のままにする〔決定v2.1 #3〕。
- 操作できるのは**運営（物流）のみ**。**理由は必須**で、変更履歴に 変更前 → 変更後 と操作者を残す。**納品済・中止・取消の配送データは対象外**。
- 無効化した送り状は消さずに `status = voided` で残し、`voided_reason` に理由を持つ（16-5）。追跡ページのリンクは無効な番号だと分かる形で表示する。
- **（旧：§18 No.20「出荷指示の後でも配送会社②・配送スタッフ・納品先の住所をこの配送だけ変えてよいか」は未決だった。2026/09/22 第3次決定で解消）**
