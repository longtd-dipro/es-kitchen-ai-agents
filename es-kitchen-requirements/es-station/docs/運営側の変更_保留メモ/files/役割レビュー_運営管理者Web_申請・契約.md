### E04：長さの上限（設計書 vs DB）— 推奨

| 項目 | 設計書（= 入力の共通基準） | code（DB varchar） | 食い違いの向き |
|---|---|---|---|
| 法人名・法人名（契約）・法人名フリガナ・請求先法人名 | 60 | 120 | code が緩い |
| 拠点名・拠点名フリガナ | 60 | 120 | code が緩い |
| 市区町村（法人・拠点） | 255 | 60 | code が狭い（有効な入力を弾く） |
| 町名・番地、建物等（法人・拠点） | 255 | 120 | code が狭い |
| 配送番号（子契約） | 60 | 40 | code が狭い |
| 設置フロア（子契約） | 60 | 100 | code が緩い |

**推奨：設計書（入力の共通基準）に合わせる。** 理由と注意：

1. **出どころが違う**：設計書の値は hong が 2026-10-03 に決めた共通基準（`input_standard.md`「違うところはこちらが正」）。DB の値は 2026-09 の契約仕様（契約_03/04/05 の varchar）を写したもので、古い側が code。したがって「直す先」は code・DB と、契約仕様の varchar 表記。
2. **狭い側は不具合**：市区町村 60・町名/建物 120・配送番号 40 は、共通基準では入るはずの値を E04 で弾く。DB を広げるだけ（データの喪失なし）。
3. **緩い側は先に調査**：法人名・拠点名 120→60、設置フロア 100→60 は狭める変更。フェーズ1（約 600 社）の移行データに 60 字超が既にあると取り込めない／切り詰めることになる。①既存データの最大長を調べる ②超過がなければ DB を狭める ③超過があるときは例外（その上限／事前整形）を hong が決める。MIGR の CSV 列は現在 `len`＝「文字列」で上限が無い（#10）ので、取込のエラー基準も同時に決める。
4. **確認事項（hong）**：共通基準の「住所（市区町村・町域・番地・建物）255」は、設計書では各項目 255 に展開されている（合計 765 字になりうる）。請求書・送り状・Bill One の宛名／住所の印字上限が分からないため、**住所の合計上限が要るか**を確認してほしい（要るなら共通基準の書き方を「住所は合計 255」に直す提案）。
5. 担当者メールは 60 でなく **160**（#6、これは直すだけ）。
